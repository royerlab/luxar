● Viewer Caching Architecture

  The viewer has a multi-level caching system, but there is no cache explicitly 
  named "Lg". The naming convention uses L0, L1, L2 for the data pipeline, plus
  a separate GPU Buffer Pool for rendering. Here's the full picture:

  Data Pipeline Caches

  ┌───────┬──────────────────────────┬────────────────┬─────────┬───────┐
  │ Level │           Name           │    Location    │ Latency │ Size  │
  ├───────┼──────────────────────────┼────────────────┼─────────┼───────┤
  │ L0    │ Decompressed Chunk Cache │ In-memory (JS) │ ~1μs    │ 200MB │
  ├───────┼──────────────────────────┼────────────────┼─────────┼───────┤
  │ L1    │ Segmented LRU Cache      │ In-memory (JS) │ ~1μs    │ 100MB │
  ├───────┼──────────────────────────┼────────────────┼─────────┼───────┤
  │ L2    │ OPFS Persistent Cache    │ Browser disk   │ ~1ms    │ 2GB   │
  ├───────┼──────────────────────────┼────────────────┼─────────┼───────┤
  │ L3    │ Network (HTTP fetch)     │ Remote server  │ ~100ms  │ N/A   │
  └───────┴──────────────────────────┴────────────────┴─────────┴───────┘

  The cascade: L0 → L1 → L2 → Network

  - L0 (cache/decompressed-chunk-cache.ts) — Caches the output of Blosc
  decompression. This skips the ~2ms decompression cost entirely, giving ~2000x
  speedup on repeated chunk access.
  - L1 (cache/segmented-lru-cache.ts) — Fast in-memory cache with separate
  segments for metadata (20%) and data chunks (80%) so metadata never gets
  evicted by large data.
  - L2 (cache/opfs-store.ts) — Persistent browser storage using Origin Private
  File System. Survives page reloads. Uses 256-bucket directory sharding and
  content-hash invalidation.
  - Prefetcher (cache/chunk-prefetcher.ts) — Proactively fetches adjacent chunks
   (±1 in each dimension) on cache misses.

  GPU Buffer Pool (the "Lg" you're thinking of)

  File: rendering/gpu-buffer-pool.ts

  This is likely what you're remembering as "Lg" (L-GPU). It's not part of the 
  L0/L1/L2 data cache pipeline — it operates at the rendering layer, reusing
  THREE.BufferGeometry objects to avoid GPU memory allocation/deallocation
  churn.

  Key features:
  - Type-aware reuse — matches both size AND attribute types (Float32, Uint8,
  etc.)
  - Capacity bucketing — sizes snap to buckets (1K, 5K, 10K, 50K, 100K, 500K,
  1M) for efficient matching
  - LRU eviction — buffers evicted after 300 frames of non-use
  - In-place updates — uses TypedArray.set() for zero-copy attribute updates
  - Multi-geometry support — Points, Lines, and GSplats each have their own
  attribute schemas

  Config (config/index.ts):
  useGPUBufferPool: true,
  gpuPoolMaxSize: 20,
  gpuPoolEvictionFrames: 300,

  Summary

  There's no formal "Lg" label in the code. The cache hierarchy is:

  L0 (decompressed chunks) → L1 (memory) → L2 (OPFS disk) → Network

  GPU Buffer Pool (separate, for rendering geometry reuse)

  The GPU Buffer Pool is the closest thing to an "Lg cache" — it sits at the
  GPU/rendering boundary and prevents expensive WebGL buffer allocations. Would
  you like me to dive deeper into any specific cache?
