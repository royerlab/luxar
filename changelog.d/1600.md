#### Rewriting a gsplat dataset keeps the appearance you authored

A command that rebuilds a dataset owns its *structure*, not its look. Eleven of
them were silently dropping both: the builders construct fresh nodes that know
nothing about the input, so the writer's own defaults took over — `blending_mode`
disappeared entirely and `opacity` / `gamma` / `intensity` / `absorption` /
`offset` / `layer` / `visible` snapped back to their identity values. Tune a
dataset in the Layers panel, run almost any gsplat command on it, and every one of
those choices was gone, with a result that still looked structurally perfect.

`lod` was the case that prompted this, but auditing the rest of the family found
the same missing propagation in `additive`, `flatten`, `partition`, `decimate`,
`reencode`, `cull`, `filter`, `slice`, `transform` and `migrate-format`.
`reencode` is the one worth singling out: it advertises itself as
structure-preserving and is supposed to change nothing but the on-disk encoding,
so appearance vanishing there is the last place anyone would look —
`migrate-format` reads the same way, since upgrading a store's layout is not
something you expect to restyle it. Only `annotate-quality`, which edits in
place, was already safe; `merge` is out of scope, since with several inputs there
is no single source root to carry.

Each of them now reads the source root's compositing attrs and hands them to the
writer's lowest-precedence channel, so the command's own structural attrs still
win. Both write paths carry them — the ones that go through `GSplatData.save` and
the ones that go through `write_gsplats_tree`.

`colormap` and the amplitude/scalar display window are deliberately *not* carried:
the writer auto-defaults them per group, which sits nearer the leaf than the root
and would shadow a carried value — preserved on disk, ignored on screen. Carrying
those needs the writer to stop defaulting when an ancestor authored one, tracked
with the rest of the sweep in
[#1600](https://github.com/royerlab/luxar/issues/1600), which asks that every
command rewriting a dataset be idempotent for what it does not own.

The root's 4x4 `transform` stays behind too, for a different reason: the stored
value is already column-major, and the leaf writer runs whatever it is handed
through the row-major `prepare_transform_for_zarr`. Carrying it transposed the
matrix a second time — an authored translation made the command exit 1 on
`validate_transform`, and a rotation was silently inverted — while the
group-rooted recipes (`adaptive`, `tiles`) would have round-tripped the same
value, so one carry meant two different things. The rebuilds leave the attr alone
until the writer can tell an already-stored transform from an authored one.

The regression test is table-driven over commands rather than written per command,
so auditing the next one is a single row.
