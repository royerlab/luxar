#### L2 write queue keeps a bound without throwing away the cache

The viewer's background OPFS write queue capped the bytes its pending writes retain at the larger of the resolved L1 budget and 64MB. That charged the queue for memory it does not own: a pending write holds the very same buffer the L1 entry holds, so while the entry is L1-resident it costs one extra reference rather than a second copy, and the only genuinely extra retention is the set of writes whose L1 entry has since been evicted. On a machine whose L1 resolves to around 100MB the cap therefore bound at roughly half of what a large scene streams, and the L2 tier silently went back to dropping most of its writes — a second visit re-fetched nearly the whole store.

The allowance is now derived from the heap headroom left outside the cache pool, the same model the eager loader's working-set budget uses: half of that remainder, capped at 512MB, and 256MB where no heap signal exists at all. A small heap still gets a proportionally small bound, which is the right answer there. Overflow also drops the arriving write instead of the oldest pending one — the queue drains from the oldest end, so evicting there kept discarding the write that was about to run and left a scattered remnant on disk, whereas dropping the arrival leaves a contiguous prefix a warm revisit can serve from, at the same drop count. The performance bench now asserts the drop counter is zero on both the cold load and the warm revisit, so a cap that binds again fails the run instead of surfacing only as a slower second visit.
