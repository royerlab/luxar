#### A stacked gsplat axis survives the default (lossy) center encoding

`combine_as_new_dimension(sigma=0.0)` is the documented way to stack per-timepoint
fits into a 4D dataset — the docstring recommends `sigma=0.0` for "discrete
dimensions (e.g., time frames)". It gives the new axis an effective sigma of 1e-7,
the epsilon `trils.py` substitutes so the covariance stays positive-definite.
Saving that dataset then destroyed the axis it had just created. Centers are stored
as per-axis uint16 fixed point, whose step is `(hi - lo) / 65535`, so each value
moves by up to half a step; on a 100-frame stack spanning 0..99 that is 7.3e-4, or
**7 320 σ**. Interior frames landed far enough from where they belonged to stop
matching a slice query at all, so they simply did not render — 200 of 5 000 splats
survived. That is the worst possible symptom, because uint16 quantization is exact
at the bounds: the first and last frame of a timelapse always looked perfect while
96 of 100 were gone.

Two things made it hard to notice. It was **not** opt-in — `AUTO`, the default,
behaves identically to `MEMORY`, so any stacked dataset saved with default settings
was affected, not just the demos that named a lossy mode. And it is **not** a
large-N problem: the sigma is a fixed constant while the quantization step scales
with the axis, so even a three-frame stack puts the middle frame 153 σ off.

**The primary fix is a grid snap in the encoder.** For an axis whose distinct
values all sit on one regular grid, `hi` is widened to `lo + step·65535` so the
stored quantization grid coincides with the values and they round-trip exactly. A
100-frame stack goes from 7 320 σ of error and 200/5 000 exact splats to zero error
and 5 000/5 000, under `AUTO`, `MEMORY` and `PRECISION` alike. This costs nothing:
`lo`/`hi` are already stored per axis, so it is a scale choice rather than a dtype
change — the store stays 3.01 MB, and the decoder and the format are untouched.
Falling back to float32 instead would also be exact, but centers are one array with
one encoding, so it converts *every* axis: measured at +78% on the same store (+123%
for whole-store `PRECISION`). No demo needs to change its encoding mode.

A grid does not have to be gapless, nor exactly representable in float32, to
qualify. Eligibility is decided by replaying encode→decode over the axis's distinct
values and requiring every one of them back bit-exactly, rather than by testing the
gaps for equality — so frames `0,1,2,7,8,9` (what a spatial tile of a stacked
dataset holds, or what a filter that empties one timepoint in one region leaves
behind) and a 0.1 s frame interval both snap, where a gap-equality test would reject
them and leave them 458 σ and 734 σ off. Ordinary data is left exactly as it was:
continuous coordinates, values on no regular grid, constant (zero-extent) axes, and
axes with more distinct values than the encoding has levels are all untouched. That
selectivity matters, because this code path encodes positions, line vertices, mesh
vertices and splat centers alike. The snap reports through arbol rather than
`warnings.warn`: a warning means the caller should act, and this is a transparent
correctness fix with nothing to do that would otherwise fire on every stacked scene.

**A second, geometry-aware rail backstops what the snap cannot reach.** A snap needs
a grid; a `sigma=0` track stack merged into a fit whose time axis is *continuous*
has none, and neither does an axis with more distinct values than uint16 has levels.
There the splats really are destroyed, and only the Cholesky factors reveal it —
the coordinates alone look perfectly reasonable. `write_gsplat_arrays` is the one
place that holds `centers` and `cholesky_factors` at the same time (both the scene
compiler and the standalone `.gsplats.zarr` tree writer funnel through it), so the
check lives there. Per axis, a splat counts as *unrepresentable* when the worst-case
round-trip displacement — half the grid step — exceeds
`MAX_CENTER_DISPLACEMENT_SIGMAS` (1.0) times that splat's own marginal σ, and the
centers fall back to float32 when more than `MAX_UNREPRESENTABLE_SPLAT_FRACTION`
(0.1%) of the splats are unrepresentable on some axis. The warning names the axis,
the step, the displacement bound, how many splats are affected and their median σ.
The marginal σ is read straight off the packed lower-triangular rows
(`Σ[i,i] = Σ_{j≤i} L[i,j]²`) in one `N·k` pass, without materializing the `(N, d, d)`
matrices.

The rail defers to the snap rather than duplicating its work. An axis that trips the
population gate is tested with the encoder's *own* grid predicate — the same
function, not a proxy — and skipped when the encoder is going to store it exactly;
otherwise a stacked axis, where 100% of the splats are formally unrepresentable,
would escalate the whole centers array to float32 and warn loudly about data that
round-trips bit for bit. The predicate is consulted lazily, only for an axis that
has already tripped, because `np.unique` per axis is real time (0.30 s of a 2.85 s
encode on 5M×3 coordinates) and a tripped axis is rare.

The snap is not the encoder's only exact path, and the rail has to know all of
them: LUT encoding (priority 3) is tried *before* the dtype encoder, stores the
original values verbatim at ~1 B/value, and is skipped in `PRECISION`. Escalating
a LUT-eligible centers array therefore replaced an exact 1 B/value encoding with
an exact 4 B/value one — 240,000 B instead of 60,000 B on a 20,000×3 measured
case — while warning about a displacement that was never going to be applied. A
public `ArrayEncoder.encodes_as_lut` now answers that question, asked (like the
grid predicate) only once an offender has been found, so the common path pays
nothing. Separately, a 1-D COORDINATE array used to encode to something nothing
could read back: the per-column reductions produce 0-d rails, which were stored
as bare JSON scalars and rejected on decode. Its rails are always 1-D lists now,
and both sides read a 1-D array as one column of N values.

Both of the rail's numbers are keyed on **harm**, not on jitter. A center moved by
less than one σ is still inside the core the splat was fitted to describe, with the
displacement bounded by the splat's own width rather than by the axis extent, so it
renders essentially where it did. That is not a claim that every query answer
survives — a slice query matches out to roughly `tolerance + coverage_sigma·σ`, so a
splat right on that boundary and pushed the permitted 1.0 σ outward drops out of it,
and because the test is *per axis* a 4-D center may move a full σ on all four at
once (2 σ in Mahalanobis terms for a diagonal Σ) with every per-axis check passing.
What the bound does rule out is the failure the rail is for: past ~1 σ the center
leaves that footprint altogether. A tighter per-splat line charges 2× the centers
bytes for sub-voxel error — measured on 200,000 splats spread over an 8192-voxel
axis with 5% pinned at the fitter's `sqrt(1/12) ≈ 0.2887` σ floor, the step is 0.125
voxel, so the worst displacement is 0.0625 voxel = 0.217 σ; that is 12.9% of splats
"unrepresentable" at a quarter-σ line and 0.03% at this one.

Because the per-splat line is strict, the population gate can be tight. Under the
displacement criterion the benign populations collapse — worst measured axis: 0.015%
for a 20,000-splat random-`U(0, 1)`-Cholesky fixture, 0.0005% for a 200,000-splat
SPZ-like log-normal scale distribution (0.001% with an added σ=1e-6 needle), 0.03%
for the light-sheet case above — so 0.1% still clears every one of them by 3× or
more while catching what a 1% gate missed: a degenerate *minority*. Merging a
2,000-splat `sigma=0` track stack into a 300,000-splat fit with a real `σ_t = 3.0`
leaves 0.662% of the splats displaced by up to 1,373 σ, and under the old gate the
rail stayed silent while only 10% of the tracks still landed on their own frame. It
remains a population test, not a minimum: real fits routinely contain a handful of
needle Gaussians — an SPZ import decodes scales as `exp(u8/16 - 10)` with a 4.5e-5
floor — and a single such splat must not double every centers array on disk
(measured: 3.18 MB → 6.23 MB of centers, +54% on a 600k-splat store).

The limitation that buys is real and worth stating: up to 0.1% of a store can still
be quantized away with no warning at all — 1,650 splats on a 1.65M-splat fit, or 100
`sigma=0` tracks merged into a 150,000-splat time-axis fit, 61 of which end up off
their own frame while the rail stays silent. Displacement magnitude cannot separate
those two populations (an ordinary `U(0, 1)` Cholesky draw yields σ = 1e-9 and
thousands of σ of displacement), so a small tracked sub-population that must land
exactly on its coordinate — and that no grid describes — should be saved with
`EncodingMode.PRECISION` rather than left to the rail. Note too that a *fraction*
tightens at small N: one unrepresentable splat trips the whole array whenever
N ≤ 999. And the verdict is taken per WRITE — that is, per leaf — so a
partitioned or laddered node decides part by part: an 8-tile `tiles` recipe emits
up to eight separate warnings, and within one logical node the centers dtype can
differ between parts, a part whose degenerate splats fall under the gate keeping
uint16 while its sibling escalates. Deferring to the snap sharpens the residual
in one more way, deliberately: escalation used to *incidentally* rescue sub-gate
needle populations on the other axes of a stacked store (centers are one array
with one encoding, so escalating for the time axis made every axis exact), and a
gridded stacked axis now keeps uint16 instead, so those axes are held to the 0.1%
gate like any other array's.

Only the **centers** escalate. The Cholesky, amplitude and color tiers keep whatever
the caller asked for — the published cell-tracking bundle depends on the Cholesky
staying uint8, and inflating it 4× would buy nothing. An escalated centers array is
also written with `deduplicate=False`. The encoder's content-dedup registry is keyed
on the centers **bytes**, but the rail's verdict depends on a *sibling* array
(`cholesky_factors`) that the registry does not key on — so two nodes with
byte-identical centers and different Cholesky collapsed onto whichever was written
first, and the escalated node was stored as a `(0, d)` `array_ref` pointing at the
other node's `linear_perchannel_u16` array. It then read back quantized: the original
bug verbatim, behind a warning claiming it had been prevented. Skipping the registry
is the whole fix, since `ArrayRefRegistry.check` both looks up and registers, so an
escalated array that never calls it neither resolves to a lossy target nor becomes
one.

The rail also stands down once an axis reaches `COORDINATE_U16_MAX_EXTENT` (2¹⁶, now
single-sourced in `typing_utils.constants` so the two rails cannot drift). The
encoder's extent rail already stores such an array as float32, exactly, and says why
— "extent ≥ 2¹⁶; uint16 fixed-point cannot resolve a unit step" — which is the
useful diagnosis for a scene that is merely very large. Firing here as well would
replace it with one pointing at a degenerate axis that is not there, and would drop
the array's content dedup for a verdict that depends on the centers bytes alone.

Four 4D demos (`cell_tracking_challenge`, `celegans_tracking`, `nexrad_supercell`,
`zebrafish_timelapse`) also cached each per-timepoint fit under `MEMORY` and then
stacked the *in-memory* object rather than what had just been written, while their
cache-hit branch loaded the store back. A cold run and a warm run therefore stacked
different splats. Each now returns what it stored, so the two runs agree — and both
branches load with `include_stats=True`, so the fit's normalization provenance (the
background floor of #1175) still reaches the stacked scene through
`agreed_normalization_stats`.
