#### Tiled partition split planes are stated in the splats' own frame

`luxar gsplat fit --tiling uniform --downscale N -j>1` wrote a `kind=partition`
whose `bsp_tree` split planes were stated in DOWNSCALED voxels while the splats
inside the parts were in full-resolution ones. Every plane was therefore a
factor of N too small and no longer lay between the parts it separated, so the
viewer's back-to-front part ordering (#1555) was computed against planes that
separate nothing — the seam popping that tree exists to prevent, back again on
exactly the datasets large enough to need `--downscale`. Part LABELS were always
correct.

The frame mismatch is deliberate, not accidental: `dispatch_parallel_tiled`
computes its tile grid on the post-downscale shape so that the parent and its
`fit --tile i/M` workers agree on the tile count M, while each worker rescales
its own splats back to original coordinates before writing. What was missing was
the reconciliation at the merge. `grid_bsp_tree` now takes an optional per-axis
`scale` — a tile spanning `[origin, origin + shape)` maps to
`[origin * f, (origin + shape) * f)`, the same convention `rescale_centers`
applies to the centers.

A `voxel_size` is the second, independent term of the same mismatch, and it
composes with the first. The tile grid is always in VOXELS, but a fit with
`output_space="real"` (the CLI default) offsets each tile by
`origin * voxel_size`, so a `voxel_size` supplied through `--config` moved the
splats and not the planes — on the SEQUENTIAL partition path too, with no
`--downscale` anywhere in sight. A downscaled parallel fit applies both factors
to its splats (`voxel_size * f * origin`), so only their product reconciles the
frames. `resolve_grid_scale` computes that product once (dropping the
`voxel_size` term when the fit emits `output_space="voxel"`, where the centers
stay in voxels), and it reaches `merge_tile_results` as a single `grid_scale`
keyword from both callers — `fit_tiled` calls that merge directly, while
`dispatch_parallel_tiled` passes the factor through `fit_tiled_parallel`.
Nothing else consumes it; `volume_shape` keeps its existing meaning (the shape
the grid was computed on) for the stats block and the empty-result fallback.

The `batch-fit` merge is the third producer and had the same bug. `batch-fit
run --config` / `submit --config` forward the YAML **verbatim** to every
`fit --tile k/M` worker, so a `voxel_size:` in it moved every task's splats
while `_uniform_slot_bsp_tree` kept building planes from the manifest's
`spatial_shape` in voxels. Measured on a 32³ store with
`--tile-size 12 --overlap 2` and `voxel_size: [4.0, 1.0, 1.0]`: axis-0 planes at
11/21/31 where the splats want 44/84/124 — every plane in the first quarter of
the object, separating nothing.

The frame is now resolved **at plan time**, where the merged fit config is
already in hand, and recorded on the manifest as `grid_scale`; the merge simply
reads it and hands it to `grid_bsp_tree`. Re-deriving it at merge time instead
would mean re-reading a YAML by path days after submission: gone, and the planes
are dropped; replaced by an unrelated same-named file, and they are silently
restated in whatever frame *that* file describes. The recorded `--config` path
is now `.resolve()`d as well, like every other path on the manifest, since it is
handed to workers that run from a scheduler's own working directory. An absent
`grid_scale` means no scale — the common case, and also what every manifest
written before this field says, so an old batch merges exactly as it did.

(A `downscale:` in a batch `--config` composes into the same term, for parity
with the single-fit convention, but such a run cannot currently reach a merge at
all: the planner decomposes the FULL-resolution shape while each worker
recomputes the grid on the decimated one, so the tile counts disagree and the
tasks fail. That is a separate pre-existing gap, untouched here.)

The fourth producer, `--tiling content`, is genuinely safe and unchanged:
`_fit_one_box` strips a `voxel_size`/`output_space` pair with a warning, an
inner `--downscale` is rescaled back to the box's own full-resolution voxels by
`fit_gaussian_splats` itself, and the box tree comes from the same voxel boxes
that were cropped.

Two knock-on corrections. `--refine volume` is now refused under a real-space
`voxel_size` exactly as it already was under `--downscale`: a per-part re-fit
reads its part's `bsp_tree` cell as VOXEL INDICES into the source, so a cell
stated in physical units crops the wrong sub-volume (and the never-worse guard
compares against that same wrong crop). `reject_downscaled_volume_refit` is
renamed `reject_rescaled_volume_refit` accordingly. The batch merge has the same
defect and now refuses it too, off the recorded `grid_scale` — at the merge
front door, and already at plan time when `--merge-refine volume` is given
there, so a typo costs nothing instead of surfacing after every tile has been
fitted. Both signs of the mismatch bite: a factor above 1 makes the crop too
large and the re-fit degenerates into a wasteful no-op, while below 1 it shrinks
to a wrong region the seed still sits inside, so nothing downstream notices.

And `resolve_grid_scale`, now public, validates its inputs like the fitter does
instead of absorbing them: an `output_space` outside `("real", "voxel")` raises
rather than silently dropping the spacing term, and a wrong-length `voxel_size`
is named rather than broadcast.
