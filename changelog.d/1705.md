#### Local E2E parallelism is sized to the machine, not hardcoded at 4 (#1705)

`playwright.config.ts` ran `workers: process.env.CI ? 1 : 4` locally. Four is a
defensible CEILING — the binding resource is the GIL-bound
`python3 -m http.server 9000` dataset server, which is why
`all-examples-smoke-test.spec.ts` already carries a 120 s timeout to "absorb
HTTP-server contention" — but it is not a target. A developer workstation shared
with CI runner slots and other jobs sits at a 1-minute load average of 12–24 on
16 cores, and four more Chromium instances on top of that starve the very input
handling Playwright's action timeouts measure.

Measured on such a box: `dimension-animation.spec.ts` failed **15 of 21** tests at
the config default of 4 workers and passed **21 of 21** in 3.3 min at
`--workers=1`. Every failure was a bare wall-clock timeout with no product cause —
`page.click: Timeout 10000ms exceeded` whose own call log reports the element
visible, enabled and stable before the hit-target step never gets a turn, plus
`page.evaluate` test timeouts. At one worker the page was demonstrably responsive:
an in-page round trip measured a median of 145 ms idle and 90 ms with a dimension
animation playing — both well under a second, animation playing or not — and a
real DOM click was serviced in 869 ms / 1216 ms respectively.

The ceiling is now scaled by the box's FREE FRACTION:
`clamp(round(4 * (cpus - load1) / cpus), 1, 4)`. Because the count is rounded to
nearest, the bands are fractions of the box and hold at any size: four workers
while at least 7/8 of the box is free, three down to 5/8, two down to 3/8, one
below that. On 16 cores that is four up to a load average of 2, three up to 6, two
up to 10, and one above that. The scaling is deliberately scale-free, so an
**idle** box of any size — a 2-core laptop included — still runs at the historical
four; the count only ever backs off under load, turning a red run into a slower
one. When either half of the signal is missing the ceiling is returned unchanged,
which is what "no signal" means; Windows, whose `os.loadavg()` is a hardcoded
`[0, 0, 0]`, is detected explicitly and reported as no signal rather than mistaken
for an idle box.

The mechanism is a heuristic and worth only so much. Two counts were measured — 4
(15/21 failing) and 1 (21/21 passing), both at load 12–24 on 16 cores, so 16 cores
at load 12 → 1 is the configuration actually observed green; the intermediate 2 and
3 the formula can select are interpolation. The 1-minute load average lags by
construction and is read ONCE, at config load, so a run launched just after a burst
ends can crawl on a box that is already idle again, while one launched into a lull
can take all four workers straight into the next burst: the protection is
probabilistic, the slowdown it costs is certain. On Linux the load average also
counts uninterruptible-sleep tasks, so heavy I/O elsewhere (a fixture generation, a
`git lfs pull`) throttles the suite for contention it is not competing in.
Sampling `os.cpus()[].times` twice would give a lag-free signal instead, but it
needs a ~150 ms wait and Playwright re-evaluates the config module in every worker
process as well as the parent, so that wait would be paid N+1 times per run — the
lag is cheaper than the startup cost. The wall-clock guards in
`nd-navigation.spec.ts` (8000 ms) and `worker-wasm-integration.spec.ts` (10000 ms)
get correspondingly more headroom on a loaded box than the same box would give them
at four workers; their comments now say exactly that, and stop short of comparing
machines, because a loaded box at one worker still needed 869–1216 ms to service a
real click.

The arithmetic is a pure, unit-tested function in
`packages/luxar-viewer/tools/e2e-workers.ts`; only a thin resolver touches `os`
and the environment. The run's decision is printed as one line —
`[🧵] [E2E] parallelism: max 1 worker — 16 cpus, load1 22.2 (capacity)` — from the
E2E **global setup** rather than the config module, because Playwright applies
`--workers=N` (and `--debug`, which forces 1) only after the config has
been evaluated: stamping it at config load printed four workers for a run that went
on to use one. The stamped count is the run's CEILING (`config.workers`), which is
why it reads `max`: Playwright narrows it to
`min(workers, maxConcurrentTestGroups)` after global setup, so a single-file run of
a spec pinned to one worker is stamped `max 3` and then reports "using 1 worker".
A ceiling that differs from what was sized prints both numbers —
`(capacity sized 3, run with 1)` — and claims no cause, since `--workers=N`,
`--ui`, a connected watch session and `playwright.perf.config.ts`'s own
`workers: 1` all produce that divergence. The line goes to stderr so it cannot
corrupt `--reporter=json`. Pin the count with `LUXAR_E2E_WORKERS=N`, clamped to
`[1, cpus]` as a typo guard for `=40` on a 16-core box — a pin may still exceed the
ceiling of four, which is the point of an explicit pin — or with Playwright's own
`--workers=N`, which overrides the config outright. CI stays unconditionally
serial. `points-rendering-perf.spec.ts`, whose JSON summary exists to be diffed
between runs, now records the concurrency it measured under and the load average
at capture time.
