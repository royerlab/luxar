#### Local E2E parallelism is sized to the machine, not hardcoded at 4 (#1704, #1705)

`playwright.config.ts` ran `workers: process.env.CI ? 1 : 4` locally. Four is a
defensible CEILING — the binding resource is the GIL-bound
`python3 -m http.server 9000` dataset server, which is why
`all-examples-smoke-test.spec.ts` already carries a 120 s timeout to "absorb
HTTP-server contention" — but it is not a target. A developer workstation shared
with CI runner slots and other agents sits at a 1-minute load average of 12–24 on
16 cores, and four more Chromium instances on top of that starve the very input
handling Playwright's action timeouts measure.

Measured on such a box: `dimension-animation.spec.ts` failed **15 of 21** tests at
the config default of 4 workers and passed **21 of 21** in 3.3 min at
`--workers=1`. Every failure was a bare wall-clock timeout with no product cause —
`page.click: Timeout 10000ms exceeded` whose own call log reports the element
visible, enabled and stable before the hit-target step never gets a turn, plus
`page.evaluate` test timeouts. At one worker the page was demonstrably responsive:
an in-page round trip measured a median of 145 ms idle and 90 ms with a dimension
animation playing, and a real DOM click was serviced in 869 ms / 1216 ms
respectively. Two issues (#1704, #1705) were filed as viewer regressions on the
strength of timeouts of this class.

The count now comes from the box's spare capacity:
`clamp(floor((cpus - load1) / 2), 1, 4)`. The `/2` budgets about two cores per
worker, because each one costs a whole Chromium (renderer process, GPU process,
the viewer's own DedicatedWorker pool) plus a share of that single-threaded
dataset server. A loaded box therefore produces a slower run instead of a red one,
while an idle box still runs at the ceiling. When the load average is unavailable
or nonsensical the ceiling is returned, so the old behaviour is what "no signal"
means; Windows' `[0, 0, 0]` reads as a genuinely idle box, which is the right
answer there.

The arithmetic is a pure, unit-tested function in
`packages/luxar-viewer/tools/e2e-workers.ts`; only a thin resolver touches `os`
and the environment. Every run prints the decision and its inputs as one line —
`[🧵] [E2E] parallelism: 2 worker(s) — 16 cpus, load1 24.1 (capacity)` — so a
suspicious run records what it actually ran with. Pin the count with
`LUXAR_E2E_WORKERS=N`, or with Playwright's own `--workers=N`, which still
overrides the config outright and is how the E2E daemon and the promotion job hold
themselves to a single worker. CI stays unconditionally serial.

No timeout was relaxed and no spec was touched.
