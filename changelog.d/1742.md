#### A demo that is empty at its default slice can finally be captured

`fractals_4d` and `gsplats_6d_kidney_multichannel_toggles` were the only two
gallery demos with no still and no orbit video. Both died the same way — the full
5-minute capture budget elapsed with nothing on screen — and neither demo was
broken. Each was EMPTY at its default slice position, and the harness could not
reach the one manifest feature that fixes that.

`waitForDataLoaded` gates on `!isLoading && totalElements > 0` and ran BEFORE the
`dimensionNav` step, so a scene that holds nothing until a hidden dimension is
stepped could never get there: the gate waited for elements that only the
navigation produces. `dimensionNav` was structurally unusable for exactly the
demos it exists for, which is why adding it to the manifest alone changed nothing.
The element requirement is now a flag — a `dimensionNav` demo waits only for the
loader to settle, navigates, and is then held to the usual non-empty check, so an
empty canvas still fails rather than being quietly published.

`initialized` (which `waitForLuxarReady` already waits for) is only set after the
initial `loadScene` returns, so dropping the element requirement does not let the
navigation run against a scene that has not loaded yet — it only stops requiring
that the loaded scene have something at its starting slice.

Why each demo is empty is worth recording, because the two causes are unrelated:

`gsplats_6d_kidney_multichannel_toggles` has three binary channel axes
(`nuclei`/`wga`/`actin`, each `range [0,1]`) and one node per channel parked at a
one-hot position — `(1,0,0)`, `(0,1,0)`, `(0,0,1)`. A discrete non-displayed dim
starts at its range minimum with tolerance 0, so the initial slice is the all-off
origin `(0,0,0)`, where no node sits. That is inherent to a toggles demo: all-off
correctly shows nothing. One step on `nuclei` brings up 50,997 splats. The scene
now authors an all-on opening state, so regenerated stores no longer start empty.

`fractals_4d` is a STALE-STORE artefact, not a property of the shipped demo. The
`fractals_4d.luxar.zarr` this was measured on predates #842: `w` was continuous
over `[-2.5, 2.5]` with `step 0.1` (51 navigable positions) while slices existed
only at about `1.0` spacing, so nine in ten positions — including the default
`-2.5` — were empty, and stepping `w` 15 times was what reached `-1.0` and 40,040
points. Since #842 the generator declares `w` discrete on the grid it actually
writes (`step = 2/grid_size`, every slider stop a data plane), so a regenerated
store is populated at its default slice and needs no `dimensionNav` at all. The
manifest keeps the entry, with a note, because it is what makes the demo
capturable on a machine that still has the old store — but its `steps`/`zoom`/
`exposure` are calibrated against that store and want re-deriving once the
dataset is rebuilt. (The drifting step values seen while walking that old axis —
`-2.4000000000000004`, `-1.9000000000000001` — come from the same place: a
CONTINUOUS dimension accumulates `pos + step` without snapping. A discrete dim
rounds to `k·step` on every move, so it does not drift.)

The kidney entry's former `dimensionNav` values were found by walking the
dimension and watching the element count, not guessed; they were removed once
the scene began authoring its populated opening state.
