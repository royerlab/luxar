#### The WebGL default path stops downloading the WebGPU renderer

The production default backend is WebGL, but every session — WebGPU or not — was
fetching and parsing the entire three.js node system before first paint.
`dist/index.html` `modulepreload`ed the `three-webgpu` chunk and the entry chunk
imported it statically, so roughly a quarter of the initial JavaScript was a
renderer that only runs when someone passes `?renderer=webgpu`.

The whole TSL cone now hangs off a single `await import()` in
`rendering/tsl/load.ts`, reached only from `SceneManager.setupWebGPURenderer()`.
Measured on the production build, the eagerly-loaded JavaScript drops from
794 kB to 598 kB gzipped — **196 kB, about a quarter, off the critical path** —
with no change to what either backend renders.

Getting there meant cutting six independent static edges, not one. The
`MaterialManager` dispatch tables hold thunks instead of classes; the
`ShaderSource.webgpu` closures stay next to their GLSL twin but obtain their
factory from the registry instead of importing it; `material-sync-helpers.ts`
identifies material families by structural probe rather than `instanceof` on TSL
classes; `erfPolyTSL` moved out of `erf.ts`, whose pure-CPU `erfRef` was pulling
`three/tsl` into the GLSL gsplat material; and `createWebGPURenderer` imports the
renderer class inside the function that needs it. The nine TSL material classes
keep their ordinary `extends NodeMaterial` shape — only the module graph above
them changed, so no test needed to become async.

The last edge was not in the source at all. `three.core.js` is shared by
`three.module.js` and `three.webgpu.js`, and with no chunk group of its own it
landed such that the plain `three` chunk imported `three-webgpu` — pinning the
WebGPU system into the eager graph while every source file was already clean.
`vite.config.ts` now splits the shared core into its own `three-core` chunk.

Two gates keep it from coming back, because those two failure modes need
different instruments. An ESLint `no-restricted-imports` rule bans value imports
of `three/webgpu` and `three/tsl` outside the registry (type-only imports stay
legal). And `scripts/check-eager-chunks.mjs`, chained into `pnpm build`, asserts
against the built `dist/` that nothing statically reachable from the entry
imports the chunk — and that the chunk still exists, so deleting WebGPU support
is not a way to pass. Both were verified to fail on the real regressions before
being trusted; a dependency-cruiser rule was tried first and dropped once it
turned out it could never fire, since that config excludes `node_modules` from
its graph.
