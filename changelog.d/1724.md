#### A starved E2E state probe now says so, instead of spending the whole test budget

`getLuxarState` was the last of the two probes the E2E suite leans on that still
ran an unbounded `page.evaluate`. On a page whose frame loop has saturated the
main thread, that probe does not fail — it simply never answers, so the run
reported a bare `Test timeout of 120000ms exceeded` pointing at a line inside the
helper, with nothing to say which dataset or which probe was pending. It is now
deadline-bounded at 45 s like `getConsoleMessages`, and throws a diagnostic that
names the starvation and the viewer bug behind it. The sentinel it races against
is a fresh Node-side object rather than `null`, because `getState()` is an
untyped payload the viewer may reshape: a primitive sentinel would turn a
legitimate falsy answer into a bogus "main thread saturated" verdict.

The four poll loops that call it (`waitForPointsLoaded`,
`waitForDimensionNavigation`, and the two silent variants) catch a failing probe
and retry, since a missing debug interface is legitimate during initialization.
That catch was swallowing the new diagnostic whole, so the two throwing loops now
carry the last probe failure into their own timeout message — otherwise a
saturated main thread is reported as missing data. They deliberately do NOT clamp
the probe to their own remaining budget: these loops succeed on any satisfying
answer, so clamping would newly fail a healthy-but-slow page across some sixty
call sites.

`performance_benchmark_example.luxar.zarr` is parked in the smoke spec's
`KNOWN_FLAKY_LARGE_DATASETS` while the underlying viewer bug is open: that
100-node scene collapses to ~1 fps about 30 s after it loads and starves the
control channel hard enough that a 0.5 ms `getState()` took 111 s to cross the
bridge. The 100-node load path therefore has no smoke coverage until that is
fixed.
