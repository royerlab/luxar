#### One uniform tile grid for every fitting entry point

`luxar gsplat fit --tiling uniform` used the historical unfolded tile grid and
an equal-share seed fallback while `batch-fit` used the folded grid and
occupancy weighting, so the same volume produced a different fit depending on
which command launched it. On `(108, 1352, 532)` at `--tile-size 512 --overlap
32` that was 6 tiles against 3. Every producer now builds the folded grid — the
sequential in-process path, the `-j N` parent and its workers, the hand-run
`fit --tile k/M` worker, `batch-fit`, and the `fit_tiled` /
`fit_tiled_gaussian_splats` Python API.

An integer whole-volume `--seeds K` is now apportioned by the same saturated,
Hann-weighted occupancy rule on both `--tiling uniform` paths (sequential and
the `-j N` parent), each tile receiving its exact count rather than a divided
share — the rule `batch-fit` already used. The weighting is **not** universal,
and the two remaining equal-share cases are deliberate: a hand-run `fit --tile
k/M` worker has no parent to hand it a count and would have to scan the whole
volume to compute one, and a `batch-fit` plan falls back to the equal share
when it cannot resolve tile-local reads (`--downscale`, `--denoise`, a deferred
or volume-derived floor, no plan-resolved `--norm-range`) or — on Slurm only —
when the inline seed table would be too large for the generated script. A tile
the allocator gives zero seeds holds no signal and is no longer handed to the
fitter, at the `fit_tile` door rather than only in the in-process loop, so a
`--tile-seed-count 0` worker skips it too instead of hitting "seeds as int must
be positive". The `--tile k/M` path now logs the grid it resolved, so a user who
computed `M` by hand can see what was actually built.

Note that folding makes one tile per axis BIGGER than `--tile-size`: it spans
up to `tile_size + overlap - 1` voxels, which at the 256/32 default is 287, or
1.41x the voxels of a full tile in 3D (256/64 is 1.93x). `--tile-size` is the
GPU-memory knob, so size it for that worst case; `-j auto` and the local batch
runner already account for it.

**This changes output.** The same command line on the same volume now fits a
different number of tiles, over different regions, with different per-tile seed
budgets. A fitted store regenerated after this lands will differ from its
predecessor by much more than a `content_hash` bump: splat count, splat
positions, and the partition's parts all move. That is the fix, not a
regression — do not diff an old fit against a new one and file the difference.

**Library-visible behaviour change.** `fit_tiled_gaussian_splats` (and its
`fit_tiled` alias) now default `fold_tile_slivers=True` instead of `False`, and
the grid primitive underneath them — `compute_tile_specs`, exported from
`luxar.gsplats` and documented in the API reference — defaults
`fold_slivers=True` to match. A direct Python caller that relied on the old
unfolded grid gets a different decomposition; pass `False` to reproduce it. A
third grid — CLI folded, Python API unfolded — was judged worse than a one-time
output change, and leaving it reachable at the most primitive public entry point
would have kept a hand-rolled `compute_tile_specs` + `fit_tile` loop (the shape
the README documents for distributed workflows) tiling a volume differently from
every command. The hidden `--fold-tile-slivers` worker flag gained an explicit
`--no-fold-tile-slivers` spelling, which every producer now emits when a stored
batch manifest records the legacy geometry, so a resumed legacy plan still
builds the grid it was planned on.

**One meaning for a user `--floor` on every uniform entry point.** A numeric
`--floor` a USER typed is now guarded the same way wherever it lands — under
`--tiling none`, the sequential `--tiling uniform` path, a `-j N` parent, and a
hand-run `fit --tile k/M`: a level at or above the volume's sampled maximum is
reported and ignored rather than windowing every tile to zero. Previously a
`-j N` run with an integer `--seeds` applied it instead, so `--tiling uniform -j
2 --tile-size 24 --overlap 4 --seeds 200 --floor 200` on a volume topping out at
1.0 failed the whole run with `Cannot write empty points (0 points)` — naming
neither the floor nor `-j` — while the same command at `-j 1` fitted normally.
A level a PARENT resolved is still applied verbatim by its workers (#1174): the
two are now told apart by a hidden `--floor-resolved` marker alongside the
forwarded level, rather than by the worker's guard being off for everyone.
