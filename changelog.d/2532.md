#### `luxar gsplat info` no longer loads a whole store to describe it

Pointed at a partition or nested `.gsplats.zarr`, `info` decoded every array of every
leaf into memory — three separate times. Once for a flat load that raises for a tree
and was discarded, once as a validity check whose result was thrown away, and once for
the summary itself. On a 10-part store of 960,000 splats occupying 6.4 MB on disk, that
was 120 decode calls and 115 MB of arrays, to print 25 lines of metadata. The
operational record has the same shape reaching 116 GB of memory on a 13 GB store.

Everything `info` prints about a tree — its kind, dimensionality, per-leaf splat counts,
bounds and fitting record — lives in the store's attributes and array metadata, so it is
now read from there. The same store decodes nothing at all, and `info` additionally
reports what a full load *would* materialise.

`load_gsplat_node(..., warn_if_large=True)` can run the same metadata walk before
allocating and warn when a load will exceed roughly 4 GiB. The preflight is opt-in
because its cost scales with the number of leaves, so normal loads retain their
existing performance. It warns rather than refuses: loading a very large tree is
legitimate on a machine sized for it.
