#### Depth sorting recovers when worker init loses a 30 s race to a busy main thread (#1694)

`ensureWorker()` in the depth-sort coordinator caches its `initPromise` and races
the Comlink `initialize` RPC against a 30 s deadline. The deadline exists for a
real reason: a worker whose script dies during async module evaluation emits an
`error` event but never settles that RPC, and every order-dependent commit
attaches a continuation to the cached promise — closing over its centers provider,
which for points pins a whole `LoadedPointsData`. Left pending, those closures
accumulate one per commit forever, so the promise MUST settle. What did not
follow is that it must settle *permanently*: the cached rejection stood for the
session, so every later commit fell into the warn-once path and the identity
(storage) ordering was what got drawn, with nothing but one console line to say
so. At ~3M points (`demo_gaia_milky_way_3m`) the main thread is saturated long
enough during load that worker startup simply loses the race, and a condition
that would have cleared in seconds disabled depth sorting for the rest of the
session — 200k and 1M sorted correctly, 3M rendered unsorted indefinitely.

The settle contract is unchanged; the failure is now CLASSIFIED. Only the
deadline timer rejects with the module-private `SortWorkerInitTimeoutError`; a
worker `error` event, a rejected `initialize`, and a constructor throw (a
CSP-blocked script) all stay permanently fatal, because nothing about waiting
longer would help them. A missed deadline is retried at most 3 times in total
(the initial attempt plus 2), with a 2 s-per-miss backoff on the monotonic
`performance.now()` clock. The bound is what keeps the anti-leak property: each
attempt opens one more 30 s window in which commits can queue continuations, so
the number of windows has to be finite — and between attempts the cached
rejection is still what every commit drains into, exactly as before.

The retry is driven from the per-frame scheduler rather than a timer, because the
frame loop is where "the main thread has room again" is observable, and it is
already gated on the conditions a retry must respect: it runs after the
`isLoadInProgress` early return (the in-flight sweep IS the starvation), and it
declines to spend an attempt during an offline capture or on a scene where no
visible, still-committed, order-dependent node actually wants sorting. A late
success then has to get the centers across, since the fresh worker holds no
registrations and the coordinator retains no centers by design: it invalidates
both freshness stamps and requests one reprocess — the same two-line recovery the
switch-to-sorted blending-mode hook has always done, now factored into one shared
helper so the two cannot drift.

The console message no longer claims more than it knows ("drawing the identity
(unsorted) order", plus whether a retry is pending), the warn-once flag is
re-armed by a successful init so a later genuine failure is still reported, and
the starved / gave-up transitions log their own lines. The degrade is also
inspectable rather than console-only: `getDepthSortWorkerStatus()` reports
`idle` / `ready` / `starved` / `failed` and the deadline-miss count.
