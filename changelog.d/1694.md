#### Depth sorting recovers when worker init loses a 30 s race to a busy main thread (#1694)

`ensureWorker()` in the depth-sort coordinator caches its `initPromise` and races
the Comlink `initialize` RPC against a 30 s deadline. The deadline exists for a
real reason: a worker whose script dies during async module evaluation emits an
`error` event but never settles that RPC, and every order-dependent commit
attaches a continuation to the cached promise — closing over its centers provider,
which for points pins a whole `LoadedPointsData`. Left pending, those closures
accumulate one per commit forever, so the promise MUST settle. What did not
follow is that it must settle *permanently*: the cached rejection stood for the
session, so every later commit fell into the warn-once path and the identity
(storage) ordering was what got drawn, with nothing but one console line to say
so. At ~3M points (`demo_gaia_milky_way_3m`) the main thread is saturated long
enough during load that worker startup simply loses the race, and a condition
that would have cleared in seconds disabled depth sorting for the rest of the
session — 200k and 1M sorted correctly, 3M rendered unsorted indefinitely.

The settle contract is unchanged; the failure is now CLASSIFIED. Only the
deadline timer rejects with the module-private `SortWorkerInitTimeoutError`; a
worker `error` event, a rejected `initialize`, and a constructor throw (a
CSP-blocked script) all stay permanently fatal, because nothing about waiting
longer would help them. A missed deadline is retried at most 3 times in total
(the initial attempt plus 2), with a 2 s-per-miss backoff on the monotonic
`performance.now()` clock — a window of at worst ~96 s of wall clock, three
deadlines plus the two backoffs. The bound is what keeps the anti-leak property:
each attempt opens one more 30 s window in which commits can queue continuations,
so the number of windows has to be finite — and between attempts the cached
rejection is still what every commit drains into, exactly as before.

The retry is driven from the per-frame scheduler rather than a timer, because the
frame loop is where "the main thread has room again" is observable, and it is
already gated on the conditions a retry must respect: it runs after the
`isLoadInProgress` early return (the in-flight sweep IS the starvation), and it
declines to spend an attempt during an offline capture or on a scene where no
visible, still-committed, order-dependent node actually wants sorting. Because
the render loop is on-demand and idle-pauses after `animation.idleTimeoutMs`,
arming a retry also arms exactly one wake-up `setTimeout` that requests a frame
just after the backoff expires — otherwise a static "load it and look at it"
scene, whose loop pauses at or before the first eligible instant, would never run
the scheduler again and never recover. If that wake fires when there is no
`requestRender` to call at all — before `configureDepthSort`, or while an offline
capture has deliberately nulled it — it re-arms the same delay instead of being
spent on nothing while the retry stays armed.

A late success then has to get the centers across, since the fresh worker holds no
registrations and the coordinator retains no centers by design: it invalidates
both freshness stamps on every unregistered, still-committed, order-dependent node
and requests one reprocess — the same two-line recovery the switch-to-sorted
blending-mode hook has always done, now factored into one shared helper so the two
cannot drift. Doing that for several nodes at once has two accepted transient
costs, both self-healing and both already inherent to the one-node case: a cleared
`loadedViewVersion` marks the node stale for the LOD freshness check, so a
substitutive-LOD group visibly drops to its coarsest ready level until the
settle-gated reload climbs back; and while `committedData` is absent the node is
skipped by the per-frame pass, so it misses that frame's cross-node `renderOrder`
assignment (a transient wrong back-to-front order across parts).

Every module-scoped write past an `await` inside the init closure is guarded by an
attempt EPOCH, bumped on dispose and whenever a retry supersedes an attempt. The
30 s deadline lives in that closure and nothing outside it can cancel the timer,
so without the epoch an orphaned attempt from a disposed app would fire 30 s later
and classify a deadline miss against the NEXT app's perfectly healthy worker:
'starved' with a retry armed, the resolved `initPromise` dropped, a third worker
spawned over the live one (leaking that thread and its transferred centers
buffers), and — since every node still reads as registered — a new worker holding
no registrations at all, i.e. the same silent death this issue is about through a
new door. The success path is guarded symmetrically. A stale attempt still
terminates its own worker; it just writes nothing and logs nothing.

The console message no longer claims more than it knows: that catch also fires for
a throwing lazy centers provider and for a `transfer()` of an already-detached
buffer, so it reports that the commit could not reach the SortWorker and that the
identity (unsorted) order is drawn, quoting the worker's actual init state rather
than asserting one. The degrade is inspectable rather than console-only:
`getDepthSortWorkerStatus()` reports `idle` / `ready` / `starved` / `failed` plus
the deadline-miss count, and is exposed on `__luxarDebug`.
