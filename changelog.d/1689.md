#### `luxar demo` reads as a catalogue instead of a wall of rows

Bare `luxar demo` printed one undifferentiated row per bundled demo, each
prefixed with arbol's `├` tree glyph, followed by four cramped lines of
commands. Nothing told you where to start, the rows would not copy-paste
cleanly, and the requirement column spelled a 29 GB download as `⬇30000MB`.

The listing is now grouped into labelled category sections, rendered through
`rich` so it carries colour and adapts to the terminal, and printed to plain
stdout so a row is exactly what you would type. Whether you already have a demo
moved into a one-character left rail — `✓` built, `•` inputs cached, blank for
neither — which both collects "what is on disk" into a single scannable stripe
and buys back the ten columns that were pushing rows past 80 and wrapping them.
Downloads are humanized (`29 GB`, `150 MB`), GPU and local-data requirements are
words rather than emoji (`GPU`, `GPU?`, `git-lfs`, `kaggle`, `manual`), and a
legend decodes both — naming the third rail state as `(blank)` rather than
inventing a dash the rows never print. The footer is six aligned lines that name
a concrete starter demo and keep the actionable half of every pair, so `--install`
still sits beside what `deps` reports and `cache clear` beside what `cache list`
measures. `luxar demo info`, `luxar demo deps`, and `luxar demo cache list` follow
the same visual key — one colour vocabulary throughout, and the same measured
section rule over `deps` and `cache list` (`info` describes a single demo, so it
is headed by that demo rather than by a rule) — so the sub-app reads as pages of
one document rather than four unrelated tables; `info` now reports build status
too, and `deps` colours its three-way ok / OUTDATED / MISSING verdict. A test
renders the whole bundled catalogue and fails if any line exceeds 80 display
columns, so a long new demo key cannot quietly wrap the table again.
