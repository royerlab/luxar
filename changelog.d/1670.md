#### Per-splat sidecars are written in the store's own splat order (#1670)

Two demos ship a per-splat payload as a separate `.npz` sidecar indexed
positionally against a cached `.gsplats.zarr` fit — the organ label per splat in
`demo_gsplats_3d_ct_totalsegmentator` (which drives the colors, the per-tissue
toggle layers *and* the hover tooltips) and the sampled RGB per splat in
`demo_gsplats_3d_visible_human_head`. Both sampled that payload at the in-memory
fit's centers *before* `GSplatData.save()`. But `save()` applies a spatial
ordering (`ordering="hilbert"` by default), so `GSplatData.load()` hands the
splats back under a different permutation: measured on a fresh 1606-splat fit,
1605 of 1606 rows move. `payload[i]` then describes some other splat entirely,
and nothing anywhere raises — the demo renders plausible nonsense.

Both demos now save the fit FIRST, reload it, and sample the payload at the
RELOADED centers, then return that reloaded fit alongside the sidecar. The pair
is aligned by construction under any writer ordering (hilbert, morton, none, or a
future LOD ladder), and the `--recompute` path now returns exactly what the
cached path will load on the next run — not only the sidecar's uint8
quantization but the `EncodingMode.MEMORY` fit itself, whose amplitudes are
stored as uint16 (median relative error 2.7e-4, p90 1.4%, max 7%) and whose
Cholesky factors are stored as uint8. Centers are unaffected (that mode leaves
them exact).

Alignment is also now CHECKED on load rather than assumed, by
`luxar.demos.voxel_sampled_payload_agreement`. Both payloads come from
nearest-voxel sampling, which gives an exact O(N log N) invariant: two splats
whose centers round to the same voxel must carry the same payload row. Correct
data scores exactly 1.000, and the 0.99 threshold is deliberately TIGHT rather
than generous: a full shuffle only falls to the payload's own chance level
`Σ p²` — which is payload-dependent (0.027 for the CT's 117 organ labels, ~0.001
for sampled RGB) — but the failures worth catching are NEAR MISSES, and those
land just under the gate. Measured on the CT pair: a different space-filling
curve (morton for hilbert) scores 0.898, a roll-by-one 0.955, an adjacent-pair
swap 0.978. Do not loosen it. A cached or shipped pair that fails (or whose
lengths disagree) is reported with the two file names and the measured
agreement, and the demo falls through to its existing download-and-refit path
instead of rendering it. Where a fit is too sparse for enough splats to share a
voxel the helper returns `None` and the pair is accepted — unverifiable is not a
failure.

`scripts/reencode_gsplat_demos.py` now REFUSES both sidecar-bearing datasets.
Its `--apply` path reorders a fit in place (`flatten` + `lod --recipe stream`)
and has never touched the `.npz` beside it, so running it was itself a way to
recreate this bug.

The invariant was measured against both shipped artifacts. The CT one happens to
be correctly aligned (agreement 1.000 over 660,934 splats — re-sampling the
rebuilt label volume at the stored centers reproduces `ct_atlas_labels.npz`
exactly). The Visible Human one is genuinely misaligned (0.00097 over 1,911,192
splats, against a shuffled baseline of 3e-05) and cannot be repaired by
re-sorting; that demo therefore refits on first run until the asset is
regenerated. Its `DEMO_META` and docs now say so: the default path really is a
~1.1 GB download plus a 4M-splat fit, so `download_mb` rises from 25 to 1100
(which puts it over `luxar demo run-all`'s 200 MB skip threshold — correctly).
Restore the 25 with the regenerated artifact.
