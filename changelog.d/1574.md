#### An explicit `None` render attr now means "absent" at the leaf adders too

#1496 settled the rule — a present-but-`None` key whose absent case has a working
default means *absent*, and the fix is to drop the key before anything looks at it
— on the three `**attrs`-forwarding gsplats doors, and deliberately left the leaf
adders alone as a wider change. Two render attrs were therefore still mishandled
one level down, inside `add_points` / `add_lines` / `add_mesh` / `add_gsplats`
themselves.

The silent one: `colormap=None` wrote `colormap='custom'`. `validate_render_attrs`
guards its colormap check on `is not None`, so the key passes, and
`compositing.sync_custom_colormap_attr` then rewrites the `None` to `'custom'` (a
`None` is not a str in `BUILTIN_COLORMAP_NAMES`) without writing any
`colormap_lut` beside it. The viewer's `build-scene-graph.ts` answers a
`'custom'` with no LUT by warning and falling back to **viridis** — so the
idiomatic `colormap=maybe_colormap` shipped a node rendered in viridis where
omitting the key gives gray, on all four geometry types and not just gsplats. The
quieter one: `coverage_fraction=None` persisted a literal `coverage_fraction:
null` LOD selector threshold into the node's zarr attrs.

Both are now dropped at the top of each leaf adder, above every consumer — the
colours gate, the entry attrs gate, each adder's `sync_custom_colormap_attr` call
sites (two per module, one in `gsplats.py`), and every structural branch — so no
route can see the raw `None`. Being above the structural branches is the part
that matters in practice: `add_points(partition={'max_elements': 150},
colormap=None)` used to stamp the LUT-less `'custom'` on *every part*, and a
partitioned scene is exactly the one nobody inspects node by node. The
rule lives in exactly one place: `compositing.strip_absent_attr_kwargs` with the
key set as a required argument, and the gsplats pipeline's wider
`ABSENT_WHEN_NONE_ATTRS` is now *derived* from the same
`ABSENT_WHEN_NONE_RENDER_ATTRS` tuple the leaves pass rather than restating it.
The set is a required argument on purpose: the pipeline door additionally reads a
`None` `labels` / `image_labels` / `partition` / `colors` / `truncation_radius` as
absent, and neither door should be able to inherit the other's set by accident.

This closes the asymmetry #1496 left behind and named: `add_gsplats_from_data(colormap=None)`
wrote `'gray'` while the `add_gsplats(colormap=None)` it delegates to wrote
`'custom'`. Both now write `'gray'`, asserted against each other and against an
omitted-key control read back from the store.

A Points/Lines `substitutive_lod=` ladder gains a second, visible fix from the
same line. The `None` never reached the coarse levels there — they are gsplat
*lift* targets and were written `'gray'` — so, measured, only the finest child
(the Points/Lines leaf itself) came out `'custom'`: an internally inconsistent
ladder, gray at every coarse level and viridis at the finest, i.e. a colour pop
at every LOD switch. Every level now agrees.

Every other render attr is still left refusing a `None` loudly, and the leaf set is
narrower than the pipeline's for exactly that reason: `opacity` / `gamma` /
`intensity` / `absorption` / `truncation_radius` answer "must be convertible to
float, got NoneType", `blending_mode` "must be a string", `layer` / `visible`
"must be a boolean". Reading those as "absent" would only mask typos, so a leaf
strip reusing the pipeline's set unchanged would have been a regression rather
than a fix.
