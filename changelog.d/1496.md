#### An explicit `None` in `add_gsplats_from_data`'s `**attrs` now means "absent"

Everything that is not a named parameter of `Group.add_gsplats_from_data` arrives
in `**attrs` and is forwarded verbatim to the children of whatever wrapper the
call produces, where `validate_render_attrs` rejects an unknown key **by name**
and never looks at its value. A present-but-`None` key was therefore not the same
thing as an absent one, even though most of these keys are named parameters of
the leaf `Group.add_gsplats` defaulting to `None` one level down. #1471 fixed that
for `labels` / `image_labels`; the rest of the family was still live, in three
different severities.

The loudest: `add_gsplats_from_data("g", data, lod_group=True,
additive_lod={"n_lods": 2}, partition=None)` — the idiomatic
`partition=maybe_partition` spelling, and the combination stock `gsplat lod
--recipe levels` output takes, its per-level stream ladders being on by default —
raised `Could not add gsplats 'child_0': Unknown node attribute 'partition'. Did
you mean 'absorption'?` **after** `add_gsplats_as_lod_group_impl` had already
created the wrapper, leaving `g` on disk as a childless `kind=lod` group that
survived `finalize()`: a scene the viewer loads and finds empty. The
route-dependence is what made it easy to miss — the same key was fine on
`lod_group=True` alone and on the bare flat route, and merely refused (nothing
written) on a flat ladder.

The merely-wrong: `colors=None` was refused on every route, as a raw `TypeError`
("got multiple values for keyword argument 'colors'") on the flat one and as the
misleading `Unknown node attribute 'colors'. Did you mean 'colormap'?` on the
other three. `truncation_radius=None` — a key this adder *injects* from
`result.truncation_radius` — suppressed that injection and then failed the
render-attr float conversion with `Truncation radius must be convertible to
float, got NoneType`.

The silent, and the worst of the three because nothing complained:
`colormap=None` was **accepted** and wrote a broken node. `validate_render_attrs`
guards its colormap check on `is not None`, so the `None` survives to
`compositing.sync_custom_colormap_attr`, which rewrites it to `'custom'` (a
`None` is not a str in `BUILTIN_COLORMAP_NAMES`) and writes no `colormap_lut`
beside it. Measured on uncoloured data: `colormap='custom'` where omitting the
key writes `colormap='gray'`. The viewer (`build-scene-graph.ts`) sees
`colormap === 'custom'`, cannot find the LUT, warns, and falls back to
**viridis** — so `colormap=maybe_colormap` silently rendered the node in viridis
instead of the intended gray. `demos/_interop_common.py` already hand-guards
`if colormap is not None:` before splatting into `add_gsplats_from_file`, which is
in-repo evidence that authors were working around this. `coverage_fraction=None`
was the same shape one attr over: a literal `coverage_fraction: null` selector
threshold on disk on the flat route, and on the multi-substitutive route the
`coverage_fraction must not be passed …` refusal for a caller who effectively
passed nothing.

The strip `strip_absent_label_kwargs` performed for the two label channels is now
`strip_absent_attr_kwargs` over `ABSENT_WHEN_NONE_ATTRS` — `labels`,
`image_labels`, `partition`, `colors`, `truncation_radius`, `colormap`,
`coverage_fraction` — and runs at the entry of `add_gsplats_from_data_impl`, of
`add_gsplats_from_file_impl`, and of `graft_gsplat_node`, above every route and
above every wrapper. A `None` for any of them is now indistinguishable from
omitting it, asserted against an omitted-key control store: the wrapper writes its
children, the data's own colours reach disk, the data's own truncation radius
applies (an explicit non-`None` radius is still a legitimate override and still
wins), the colormap is `'gray'`, and no null threshold is written. The set is
*derived* from `GATE_FORWARDED_LEAF_PARAMS`, the node-attrs gate's own exclusion
tuple, so the two cannot drift; it is deliberately wider, because the four keys
beyond that tuple must stay out of it — a non-`None` value of each still has to be
judged.

Every OTHER render attr is deliberately left refusing a `None`, because each
refuses loudly on its own and reading it as "absent" would only mask typos.
Measured, one call each: `opacity` / `gamma` / `intensity` / `absorption` answer
"must be convertible to float, got NoneType"; `blending_mode` "must be a string,
got NoneType"; `layer` / `visible` "must be a boolean, got NoneType" — their value
validators run unconditionally, unlike the colormap one. `scalars=None` refuses
too, for a different reason worth keeping straight: GSplats has no scalars channel
at all, so it is an `Unknown node attribute` regardless of value.

A `colors` key with a value, or a `centers` / `amplitudes` / `cholesky_factors`
key **at all**, is judged as what it actually is: a collision.
`add_gsplats_from_data_impl` passes all four positionally off the `GSplatData`
(`centers=result.centers`, `colors=result.colors`, …), and on a split route they
could not be sliced per child anyway — a coarser substitutive level holds merged
representatives and an additive rung holds a prefix, each with its own element
count, the same argument the `labels` refusal already makes. All four are now
refused at the entry of the adder, the file door and the graft door, before any
route is chosen and before anything is written, as a `ValueError` (the flat route
used to leak Python's raw `TypeError`, escaping a caller's `except ValueError`)
whose message names the collision and says where the value comes from, instead of
advising a switch to `colormap=` that would silently change what was asked for.
`colors` is asked first, then `centers`, `amplitudes`, `cholesky_factors`, so a
call passing several is answered deterministically.

Note the asymmetry, spelled out because it is easy to state wrongly: the refusal
tests for the KEY, not the value, so `amplitudes=None` and
`cholesky_factors=None` are refused too — those three are required positional
parameters of the leaf adder with no `None` default, so there is no "absent"
reading available for them, and `amplitudes=maybe_amps` is **not** a safe call
form. Only `colors` has one, because it alone has a `None` default at the leaf.

`centers` mattered most of the four: on the `from_data` routes nothing was ever
written for any of them, but at the graft door
`scene.add_gsplats_from_file("g", <nested partition store>, centers=…)` raised the
raw `TypeError` **and** left `g` behind as a childless `kind=partition` surviving
`finalize()`.

One verdict gets QUIETER rather than louder, and it is worth naming rather than
leaving to be discovered: `colors=None` used to raise (a `TypeError` on the flat
route, `Unknown node attribute 'colors'` on the others) and is now accepted and
ignored, with the `GSplatData`'s own colours reaching disk. That is the intended
reading of the rule, and it makes `colors` the one key in this family where
neither spelling does what a naive caller might expect — a `None` is silently
ignored, a value is refused. The refusal message for `colors` therefore says so
explicitly, since its own opening clause ("`colors` cannot be passed as a keyword
here") is not literally true of the one value it accepts.

Two precedence consequences, both deliberate and both now pinned with negative
controls. The collision refusal sits at the adder entry, so it outranks
everything below it — the `dim_order` spec validators, the rank guard, the
`coverage_fraction` refusal: a channel collision means the adder cannot build the
call it is about to make at all, so there is nothing below it worth reporting
first. And the pair runs once at the top of `add_gsplats_from_file_impl` rather
than being left to that method's two branches, because with it left to the
branches they disagreed: measured with a 4-column store into a 3-dimension scene
plus `colors=<arr>`, the matrix-shaped file answered the collision while the
partition file answered `Dimension mismatch for 'g': centers array has 4 columns
…` — one public method, one mistake, a verdict decided by a structural property of
the file. That is exactly what `from_io`'s own comment on the stored-column-count
check says must not happen.

While in there, the multi-substitutive `coverage_fraction must not be passed …`
refusal gained the `Could not add gsplats '<name>': ` prefix every sibling refusal
in that module applies by hand; it was the only one without it, so the same fault
was worded two ways depending on which check caught it.

Known residual, unchanged here: the leaf `Group.add_gsplats` door has the same
`colormap=None` → `'custom'` problem (measured directly). Only the
`add_gsplats_from_data` / `add_gsplats_from_file` / graft doors are fixed, since
those are the ones that forward `**attrs` through wrappers; fixing the leaf adder
means touching `add_gsplats_impl`'s own attrs handling, which is a wider change
than this one. Also unchanged: an invalid `partition` **spec value** still refuses
from inside `child_0` (the spec check lives one level below the gate), and a
right-length `labels` plus a decomposition kwarg on a grafted exempt leaf remains
the #1505-era residual it was.
