#### Harden the zipped-scene path with browser and zip64 coverage

The `.luxar.zarr.zip` reader had no positive-path browser test, for a structural reason: the E2E suite's data server is `python3 -m http.server`, which ignores `Range` and answers `200` with the whole body, so the zipped path could not run under it at all. Playwright now also boots the range-capable `tools/range-http-server.py` on port 9001 over the same document root, and a new `zip-archive-loading.spec.ts` uses the pair to pin both halves of the contract — an archive renders with the same point count as its own directory twin, and a host that ignores `Range` fails loudly with the remedy text instead of quietly presenting an empty scene.

The equivalence assertion is the point rather than a flourish: "the zip rendered something" is not evidence, since the zipped benchmark once reported a spectacular result that turned out to be a stale dev server timing an empty scene. `generate_test_data.py` gains the one scene packaged both ways that makes the comparison possible.

Archives past 65,535 members are now covered too, since only the zip64 end-of-central-directory record can describe them and a large scene crosses that boundary easily. The fixture is written by Python's `zipfile` rather than by the already-present `fflate`, which does not implement zip64 — at 70,000 members it emits a classic record whose count has wrapped modulo 65,536 to 4,464, so a test built on it would have validated the reader against a corrupt archive. A guard asserts the fixture really does carry a zip64 record, so the read assertions cannot silently degrade into exercising the classic path.

The viewer guide now documents producing, serving, and hosting a single-file scene, including the honest tradeoff: an archive is a modest cold-open loss and its case is distribution, not speed.
