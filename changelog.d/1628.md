#### A `.gsplats.zarr` archive whose store sits at its root is now a readable dataset

A "flat" archive holds the zarr store at the archive ROOT — `zarr.json` (or
`.zgroup`) and `centers/…` at depth 0 — which is what `zip -r x.gsplats.zarr.zip .`
from inside a store, or a zarr-native `ZipStore` write, produces.
`save_gsplats(..., compress=…)` never writes one, but they exist in the wild, and
until now only `luxar gsplat info`'s metadata peek handled the shape: it opens a
flat zip in place as a `ZipStore`, so it never had to resolve a store root at all.
Everything else did, and resolved it wrongly. `extract_compressed_zarr` defined
the store as a top-level DIRECTORY, so for a flat archive its "sole top-level
directory" fallback picked whichever child `iterdir()` yielded first — one of the
store's own arrays.

The two failures that cost real work: `luxar gsplat lod flat.gsplats.zarr.zip out/`
wrote `absorption 1.0, blending None, opacity 1.0` over a source that authored
`0.7 / volumetric / 0.5`, because the appearance peek refused a depth-0 attrs
document by design and `{}` is indistinguishable from "this dataset authored no
appearance"; and `luxar gsplat info` on a flat-zipped 4-part partition resolved to
one of the store's own child groups instead of its root, picked by `iterdir()`
order. Measured on this code that is exit 1 with `Invalid format_type: None`, and it
can be nothing else: every child a `gsplat partition` writes (`fitting`,
`part_0`…`part_3`) lacks that key, which only the store root carries. The issue was
filed with `Root kind: leaf` and a quarter of the splats at exit 0 — a line printed
only once the node load has SUCCEEDED, so that report came from a store shaped
differently from a `gsplat partition` output. Same root cause, and either answer is
wrong. `load_gsplats` / `load_gsplat_node` raised `ContainsArrayError: An array
already exists in store …/amplitudes`.

Store-root resolution now has three tiers instead of two: a top-level
`*.gsplats.zarr` directory, as `_compress_zarr` writes; then the archive root
itself when a zarr GROUP document sits at depth 0; then the first top-level
directory, whatever it is called. The order matters — the named directory keeps
winning even in the odd archive carrying both shapes, because that is what the
flat-zip classifier already decides and the two must not disagree. An extracted
flat tree is moved one level down under a store-shaped name, so the returned
path's parent stays a temp directory the caller may remove, which is the contract
every caller relies on. `.tar.gz` gets the shape for free, and for tar this is the
only possible route (zarr has no tar store).

One shape is reversed by that order, deliberately. An archive carrying a depth-0
group document *and* the real store one level down under a non-`*.gsplats.zarr`
name — `zip -r x.gsplats.zarr.zip .` run from inside a parent zarr group that
merely contains the store — used to fall through to the directory and load; it now
resolves to the wrapper and fails loudly with `Invalid format_type: None`. Nothing
in an archive distinguishes "a store whose root has one child group" from "a wrapper
around a store", and gating the flat tier on "the sole child is not itself a group"
would break the flat partition that is this issue's own repro. Re-archive the inner
directory on its own to read such a wrapper.

A zip's symlink members are now rejected the way a tar's already were.
`extractall` writes one out as a regular file holding the target path, which
escapes nothing — but it is a way to hand the extractor a depth-0 `.zgroup` that
the index-only resolvers skip, so a crafted archive could make the loader and the
appearance peek read different nodes.

The appearance peek grew the matching middle tier, gated on the same condition the
classifier uses: a depth-0 attrs document is the store's root only when a depth-0
GROUP document is there with it. A loose `.zattrs` with no `.zgroup` beside it is
still a stray and still loses to a real store one directory down. The sole-directory
tier is refused outright once the archive is flat, so a flat store that authored no
root attrs carries nothing rather than handing back `centers/.zattrs` as the
dataset's appearance.

`luxar gsplat view` and the tree branch of `luxar gsplat info` now resolve through
`resolve_store_path` — the same call the loader makes — rather than reaching for the
extractor directly. That matters most for `info`, which uses the loader purely as a
gate and then re-resolves: the two could previously disagree about which node an
archive holds, which is precisely how a partition came out as a leaf.

`luxar gsplat view` also leaked its own extraction, which this fixes on the way
past. Cleanup lived only in the `KeyboardInterrupt` and the generic `except`
arms, so a NORMAL return from the viewer — and the `typer.Exit` a failed
`pick_port` raises after the archive has already been extracted — left a full
uncompressed copy of the dataset behind in `/tmp/luxar_gsplat_*`. It is now
removed once, in a `finally`. The leak is pre-existing and never had anything to
do with the flat shape (a nested archive leaked exactly the same way); what makes
it worth fixing here is that `view` serves flat archives too now, so it reaches
the extractor on a wider set of inputs than before.

`flat_zip_in_place` stays, and the metadata inspector keeps opting in, but its
justification has changed: both routes work now, so the flag is about temp space
rather than capability. Reading a flat zip in place costs none, where extraction
costs the dataset's full uncompressed size — a poor trade for a call whose whole
purpose is a cheap metadata peek. Readers that touch array data still resolve to a
directory store.
