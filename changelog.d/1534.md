#### Mesh and GSplats now run the node-attrs gate at the adder entry too

`add_mesh(..., partition={...}, blending="max")` and `add_gsplats(..., partition={...},
blending="max")` raised the right message but still left a childless
`kind=partition` node on disk, and that node survived `finalize()` — the same
stranding #1529 fixed for Points/Lines, one geometry type over. Neither adder
validated the caller's node attrs before dispatching into its `partition=`
wrapper: the bad attr was only caught from inside the first synthesised part
(`part_0`), by which point `add_partition_group` had already created the
wrapper group.

Mesh's `substitutive_lod=` branch already ran the same validator
(`validate_render_attrs`, with the correct `MESH_RESERVED_ATTRS` set) before
this fix, so it never stranded anything — but it ran the check *after*
resolving its own `extend_to_all`, the opposite of the order Points/Lines
settled on in #1529. Mesh's `additive_lod=` reveal ladder had no attrs check
of its own at all: it fell straight through to the multi-LOD writer's
unreserved validator, matching the shape of the #1529 additive bug with BOTH
of its symptoms, not just the milder one. A genuinely mesh-reserved key that
is not also a generically-allowed one (`ordering=`) came back as an *unknown
attribute* instead of the correct *reserved* verdict — still refused, nothing
written. `position_bounds=` — reserved for mesh, but also a generically
allowed node attr — didn't raise at all: a real reveal ladder was written,
and the returned `Mesh` node's own construction then re-persisted the
caller's stale `position_bounds` value right back over the writer's own
correct stamp, breaking `finalize()` later with an unrelated `ValueError`
far from the actual cause — byte-for-byte the symptom this same changelog
entry's #1529 predecessor documented for Points/Lines.

Both adders now run `validate_render_attrs` once, on the un-split caller
attrs, at the top of the adder — above every structural branch (`partition=`
for both; `substitutive_lod=` and `additive_lod=` for Mesh too) and above
`extend_to_all` resolution, so nothing is written before it runs and every
split path refuses byte-identically to the flat one. GSplats' only structural
door on `add_gsplats` is `partition=`; its `lod_group=`/`additive_lod=` doors
live on the separate `add_gsplats_from_data` adder and carried the same
`lod_group=` stranding one level up (a bad attr was refused correctly, but
only from inside `child_0`, after `add_lod_group` had already created the
`kind=lod` wrapper) — now closed the same way, before that wrapper is built.
`additive_lod=` on that adder needed no change: its writer
(`write_gsplat_leaf_subtree`) already ran `validate_render_attrs` with the
correct `GSPLATS_RESERVED_ATTRS` before creating any group.

Unlike the four leaf adders, the `lod_group=` gate on `add_gsplats_from_data`
cannot hand its caller's `**attrs` to `validate_render_attrs` unfiltered:
`labels` / `image_labels` are named parameters of the LEAF `Group.add_gsplats`
but not of `add_gsplats_from_data_impl`, so on this one door they arrive inside
`**attrs` and need their own dedicated (and more informative) refusal instead
of being misreported as an unknown attribute — see #1471/#1504. `partition`
is excluded for the same reason and sits in the exact same position: a
leaf-only named parameter, forwarded structurally into each substitutive
child, where it drives that child's own BSP split. So
`add_gsplats_from_data(..., lod_group=<...>, partition={"max_elements": N})`
keeps working and still builds a partitioned child per level; the gate only
sees the keys that genuinely belong to it.

Some verdicts on this door genuinely change, and are called out here rather
than left implicit: a bad attr NAME/reserved-KEY collision on `lod_group=` now
refuses immediately, naming the caller's own node, before the `kind=lod`
wrapper is created — previously the same fault fired from inside `child_0`,
after the wrapper was already on disk (and it survived `finalize()`). And
because this gate's value validators (colormap, opacity, ...) now run on this
door too, a bad `colormap`/`opacity` VALUE outranks the dedicated
`labels`/`image_labels` refusal below it — matching the flat path's own
precedence between its attrs gate and its labels handling.

What this closes on that door is the stranding for every attr key OTHER than
the three excluded ones — `labels`/`image_labels` were closed earlier by #1471
and #1504, and a valid `partition=` never stranded in the first place. Two
neighbours stay open and are worth naming rather than implying away. A
present-but-conflicting `colors=` or `truncation_radius=None` in the same
`**attrs` is #1496 (the gate does improve `colors=None` from a raw `TypeError`
plus a stranded wrapper to a clean refusal that writes nothing, but #1496's
design question — what `colors=` should MEAN on a path that already forwards
the data's own colours — is untouched); #1496 has since answered it, see its
own entry. And an invalid partition SPEC, as
opposed to an unknown attr key — `partition="nonsense"`, `partition={"max_
elements": 0}` — is still refused only from inside `child_0`, leaving the
childless `kind=lod` wrapper on disk: the spec check lives in the leaf adder,
which is one level below this gate, so hoisting it is a separate change.
