#### A hand-placed demo input is no longer treated as a clearable cache

The Gaia Milky Way demo is the first whose *input* is a file the user puts under the
demo cache root by hand: the Gaia DR3 catalog is CC BY-NC, so it is not shipped,
and recovering a deleted copy means a ~90-minute ESA TAP re-query. Every piece of
tooling that walks `~/.cache/luxar/` assumed everything there was a
re-downloadable derivative, and neither possible `DEMO_META` state protected it —
with `"caches": []` the inventory called `milky_way_gaia_3m/` an *orphan* and
`luxar demo cache clear --orphans` deleted it, while declaring the name in
`caches` quieted the orphan report but then made `clear <key>` and `clear --all`
delete it as if it were a download.

There is now a third classification, `luxar.demos.registry.PROTECTED_INPUT_DIRS`,
in the spirit of the existing `NON_CACHE_DIRS` guard. Such a directory is still
inventoried — the bytes are real and the user should see them — but it is claimed
by definition, so `demo cache list` shows it as a `🔒 hand-placed input` rather
than an orphan, and `demo cache clear` refuses it on all three routes (by key,
`--all`, `--orphans`), printing one keep notice per directory in `--dry-run` and
in a real run alike. Everything else in the same selection still clears normally.
`make clean-cache` was the fourth and most casual route — a bare `rm -rf
~/.cache/luxar`, also reached by `make clean-all` — and now clears the cache root
while sparing the same names; because a clean target has to work with a broken
environment, the recipe spells the names out and a unit test pins that copy
against the constant. The set is deliberately independent of `DEMO_META`, so no
later edit to a demo file can quietly disarm the guard; another drift test pins it
against the demo's own `CACHE_FILE`.

`scripts/gallery/generate_gallery_datasets.py` was the other half of the problem:
a demo whose input the demo itself cannot fetch (`local_data` of `manual-file` or
`kaggle-auth`) exits 1 wherever that input is absent, which the harness reported
as a hard `failed`, returning 1 and aborting `make generate-gallery` on any fresh
clone — five manifest entries need a hand-placed file and two need Kaggle
credentials. Those entries are now **demoted on failure** rather than skipped up
front: they are run like any other, so a machine that has the input regenerates
its tile on every route (`--force` included), and only a NON-ZERO EXIT is
reclassified into the soft `manual-data` bucket. The honest cost is that a genuine
bug inside one of those seven demos is now reported in that soft bucket instead of
returning 1; its error tail is still printed. A `timeout` or a `no-output` (exit 0
having written nothing) stays a hard failure, which leaves one case unrescued and
worth stating plainly: `arxiv_papers_kaggle` needs no credentials to begin and
declares a ~30 GB download, so on a cold machine it can exhaust the per-demo
timeout and return 1 anyway — as it already did before this change. Capping that
with a download-budget skip is deliberately not done, since it would stop
regenerating the tile on a machine whose cache is warm. The declared mode is read
by AST through `registry.extract_demo_meta`, never by importing the demo, and the
`luxar` import is deferred so `--help` and `--list` keep working on a partial
environment.
