#### Grafting a partition beside an `additive_lod=` ladder no longer strands a childless wrapper

`scene.add_gsplats_from_file("g", <unladdered nested .gsplats.zarr>,
partition={"max_elements": 4}, additive_lod={"n_lods": 2})` answered `Could not
add gsplats 'part_0': partition= is not supported alongside an additive_lod=
ladder …` and left `g` on disk as a childless `kind=partition` that survived
`finalize()` — the last strand of this family left open by #1550.

`partition=` and a multi-rung ladder are mutually exclusive (the multi-LOD
writer has no `partition` parameter), and the data door already judges that
correctly, because it reads the resolved `GSplatData`. The file/graft door read
the ladder off the STORE instead, and `additive_lod=` is not a parameter of
`graft_gsplat_node` at all — it rides in `**attrs` down to each part's own
`add_gsplats_from_data_impl`, which BUILDS the ladder there, one level below the
wrapper the graft has already written. So the conflict surfaced after the damage.

The gate now asks one question per leaf: would a ladder still be there once the
kwarg is applied? Checking the kwarg's mere PRESENCE would be wrong — `{"n_lods":
1}` resolves to a single rung and partitions perfectly well, while `{"method":
"radial"}` carries no `n_lods` to read and takes the `n_lods=4` default, four
rungs on any leaf of at least 4 splats — so the answer comes from a new
`gsplats.lod.additive.additive_rung_count(n, n_lods, breakpoints)`, pure
arithmetic over the SAME cut resolver `make_additive_lod` uses. Sharing that
resolver is what makes equal-count, `stream:<c>` and explicit counts exact:
they are counted off the very cuts the build would consume, never re-derived.
(The query also mirrors the build loop's `if end <= prev: continue`
de-duplication, but as a mirror against a future cut resolver that emits a
duplicate — the resolver returns strictly-increasing positive cuts on every
non-energy path today, so the branch is unreachable in both loops.) Parity with
the builder itself is pinned per breakpoint kind. A new
`core.group.lod.gsplats.resolve_additive_rungs` applies the `additive_lod=`
vocabulary to one leaf on top of it, mirroring `resolve_additive_axis_gsplats`
key for key — the two are one contract stated twice, down to judging an explicit
`counts:` list in the resolver's own order: strict `validate_counts_breakpoints`
first and `clamp_counts_breakpoints` only after, because a single grafted leaf IS
the `substitutive_levels[0]` that validator measures against and the clamp is
there for the coarser levels of a pyramid. Clamping first answered a confident
wrong count exactly where the resolver raises — `{"recompute": True,
"breakpoints": [100]}` on a laddered 12-splat leaf clamped to `[12]`, counted one
rung, and stranded the wrapper anyway.

That closes the mirror-image half too. A laddered store plus
`additive_lod={"n_lods": 1, "recompute": True}` collapses to a single rung, takes
the flat route and splits fine, but the store-only test refused it; only the
`additive_lod=False` spelling had been skipped by hand.

Which remedy the refusal names is now decided per call, by the OFFENDING leaf's
store alone. If that leaf's store carries a ladder the message is unchanged — it
names the store and points at `gsplat flatten` — which is also the right answer
when the call ALSO rebuilds that ladder, since a stored ladder is the obstacle
that survives dropping the kwarg and "drop one of the two" would only buy a
second refusal. When the ladder exists only because `additive_lod=` builds it,
the refusal names `additive_lod=` and says to drop one of the two. "Offending",
not "anywhere in the tree": on a mixed store where the kwarg collapses the
laddered leaf and ladders the flat one, the blocking leaf is the flat one, so the
message names `additive_lod=` while a stored ladder sits untouched next door —
correctly, since `gsplat flatten` would rewrite a ladder that is not in the way.

The reason BODY of the kwarg-built refusal is byte-identical to what the data
door says for the same call one step later (they share
`partition_beside_a_ladder_reason`). The whole message matches on the
matrix-shaped branch; on the graft branch it deliberately names `'g'` where the
data door would have named `part_0`, which is the whole point. And even the body
matches only for a call whose only fault is this conflict. The gate runs
above the data door's `lod_group=` resolution, so
`add_gsplats_from_file(..., lod_group="bogus", partition={…}, additive_lod={"n_lods": 2})`
answers the conflict where `add_gsplats_from_data` with the same effective
arguments answers `TypeError: lod_group must be …`. Both refuse and write
nothing, so the divergence is in naming only.

An unknown count falls back to the store. An energy-fraction `breakpoints` list
cannot be counted without the ordering and the energy curve — the expensive half
the query exists to avoid — and neither can a malformed or junk spec, but `None`
there is a statement about the KWARG, not about the store: the store's own ladder
still stands, and refusing on it is exactly what the pre-#1632 gate did. Skipping
the leaf instead re-stranded the very wrapper this change closes. The cost is one
over-refusal in the conservative direction, `{"recompute": True, "breakpoints":
[1.0]}` on a laddered store, which pre-#1632 also refused.

That fallback leaves two residuals open on an UNLADDERED store, and they are
different kinds. First, an INVALID call: `additive_lod=True` there is one rung,
skips the gate, and still fails from inside `part_0` with "additive_lod=True
requires every substitutive level to already carry an additive ladder", and a
malformed spec does the same with its own message. Both strand identically
without `partition=` at all, so the fault is the call's and the report is the
builder's — "a query must not pre-empt the builder's own fault report", preserved
where it belongs. Second, and genuinely still open, a VALID energy-fraction spec:
`partition={"max_elements": 4}, additive_lod={"breakpoints": [0.5, 1.0]}` on an
unladdered store counts UNKNOWN, falls back to a stored one rung, skips — and
then hits this very conflict refusal from inside `part_0`, one level too late,
leaving `g` childless. Nothing is malformed there; the builder really does make
two rungs from that spec, and the count is unknowable only because energy cuts
need the ordering and the energy curve. Refusing on UNKNOWN instead was rejected
deliberately: `{"breakpoints": [1.0]}` resolves to a single rung and partitions
fine, so a gate refusing every uncountable spec would refuse what the flat path
accepts — its own regression. One further trade, in the other
direction: a fault the count cannot see (a bad `method`, a stray
`substitutive_level` key) is now masked by this refusal rather than reported by
the builder — acceptable, the conflict being the more fundamental fault and
nothing being written either way.
