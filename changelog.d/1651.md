#### A bare `page.evaluate` in an E2E test can no longer eat the whole test budget

`page.evaluate` carries no timeout of its own — neither `actionTimeout` nor
`setDefaultTimeout` reaches it — so an evaluate the page never answers can only
be stopped by the whole Playwright test budget. On a software-rendering Linux
workstation that is not hypothetical: a run of `webgl-errors.spec.ts` sat for the
entire per-test budget inside the console-buffer probe in
`getConsoleMessages`, which at the time the shared fixture's
`assertNoConsoleErrors` teardown ran for every spec that imports `test` from
`./fixtures` (59 of the 67; the other 8 import `@playwright/test` directly and
get no fixture teardown). That fixture call is gone (#1760); the call sites the
bound now protects are the specs that gate on the in-page buffer from their own
`test.afterEach`, which get the same After-Hooks slot, plus the mid-test callers,
which share the test body's budget. Playwright reported it as
`Tearing down "page" exceeded the test timeout` pending
on that one line. The issue report saw the same wedge burn the two-minute budget
its own run allowed, and noted there that the page stayed alive throughout — the
viewer's own adaptive-DPR probe kept logging — it simply never got around to
running the injected function.

Instrumenting that wedge on the sharpness-showcase scene answers the other half
of the issue, which asked why it happens at all. On an otherwise idle box a
trivial `page.evaluate(() => 'ok')` went unanswered for its 5 s deadline twelve
times in a row, about 78 s of wall clock, while the page kept rendering. The
rendering evidence comes from two counter samples 28.0 s apart (t = 7315 ms and
t = 35338 ms) — a window _inside_ that stall, not a measurement across the whole
of it: over those 28 s `requestAnimationFrame` ticked 123 times and the
renderer's own `info.render.frame` counter advanced 246, i.e. ~4.4 rAF/s and
almost exactly the two `renderer.render()` calls per animation frame the default
two-pass pipeline issues. `visibilityState` stayed `visible` and the WebGL
context was never lost. An in-page `setInterval(…, 1000)` sampler over the same
28 s window fired twice.

So this is main-thread task starvation, not a stuck GL command buffer and not one
unlucky probe: a saturated software-rendering rAF loop schedules frames back to
back at ~230 ms apiece and the lower-priority task sources — in-page timers and
Playwright's `Runtime.callFunctionOn` round trip — starve for tens of seconds
while rendering continues. Whether that is task-source priority alone or sheer
queue depth is not settled here, and the arithmetic points at depth: under pure
priority the event loop still runs one task per turn, so at ~4.4 rendering
turns/s a `setInterval(…, 1000)` should still fire about once a second, and two
fires in 28 s is ~14x slower than that. That fits a deep backlog of
already-queued work better than priority does. The `OPFS timeout: set(...)
exceeded 10000ms` warnings arrive in the same window, and a flooded OPFS write
queue is a canonical producer of exactly such a backlog — which that single
instrumented run could not tell apart from a symptom, but a before-and-after can.

It largely was the cause, and saying so plainly is what keeps this change from
claiming more than it does. With #1647 — the OPFS circuit breaker and `?noOpfs`
kill switch, now on dev — merged in, the whole spec passed 10 of 10 in 58.8 s,
with two `OPFS timeout` lines in the run. Current dev _without_ this change fails
3 and passes 7, twice in a row, with 10 to 12 of those lines: one run's three
failures are the unbounded-evaluate signature (`page.evaluate: Test ended` after
the budget, plus `page.waitForFunction: Test timeout of 60000ms exceeded`), the
other's are a `Target page, context or browser has been closed` cascade. At the
pre-#1647 dev the same file failed 4 of 10 in 2.1 min with 9 such lines, and four
runs of this branch on that base failed 5, 5, 2 and 4 — the pass count varies run
to run on this box and the wedge moves from one test to another, so no single run
is a measurement. The OPFS write path is where this file's failures largely came
from, and #1647 is what removes most of them. What the bounds added here
contribute is narrower and orthogonal: when the page does starve, the failure now
arrives in seconds and names the probe that went unanswered, instead of consuming
the whole budget and then reporting nothing about where it went. This change is
not claimed to fix the spec's failures.

Three things follow for the tests. Bounding the evaluates is the right test-side
fix, since nothing the test does can make the page's own render loop yield. The
deadlines have to be generous, because the stall is environmental and outlasts
any bound that still fits inside a per-test budget — which also means any bound
can cut short a stall that would have ended, so the bound is a trade rather than
a free win. And zero observed render ticks is not by itself a failure: the
counter demonstrably advances during the stall, so what is starved is the
observation, and the only version of that worth a red test is a page that answers
promptly and a renderer that still is not drawing.

`getConsoleMessages` and the three bare evaluates in `webgl-errors.spec.ts` are
now bounded by the same `raceEvaluate` helper #1640 introduced for the
render-pacing waits: a race between the already-started evaluation and an
explicit deadline, resolving with a sentinel the in-page function can never
return so the call site can tell a real answer from a missed one. What a missed deadline _means_ is decided per call site.
`getConsoleMessages` throws after 45 s saying the page never answered the probe
and that the console-error check therefore could not run — deliberately not empty
buckets, which would have turned that gate into a vacuous pass for every spec
that calls it. 45 s rather than the whole budget because Playwright gives the
After Hooks phase a _fresh_ timeout slot equal to the per-test timeout (the
config's 60 s, or more in a file that raises its own), so an `afterEach` gate
always has that full slot no matter how much the body used: 45 s lands inside it, which is what makes the failure attributable to this
probe by name, while still leaving a wide margin for a page that recovers late. The
same default bounds the mid-test call sites, where the probe shares the body's
budget instead. The two detectors in the spec (the `gl.getError()` drain and the
geometry-buffer traversal) keep a 15 s bound and throw likewise, naming what went
unverified — their answers are what the tests assert on, so cutting them short
buys nothing — as does a page that answers but exposes no numeric frame counter
at all, since there is then nothing to confirm a render tick against. An
_unanswered_ counter probe is the starvation case instead, and is reported rather
than thrown. The per-tick kick is the one deliberately best-effort part: it is
counted, not asserted.

The same spec also stopped asking the render-pacing helper for frames it does not
guarantee. `waitForNextRender` is documented as best-effort and its fallback is
silent, so a detector could not tell a confirmed flush from a fallback, and a GL
error that only appears on the tenth draw might never get logged. A new
`tests/e2e/render-ticks.ts` module now kicks and confirms each tick in turn
against the renderer's own counter, with a 3 s per-tick bound _and_ a 10 s
aggregate budget for the whole flush — the per-tick bound alone was paid twice per
iteration and up to `ticks` times, so a ten-tick flush could have spent a whole
60 s per-test budget and reproduced the very timeout being fixed. Each wait is
clamped to whatever is left of the budget, and the report says when the budget is
what ended the loop — including the case where the wait that timed out was one the
remaining budget had clamped, which otherwise reports as an ordinary per-tick miss
and never mentions the budget at all. The aggregate bound is per CALL, so the one
test that loops over all five datasets in a single body passes a smaller one; the
comment there does the arithmetic and admits what it cannot fix, since five scene
loads in one test can exhaust that test's budget whatever the flush is bounded to.
A tick count that is not a positive integer is rejected outright instead of
producing a phantom zero-tick flush on a healthy page. The counter is
`info.render.frame`, which counts `renderer.render()` calls — about two per
animation frame with the default WebGL pipeline — and it is the same counter the
previous helper watched, so the numbers the detectors ask for are unchanged; only
the confirmation is new. (`WebGPURenderer` has no `info.render.frame`, so there
the probe falls to `info.frame`, which THREE advances from its own animation loop
whether or not anything was drawn; a confirmed tick is weaker on that backend, and
the module says so rather than pretending otherwise.) Living in its own module
rather than at the foot of the spec is what makes all of this unit-testable
against a fake page — `src/tests/unit/tests/e2e-render-ticks.test.ts` covers the
counting loop, the targets, the budget (both the clamped-wait case and the
per-tick miss that must _not_ blame it), the error re-throw rule and every verdict
branch, and executes the two injected in-page closures for real against a stubbed
`window` so that the baseline probe's wrapped answer and the `>= target` predicate
are not merely assumed.

A _partial_ flush is reported rather than failed (a strict version is reported in
#1652 to turn the healthy case red on a box rendering at the ~4.4 rAF/s measured
above) and the assertions still run
against whatever landed. A flush that confirmed nothing at all gets a verdict,
taken after the detector's own dump and assertion so a real GL error stays the
error you see, and taken from evidence rather than from the tick count: one
bounded probe re-reads the counter, the context-lost flag and
`document.visibilityState` in a single round trip, and the run only goes red when
the page answered that probe, the context is not reported lost, the flush had a
baseline, the counter still reads exactly that baseline, the page reports itself
`visible`, _and_ at least one kick was actually answered. That last condition
matters because the animation loop
auto-pauses after ~2 s of idleness: with no answered kick, nothing is confirmed to
have asked the renderer to draw and a frozen counter needs no renderer defect to
explain it. Everything else is a single warning naming which case it was — the
observation channel starved, so nothing can be said either way and the detector's
`page.on('console')` capture was unaffected regardless; or the counter did
advance, so only the per-tick confirmation was starved; or the counter came back
_below_ the baseline, which a monotonic counter cannot do and which means the
renderer was re-created, leaving nothing comparable; or the page is not visible, so
it is getting no animation-frame callbacks at all; or no kick was answered; or the
WebGL context reports itself lost, which `fixtures.ts` already allow-lists
as environmental and which freezes the counter by construction, THREE skipping
`renderer.render()` entirely while the context is gone. Where no WebGL context can
be read at all — `canvas.getContext('webgl2')` returns `null` on a canvas already
in `webgpu` context mode — the message says context loss is _unknown_ rather than
claiming it is false.
