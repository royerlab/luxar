#### One place decides a LOD ladder's thresholds and the selector that describes them

A `kind=lod` group writes two things that are really one decision: the per-child
`coverage_fraction` thresholds, and the group-level `selector` naming the units
those thresholds are in — the legacy diagonal metric (`"coverage"`, bounded by
`MAX_COVERAGE_FRACTION` = 4.0) or literal screen-area fractions
(`"screen-area"`, anchored at half the screen for a whole object and
fills-screen for a partition tile). Pair them wrongly and nothing raises, because
both spellings are individually valid; every switch point the viewer computes is
simply on the wrong scale.

The rule that picks between them — an explicit `coverage_fractions=[...]` list
keeps the legacy units it was authored in, anything derived is stamped
screen-area — was written out four times (the `add_points` / `add_lines` /
`add_mesh` `substitutive_lod=` wrappers and the `add_gsplats_from_data`
`lod_group=` dispatch) and enforced nowhere. Those four now share one decision,
`lod.group.resolve_lod_ladder`, which returns the selector alongside the
thresholds it describes so a producer has no occasion to name a selector at all;
the previously-dead `DERIVED_LOD_SELECTOR` constant and its new
`LEGACY_LOD_SELECTOR` sibling are what it returns, and the `add_lod_group`
default now reads from the latter instead of repeating the literal. Each call
site keeps its own user-facing length-mismatch message, so no error text moved.

The refactor is behaviour-preserving: all four adders were already pairing
correctly, so nothing a user sees changes. The detached-tree paths are
deliberately untouched and still separate, because they answer a different
question — not "did the caller supply a list?" but "what does a *stored* tree
already claim about its own thresholds?" That one lives in
`gsplats.tree.gate_authored_selector`, shared by
`io/_compiler/gsplat_tree.write_gsplat_node` and
`gsplats_pipeline/from_io.graft_gsplat_node` (the `add_gsplats_from_file` graft
path, which derives its thresholds directly and takes its selector from that
gate).

A new cross-geometry suite pins the rule from both sides for all four adders —
derived ladders stamp screen-area (neither mesh nor gsplats had ever been
asserted), explicit ones stamp legacy (nothing asserted that anywhere) — plus the
consistency invariant that a stamped selector must agree with its own stamped
thresholds, an AST guard that no ladder producer spells a selector out for itself
again, and a discovery guard that a *fifth* `add_lod_group` producer has to be
either routed or explicitly exempted. The suite is a regression fence, not a
detector: it constrains what the library writes from here on and says nothing
about the 209 already-shipped ladders that carry `selector="coverage"` over
derived-looking thresholds (issue #1727) — auditing or migrating those is
separate work.
