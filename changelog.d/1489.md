#### An unwritable colour dtype no longer strands a partial node

A `colors` array whose dtype the writer cannot store was refused by the encoder,
not by the pre-write validator sweep — so the refusal landed mid-write, after
part of the node was already on disk. `np.array([[255, 0, 0]])` is `int64` on
Linux, which makes this the easy mistake to make. Measured residue, each of it
surviving `finalize()`: a flat write left the node holding its geometry arrays
and nothing else (`positions` for Points; `vertices`/`segments`/`widths` for
Lines; `centers`/`amplitudes`/`cholesky_*` for GSplats; `vertices`/`faces` for
Mesh); a `partition=` that really split left a `kind=partition` wrapper holding a
partial `part_0`; `additive_lod=` left an `additive_0` child (measured for
Points and for Lines); a Mesh
`substitutive_lod=` left a `kind=lod` group holding a partial `child_0`; and the
GSplats substitutive door, `add_gsplats_from_data(..., lod_group=…)`, left a
`kind=lod` group holding a partial `child_0` — or, when only the finest level's
colours were bad, a COMPLETE `child_0` beside a partial `child_1`, a half-written
ladder. Only Points and Lines under `substitutive_lod=` were clean, because the
gsplat lift carries its own copy of the rule.

`validate_colors_for_writing` now enforces the dtype rule itself, through a new
`validate_color_dtype` helper: a COLOR array must be floating point (any width)
or integer `uint8`/`uint16`. That validator is what every geometry type's
pre-split gate runs against the SOURCE arrays before a `partition=` /
`additive_lod=` / `substitutive_lod=` decomposition, and the gsplats
`lod_group=` gate now walks every rung of every substitutive level with the same
validator before its wrapper group is created. Measured across the 17 doors that
exist — Points and Lines flat / `partition=` / `additive_lod=` /
`substitutive_lod=`, GSplats flat / `partition=`, Mesh flat / `partition=` /
`substitutive_lod=`, and `add_gsplats_from_data` flat / `additive_lod=` /
`partition=` / `lod_group=` — an unwritable colour now leaves the store
completely untouched, and the wrapped path reports the same COLOURS verdict as
the flat one, byte for byte. (Only the colours verdict: a call that also trips a
Cholesky fault still reports colours under a wrapper where the flat path reports
Cholesky, which is the pre-existing pre-split-gate precedence asymmetry the
`labels` gate already has.) The rule is
also spelled as a whitelist rather than an integer special case, which closes the
same stranding for a `complex` array: complex is numeric enough to pass the
finiteness check, so it used to reach the per-channel encoder and die there with
`color_mode required for float COLOR arrays`, positions already written.

The check runs last inside `validate_colors_for_writing`, matching the
precedence of the encoder rule it mirrors: a negative integer array still
reports negativity, and an empty array still passes through with no dtype
opinion at all (the encoder writes empties ahead of its own validation). Two
things that used to write now do not, both deliberately: a `complex` colour
array whose values happen to be uniform used to reach the broadcast encoding and
land on disk as a `complex64` zarr array the viewer cannot decode, and the
standalone `.gsplats.zarr` writer inherits the same refusal. Everything else is
untouched — floating point colours of any width including `longdouble` (still
accepted, still quantized to uint8 by AUTO), `uint8`/`uint16`, a uniform RGB(A)
list or tuple (which takes the broadcast door, becomes float32 and never meets
the rule), and a bool array, which keeps its existing non-numeric refusal.
