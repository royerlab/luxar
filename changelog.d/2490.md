#### GSplats `array_ref` resolution is now covered by a test, and #2490's diagnosis retracted

Issue #2490 reported that the viewer does not resolve `array_ref` for gsplat
`centers`, on the strength of a hosted render A/B in which the DESI
`By redshift` layer settled at 348,558 elements against the published store's
7,116,524 — a 243x gap that appeared exactly when the re-laddered scene started
deduplicating its coarse-level `centers` across the two layers.

It resolves them. A controlled A/B settles it: two locally-served stores built
from the same 2M points, the same LOD recipe and the same colours, differing
only in which layer was written first — and therefore only in which layer's
`centers` are `array_ref`s. Toggling the layer produced identical totals
(66,438 -> 70,438 in both arms), identical per-node draw counts
(`child_0` 31,219, `child_1` 4,000 in both) and identical request counts
(1,239 ok / 9 failed in both). The hosted gap is a measurement artefact: on that
scene `totalElements` swings 320k <-> 6.2M *within a single run* in both stores
as the 512 MiB refinement residency ceiling and the GPU buffer pool trade
nodes, and the regenerated leg logged 7x the aborted requests. Two 9.75M-point
layers do not fit that budget; which nodes win the race is not deterministic.

What was true is the coverage gap the issue identified. The suite covered
`array_ref` through `ArrayDecoder.decode` (whole-array, Points `colors`,
direct target) and not at all through the gsplats RANGE path
(`loadArrayRanges` -> `loadRangesResolvingRef` -> `resolveArrayRef` ->
`loadPerChannel`), where the target is per-channel quantized. So a `(0, 3)`
ref resolved against the wrong metadata could decode corrupt values without an
error, and no test would have caught it. A new fixture and test close that: the
deduplicated layer must decode centers and amplitudes bit-identically to the
layer that owns them, non-vacuously, with the store's own `array_ref` encoding
asserted so the test cannot quietly stop covering refs.
