#### A hidden gsplat dimension no longer fetches chunks that cannot render (#1183)

`computeTolerance('gsplats', …)` gave a hidden CONTINUOUS dimension a query
tolerance of `step × 3.0`, and every doc that described it — the module header,
both loader READMEs, `MESH_NODE_SPEC.md` — called it "3 σ". It was neither: the
number multiplied the dimension's _navigation step_ and had nothing to do with the
splat covariance or the node's `truncation_radius`.

The reach it added was also unreachable by design. `compute_chunk_bounds_gsplats`
already expands each continuous dimension of a chunk's AABB by
`sqrt(covariance[d, d]) × coverage_sigma`, hidden dimensions included, with
`coverage_sigma` set to the node's own `truncation_radius` — and the read side's
cutoff is that same radius. Which code enforces it matters, and the first version of
these docs named the wrong one: for a hidden dimension it is the CPU/WASM projection
kernel's shifted-Gaussian attenuation, `(e^{-m²/2} − c)/(1 − c)` clamped at 0 in
`project_gsplats_nd_to_3d`, exactly 0 at `m = truncation_radius`. The shader's
`uTruncate`/`uTruncateSq` discard is the DISPLAYED-dimension counterpart and never
sees a hidden dimension. So a chunk that fails a zero-tolerance intersection test
holds _only_ splats the projection attenuates to nothing: widening the query could
never make a visible splat appear, only download chunks that render nothing. (For
gsplats this array is a chunk-FETCH reach and nothing else; per-splat hidden-dim
visibility comes from that projection math, which does not read it.)

The continuous arm is now a float-safety epsilon, `max(1e-3 × step, 2.75e-5)`, with
one term per reason it cannot be a literal `0`:

- `1e-3 × step` — a continuous dimension along which the splats have ZERO variance
  (a stacked axis declared continuous rather than discrete) gets no σ expansion,
  and the write side epsilon-pads _discrete_ dims only, so its stored bound is the
  axis value itself. The dominant perturbation is that the bound is stored as
  **float32** (`chunk_bounds` is `dtype=np.float32`) while the query position is a
  float64 — ≈1.9e-7 of disagreement at a coordinate of 5.3; the `start + k × step`
  arithmetic drift is real but secondary (≈9e-16 there). At tolerance `0` membership
  would degenerate to an exact float comparison and could silently select nothing.
  At a unit step this is exactly the write side's `_BARRIER_BOUND_EPS = 1e-3`, whose
  reader-side mirror it is — pinned from the Python side by a test that parses the
  TypeScript declaration, so the two cannot desync silently.
- `2.75e-5` — the read side does not use a raw zero variance either.
  `computeMarginalCholesky` REGULARIZES a degenerate pivot, floored at
  `sqrt(CHOLESKY_EPSILON) = 1e-5` for an all-zero hidden block, so such a splat
  still renders out to `truncation_radius × 1e-5`. Term 1 alone falls below that for
  any `step < 2.75e-2` — a 10 ms-frame axis at `step = 0.01` gave a 1e-5 fetch
  window against a 2.75e-5 render band, dropping splats the kernel renders at up to
  ~60% of full brightness (the attenuation one σ out).

That band is ABSOLUTE, in the dimension's own units, because the floor behind it is
an absolute variance floor rather than a step-relative one. It therefore spans many
CELLS on a micro-step axis — ≈27.5 at `step = 1e-6` — and a cap at a fraction of a
cell, which an earlier cut of this change carried, is the wrong answer: a
`0.25 × step` ceiling gives 2.5e-7 at `step = 1e-6` while the renderer shows content
out to 2.75e-5, so a splat ten navigation steps away renders at ~60% brightness with
its chunk never fetched — narrower than the `step × 3` rule this replaces. The
quarter-cell rationale belongs to the DISCRETE arm, where over-reach bleeds a
neighbouring CATEGORY; a continuous axis has none, so window width there is a
bandwidth question (and mesh already gets a FULL cell for a continuous hidden dim).
What holds at every step is the property that matters: the epsilon is never smaller
than the band a degenerate axis can render in, so the query cannot miss renderable
content. That bounds the DISTANCE and not the fraction of a node fetched: where the
dimension's real σ is micro-scale as well (`step = σ = 1e-9`, a metre-declared axis
carrying nanometre structure) the window the data needs is `T · σ = 2.75e-9`, so the
epsilon over-fetches by ~1e4 and can pull the whole node — the one regime in which
this is worse than the `step × 3` it replaces. Narrow _and_ complete needs a
scale-aware regularization floor in the kernel, or the splats' actual per-dimension
σ plumbed into the query — not a different constant.

Three limits are documented rather than papered over, all of them "the axis is
mis-declared": coordinates far from the origin (an expansion below half a float32
ULP rounds away entirely, so with `T = 2.75` _any_ `σ_d ≲ (1.1–2.2)e-8 × |coord|`
behaves like zero variance); a degenerate dimension beside another hidden dimension
of very large σ, where the regularizer's floor is RELATIVE (`σ_max × 1e-6`) and the
rendered band `T × σ_max × 1e-6` exceeds the epsilon once
`σ_max > max(1e-3 × step / (T × 1e-6), 10)` — `≈363.6 × step` or the absolute 10,
the two branches agreeing exactly at the crossover; and a node stamping a
`truncation_radius` well above
the default, which scales the band linearly while this call site — handed only a
`DimensionInfo` — must use the default.

The "bounds already carry the extent" premise is stated with its PRECONDITION:
`compute_chunk_bounds_gsplats` expands the dims NOT in its `slice_dims` argument and
gives the ones that ARE only the tight barrier pad, so it holds while the write
side's barrier set equals the set the reader treats as `discrete`. It does for a
scene that declares its dimensions (`geometry_writers/gsplats.py` uses
`discrete and not display`); with `scene_dimensions` absent the writer falls back to
the value-based `detect_barrier_dims`, whose own docstring calls a false positive a
correctness bug. That disagreement predates this change, but the old rule MASKED it
— a bare `3.0` covered a mis-detected barrier dim's tight bounds, and `1e-3 × step`
does not. The robust fix is plumbing: the writer already publishes the set it used
as the ordering `slice_dims` attr and the tolerance computer does not read it.

The cross-language constant the band derives from now lives in the viewer's
mirrored-constant home, `config/constants.ts`, beside
`GSPLAT_DEFAULT_TRUNCATION_RADIUS`, and the TypeScript reference kernel now IMPORTS
it rather than keeping a third copy — so only `wasm/rust/src/common.rs`, the backend
that actually runs, still owns an independent literal, named in a `MIRROR:` comment
and pinned by a test that parses that one declaration. The loaders layer still does
not import a kernel module (whose top-level workspace allocations rode along).

`ToleranceOptions.gsplatsDefaultTolerance` is gone with the reach it scaled —
gsplats has no continuous-dimension knob now, because the data carries the extent.
`meshSlabTolerance` stays: a mesh has no per-element extent, so its slab thickness
genuinely has to be invented.

#### The `?debug` query log no longer prints an epsilon as `0.00`

`SpatialQueryBuilder` formatted every tolerance with `toFixed(2)`, so the whole
gsplats epsilon range (1e-3 … 1e-5) printed `0.00` — indistinguishable from Lines'
true `0`, from a zeroed array, or from a NaN, on the one surface (`?debug` /
`pnpm agent:debug`) that would reveal an "empty node because nothing matched" bug.
Sub-0.01 values now print in exponential form; the common case (`0.25`, `1.00`,
`∞`) is unchanged. The points loader's sibling `Query tolerance (with discrete
awareness)` line used `toFixed(3)` and had the same blind spot one decade lower
(`2.75e-5` → `0.000`); it now shares the same `formatTolerance` helper.

#### The points fallback query reach ignores the ViewState ride-along (#1183)

`fallbackQueryTolerance` (the points query path when a node has no
`EffectiveRadiusConfig`) read `viewState.tolerance[d] ?? maxRadius` for
spatial/continuous dims, letting a scene/config constant decide a node's fetch
reach. It now always uses `maxRadius`, which at that call site is
`attrs.max_radius ?? config.dataLoading.spatial.defaultMaxRadius` — the node's own
attr where it declares one (and otherwise the same config default the ride-along
carried, where the flip is a no-op), the quantity `io/_ordering/points.py` expanded its chunk bounds
by, and what its sibling `calculateSpatialQueryTolerance` already says in as many
words ("ALWAYS use maxRadius for spatial dimensions, ignore tolerance array"). The
cost is stated plainly: where the ride-along was the `0.1` default and a node's
`max_radius` is larger, the query now FETCHES MORE — up to that node's own radius
reach — and a differing value can also cost a duplicate SliceCache entry. Neither is
a stale serve, and a scene-wide constant cannot know a node's extent. The
`extend_to_all` sentinel branch stays ahead of it and still wins.

That closes the reconciliation #1183 asked for between the two ViewState tolerance
producers (`dims-to-view-state.ts` → `maxRadius`, `view-state-manager.ts` →
`config.dataLoading.spatial.defaultTolerance`): no QUERY path reads the continuous
ride-along any more. Its magnitude is still read for a continuous dimension by two
non-query consumers, and the docs now say so rather than claiming the remaining
readers do not care: `buildSliceViewSig` keys the SliceCache on the raw value and
`viewStatesEqual` compares it (both collapse the ride-along only for a _discrete_
non-spatial dim). The two producers are inert today only because they agree
NUMERICALLY — `scene.userData.maxRadius` is never set in production, so both resolve
to `0.1`; a future divergence would cost cache misses and progressive resets, not
wrong data.

Also corrected, without changing behaviour: the Points arm's rationale, which held
for only one of the two write-side branches. With radii PRESENT (per-point or
scalar) the bound builder expands by the full radius, and there the reader-side
`maxRadius` is exactly the pure over-fetch the gsplats arm just removed. With radii
ABSENT it uses a `max(1% of range, 0.01)` margin, which under-expands against the
default radius the renderer applies, and the reader-side expansion is what keeps
those points from being dropped at a chunk edge. The tolerance computer is handed no
radii-presence flag, which is the honest reason points cannot simply copy the
gsplats fix; the Python under-expansion is the thing that should eventually change.
