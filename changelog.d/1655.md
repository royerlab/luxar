#### A points chunk written without radii is now bounded by the radius it is actually drawn with

`compute_chunk_bounds_points` expands each chunk's spatial bounds by the point
radius, which makes `[min - r, max + r]` exactly the set of query positions for
which some point in the chunk can still be visible — right in both directions,
not merely wide enough. That held only when the node carried a `radii` array.
With `radii=None` the bound was padded by an unrelated fudge instead — 1% of the
chunk's own coordinate range, floored at 0.01 — which bears no relation to the
0.5 the renderer falls back to: tighter than the footprint for any chunk
spanning less than 50 units, looser than it above that, and different for the
same scene authored in micrometres and in millimetres.

The tight case really did drop points, on a hidden continuous spatial dimension
— displayed dims and `extend_to_all` dims query with a tolerance of `1e10`
(`data/points/effective-radius-calculator.ts`), so the pad is inert there, and a
discrete axis never got radius extent on either the old or the new path. On such
a dimension a node with no `radii` array carries no `max_radius` attribute either
— the writer stamps that only alongside radii — so the viewer's spatial-index
query falls back to `defaultMaxRadius = 0.1`. A total reach of
`0.01 + 0.1 = 0.11` against a 0.5 disc leaves a point near a chunk boundary
genuinely unfetched, with nothing to notice it had gone.

Absent radii now simply mean the default radius: the no-radii case reuses the
scalar-radius path with `DEFAULT_POINT_RADIUS`, and the two produce identical
bounds. Barrier/discrete axes are unaffected — they still get only the tiny
`_BARRIER_BOUND_EPS` float-boundary pad on every path, because a categorical
axis has no footprint to cover.

The writer path that sees `radii=None` is `write_points_multi_lod`, reached
whenever `add_points` builds an additive ladder before the authoring default is
materialized — via `additive_lod=`, via the default stream ladder that
`substitutive_lod=` composes for its finest child, or via `partition=` parts that
carry a ladder of their own. `LuxarZarrCompiler.write_points(..., radii=None)` is
the low-level door. A plain `add_points` (and a bare `partition=`, whose parts
recurse back through it) fills in `DEFAULT_POINT_RADIUS` first, so those write a
uniform radius rather than none.

The 0.5 itself is now owned by `luxar.typing_utils.constants` instead of being
restated at each site. `add_points` (which materializes it when a caller
supplies no radii), the chunk-bounds writer and the viewer sites that stand in
for a missing radii array all read one constant per language, with the usual
mirror note and tests on both sides naming each other.

Only the write side changes here. For a radii-less node the reader still runs no
per-point effective-radius cull and still queries with the 0.1 tolerance
fallback, so an honest (wider) bound means more chunks fetched AND drawn — the
right trade against the old under-fetch. Shrinking the reader's tolerance to a
float-safety epsilon now that the bounds are honest is tracked as items 2 and 3
of issue #1655; those will have to account for stores written before this
change, which keep the old tight bounds and carry no version stamp to tell them
apart, so the reader cannot simply assume every bound already includes the
footprint.
