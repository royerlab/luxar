#### `test-fixtures-rendering.spec.ts` failures say what went unanswered (#1746)

This file ran on the config's 60 s per-test timeout while the helpers it calls
budget far more than that: `page.goto` can spend the 60 s `navigationTimeout`
before a helper even runs, `waitForLuxarReady` allows 45 s, `waitForPointsLoaded`
up to ~90 s (a 45 s loop plus one deliberately unclamped inner `getLuxarState`
probe), and `assertNoConsoleErrors` and `getLuxarState` 45 s each. A wall below
the sum of the phases it is meant to backstop cannot be attributed to any of
them: the run ended as a bare `Test timeout of 60000ms exceeded` with nothing to
say which dataset or which probe was pending — the same failure shape #1651
removed from the helpers. The file now configures 120 s, which is what the two
other `describe.configure` files in the suite use (`webgl-errors.spec.ts`,
`all-examples-smoke-test.spec.ts`), and at that value the first two phases live
inside the wall and report themselves.

Raising a wall is a backstop, not a fix. The fix is that the one unbounded probe
in the file — the 100k-texel element-texture scan in the `lut_uint16` test — is
now raced against a deadline through `raceEvaluate` and throws by name when the
page does not answer, saying the LUT round-trip assertions could not run rather
than passing on an empty read. Its budget is derived from what is left of the
test's own timeout (capped at 45 s, floored at 5 s, with 10 s reserved for the
throw and teardown) instead of being a constant: a fixed 45 s under a 120 s wall
is only reachable when the bounded prefix finishes inside 75 s, and a slower
prefix would let the wall fire mid-scan and reproduce exactly the unattributable
timeout being removed. What exposes this test and not its five siblings is the
scene rather than the probe — it renders 100k points where they render 20 to
1000, so only its page saturates the render loop — and the trade #1651 named
still applies: a bound can cut short a stall that would have ended.

The `test_lut_u16` fixture also drops its point radius from 0.5 to 0.1, which is
a fill-rate change and not a geometry one. The reasoning is in screen pixels: the
point shader clamps `pointSize` to a 1.5 px floor, so at this cloud's default
auto-fit framing a 0.5-radius point rasterizes 9.4 px across and a 0.1-radius one
1.9 px — still above the floor everywhere, so the sprite remains the size the
radius asks for while shedding roughly 25x of the overdraw that made this the one
fixture heavy enough to starve a shared box under the suite's parallel workers.
Smaller is a trap rather than a further saving: at 0.08 the clamp takes over, and
below it the fragment shader compensates the enforced sprite area by squaring
`min(vPointSize / 1.5, 1.0)` into alpha, so peak alpha collapses for no fill-rate
win at all. The point count stays at 100k because that is what puts the encoder
in the `lut_uint16` tier this test exists to exercise.
