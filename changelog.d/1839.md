#### Screen a built store's LOD ladders against the opening shot (#1839)

`luxar restamp-lod` can re-derive any legacy `coverage` ladder onto the current
`screen-area` selector, but nothing said whether doing so *buys anything on a
given store*. A ladder can only defer detail if the opening framing leaves it
room, and the answer is per-GROUP: a store whose 187 ladders are per-tile has no
single number. The new `luxar.io.lod_screening` measures it — per `kind=lod`
group, at the framing the viewer actually opens with, does the re-derived ladder
pick a strictly COARSER level than the stored one?

It is a read-only report and it can never fail a build. `scripts/check_demo_ladders.py`
gained `--screen` (append the pass to the existing streaming-ladder gate) and
`--screen-only` (skip the gate entirely, always exit 0); the default invocation —
the one `hatch run check` runs — is unchanged.

```
hatch run check-demo-ladders --screen-only datasets/examples/*.luxar.zarr
```

Four things the measurement is careful about, each of which a cruder one gets
wrong:

- **The cut is the group's own anchor, not a flat 1.0.** A derived whole-object
  ladder's finest rung is `WHOLE_OBJECT_FINEST_ANCHOR` = 0.5; only a
  partition-bound one anchors at `PARTITION_FINEST_AREA` = 1.0. A whole-object
  group opening anywhere in `[0.5, 1.0)` still shows full detail on frame one, so
  re-deriving it defers nothing. Which anchor a group gets — and which clause of
  the writers' two-clause rule decided it — is resolved through `lod_restamp`'s
  own `_is_partition_bound` and printed, so the screen and the rewrite can never
  disagree about it. Every refusal is shared the same way: `already-current` is
  decided on the SELECTOR ALONE, exactly as `_plan_lod` decides it (it returns
  before reading a single threshold). A descending stored ladder or an orphan
  `coverage_fraction` child skips a legacy group through `lod_restamp`'s own
  predicates; an already-current group keeps that finding as detail without
  changing buckets. A report that predicted a rewrite the command refuses to
  make would be worse than no report.
- **The two selectors are in different units.** What the store does TODAY is
  scored under its STAMPED selector: the legacy `coverage` metric is an UNCLIPPED
  projected diagonal in pixels over `FILL_FACTOR × min(W, H)`, range ~`[0, 4]`,
  while the re-derived side is always the viewport-clipped area fraction, range
  `[0, 1]`. Feeding either into the other's ladder inverts the answer — a unit
  cube at one framing reads 1.09 (finest under `[0, 0.5, 1.0]`) and 0.148
  (coarsest under `[0, 0.25, 0.5]`) — so the two are never mixed, and a test
  crosses them deliberately to keep it that way.
- **No inherited baseline.** Against an assumed "5.2x" figure a genuine win and a
  no-op look identical, so today's pick is measured, never assumed.
- **Aspect ratio is an input.** Every group is reported at 1:1, 16:9 and 21:9.
  Under the fitted framing the legacy metric happens to be aspect-invariant while
  the area metric is not, so a lone object filling the shot reads 0.56 at 1:1 and
  0.24 at 21:9 — two different levels. Those groups come back `fragile`, their own
  bucket, rather than being filed as a win or a no-op.

The verdicts are `win` / `no-op` / `fragile` / `off-screen` (the frustum gate
fires, so no metric is ever taken) / `already-current` / `skipped` with a reason.
Over a freshly built `datasets/examples` the five LOD stores screen as 1 win, 2
no-ops and 3 already-current: `energy_breakpoints` authors an explicit
`coverage_fractions` list, which pins it to the legacy selector, and it opens on
its finest 8,030-point level where a re-derived ladder would open on its 502-point
one. The three whole-object ladders that are already stamped `screen-area` bucket
`already-current` — the command would not touch them — and `partition_of_lod`'s
two tile-anchored parts already open on their coarse level. Two scenes are skipped because they
author `viewer_config.camera.position`/`target`/`target_node` and so do not open
at the fitted pose the screen models. A scene whose FOV comes from
`cinematic_mode` / `camera.fov_preset` is skipped the same way, with a pointer to
`--screen-render-fov 63`: that value lives in the viewer's own preset table and
guessing it wrong doubles every occupancy.

The camera pose, both metrics, the hysteresis pick, the frustum gate and the
nD→XYZ bounds projection are transcriptions of named viewer functions, each
citing its twin, and each is exported and unit-tested against values derived
analytically rather than snapshotted. Dynamic near/far clipping is deliberately
not modelled: the near-plane hazard that matters is the homogeneous-`w` straddle
inside `projectBoxNdcRect`, which never reads `camera.near`.
