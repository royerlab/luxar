#### The README, the format spec and the viewer's LOD docs describe today's threshold rule (#1732)

Several prose sites still described substitutive LOD selection as it worked
before v3.4. The README told readers the viewer picks a level with
`coverage_fraction = sqrt(N_i / N_finest)` and that the finest level shows once
an object's projected size reaches about half the viewport's fitted screen axis.
Both halves were wrong, and not by relabelling: the count-ratio derivation is
retired, and today's metric is a screen-AREA fraction (projected bbox rect area
over viewport area) where the old anchor was a projected DIAGONAL fraction. No
factor converts one into the other — a rect's area share depends on its own
shape and on the viewport aspect, so the square rect whose diagonal is half the
fitted axis covers ~7% of a 16:9 viewport, not a quarter of it. The paragraph
also said nothing about tiles, which left it subtly wrong for two of the six
recipes tabulated immediately above it.

The rule as the code has it: thresholds are derived by screen-occupancy halving,
count-INDEPENDENTLY (the counts set only the ladder's length), a whole-object
ladder anchoring its finest level at area `0.5` — `[0, 0.125, 0.25, 0.5]` for
four levels — and the two partition-bound recipes, `adaptive` and `overview`,
anchoring one step higher at `1.0`. The old "self-calibrates on any monitor or
aspect ratio" is now "needs no per-resolution or DPI tuning": an area fraction
is exactly resolution-independent but genuinely NOT aspect-invariant, since the
camera framing is fitted to one screen axis, so a wider viewport shows more
world and the same object covers a smaller share of it.

The two v3.2 version-history bullets in `GSPLATS_ZARR_FORMAT.md` each ended with
"the upper bound later widened to `4.0` for partition-bound ladders", which had
the driver backwards: the bound widened so a hand-tuned
`coverage_fractions=[...]` list stayed expressible after the viewer's fill
anchor was loosened — a ×4 rescale that engaged the finest level at a normal
full-frame view instead of only once the object overfilled the screen — and
partition-bound derived ladders then anchored on the already-widened bound.
`MAX_COVERAGE_FRACTION` = 4.0 (a Python-side constant) remains the ceiling on a
`selector="coverage"` ladder, and is only APPROXIMATELY fills-screen in those
legacy diagonal units — a screen-filling object's diagonal is 2.04 fitted axes
at the 16:9 reference, rounded to a plain 2. What it is not is today's anchor,
which under `screen-area` is `0.5` whole-object and `1.0` partition-bound. The
diagonal metric itself arrived in v3.2 for device-independent switching; making
the whole-object anchor aspect-exact was the goal of a later re-anchoring of its
denominator to the fitted screen axis, not of the metric.

Two viewer package READMEs stated the retired rule in the present tense as well
— `src/types/README.md`'s LOD-groups paragraph and `src/scene/README.md`'s
per-frame selector algorithm — as did the `scene/` doc comments the selector is
read through (the hysteresis pick, the cross-fade plan, the mesh freshness
note). They now lead with the derived `screen-area` path and name the diagonal
one as the legacy `selector="coverage"` path it has become, matching the doc
comment in `types/lod-group.ts` that was already correct.

The mesh substitutive-LOD path carried the same premise three more times — the
wrapper docstring, the loop guard that drops a level which fails to reduce the
surface, and the test covering that fallback — each justifying the drop by
saying a duplicate count hands `coverage_fractions` a repeated ratio that is not
strictly ascending and raises. It no longer does: thresholds come from the
ladder's LENGTH, so a duplicate count is not a duplicate threshold. Dropping the
level is still right, for the reason now stated — two identical surfaces would
each claim their own halving of screen occupancy, so the viewer would swap
between them and pay a load for nothing. `decimate_cluster`'s `Raises` block
needed a different correction rather than the same one: it explained why an
empty result is an error by pointing at the `coverage_fractions` raise, which
only fires on an empty FINEST level, while every level that function produces is
a coarse one. The reason is one layer up — an empty return would be dropped in
silence by the wrapper's strictly-ascending guard, and the degenerate mesh would
come out as a plain leaf with nothing naming which mesh caused it.
