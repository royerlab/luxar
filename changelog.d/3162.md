#### Depth sorting on the GPU for native WebGPU

Order-dependent blending (normal, volumetric) draws points, lines and splats back to front. On WebGPU the CPU sort worker's order was uploaded whole on every re-sort, 40 MB for a 10M-splat node, and that upload, not the shaders, made large sorted scenes slower than on WebGL: on an RTX 3070 a 10M-splat orbit's frame p95 was about twice WebGL's.

On a native WebGPU device the viewer now re-sorts these nodes on the GPU as the camera moves. A compute pass reads each element's center from the element texture already on the GPU and writes the order into the buffer the vertex shader reads, so a re-sort moves nothing across the CPU. A commit's first order still comes from the worker, which keeps the CPU copy that appends and buffer growth build on. A 10M-element sort takes about 9 ms of GPU time on an RTX 3070. The order matches the worker's to within one depth bucket for a rare element near a bucket edge. Mesh nodes, nodes too large for the device, and the other backends keep the worker, and so does everything while the pipelines compile or after a device loss.

It is on by default on native WebGPU (`config.depthSort.gpuSort`); `?gpuSort=0` sorts on the worker instead. On the RTX 3070, a 10M-splat orbit's frame p95 drops from 193 to 98 ms (WebGL: 93 ms), CPU time per frame from 4.2 to 1.2 ms, and the extra renders sort results caused are gone. `__luxarDebug.readDrawnOrdering(uuid, count)` reads back the order a node is drawn with.
