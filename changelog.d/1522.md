#### A mesh reveal ladder's vertex buffers now track the committed prefix (#1522)

`#1521` sized a mesh's `position`/`color`/`normal`/`aScalar`/index buffers from the
node's LIFETIME totals rather than the committed prefix, so a reveal ladder's
levels write INTO the same capacity-sized buffers instead of rebinding (and
orphaning) them on every level. That capacity change left every one of those
vertex attributes needing an in-place UPDATE path of its own, and two of them
did not get one.

**`color` first.** Its guard kept comparing counts — and once the buffer is
bound at the node's full capacity, every level of a ladder binds at that SAME
count, so the guard could never tell "just installed" apart from "still holding
an earlier level's prefix". Every vertex a later level revealed kept the
zero-filled slot it was born with, which zeroes alpha for a padded RGB or any
RGBA mesh — invisible, not merely wrong-coloured, since `vAlpha` is a mesh's
entire coverage term — and leaves a `float32` RGB mesh black-but-opaque.

**`normal`/`aScalar` have the identical bug.** `replaceVertexAttribute`
gated its in-place copy on `existing.array !== data`, comparing the BOUND
buffer's identity against the caller's array — but once that buffer is a
capacity-sized copy `atCapacity` made at the first rebind, it is never
identity-equal to the caller's array again, including on the very level that
produced it. So a laddered mesh with normals or scalars re-uploaded the ENTIRE
capacity buffer (`V·12` bytes for normals, `V·4` for scalars) on every slice
move, with no update ranges, at every level — real bandwidth at the 2^27-vertex
cap, not merely a missed optimization.

Both are fixed the same way now: `isAttributeCurrent`/`stampAttributeCurrency`
track currency by the SOURCE array's own identity plus the committed vertex
count, stamped on `geometry.userData`, instead of comparing against the bound
buffer. `color`, `normal` and `aScalar` share one helper rather than three
near-copies of the same two lines. The in-place writes are also now bounded to
the prefix actually rewritten via `clearUpdateRanges`/`addUpdateRange`, mirroring
`applyMeshIndices` — before, both `color`'s pad-loop write and `normal`/`aScalar`'s
copy dirtied the WHOLE capacity buffer on the classic WebGL backend, which
honours update ranges. A shared `padRgbIntoRgba` helper replaces the RGB→RGBA pad
loop that used to live twice (once per fresh-buffer build, once per in-place
refresh), so the `uint8`/`uint16` opaque-alpha constant cannot diverge between
them.

**A second, unrelated defect surfaced the same way: `position` could go stale
across an aborted ladder commit.** `updateMeshGeometry`'s position upload is
gated on `positionChanged || keyChanged`, both derived from the projection's
`displayDims` key — but neither one can see a LEVEL change. A superseded commit
(an ordinary scrub landing mid-fetch) lets `projectMeshTo3D` stamp the
loader-owned scratch's `displayDimsKey` and memoize the level's data without the
geometry ever receiving it; the next sweep then re-projects the same memoized
level with `positionChanged === false` and an unchanged key, while the index and
draw range advance anyway. Every vertex that level revealed kept the zero fill
`atCapacity` gave it, so the newly revealed triangles drew as a fan collapsed at
the display-space origin — and stayed wrong until the next `displayDims` change.
Fixed the same way `keyChanged` repairs a key gap: `geometry.userData.
meshUploadedVertexCount`, stamped only where the upload actually runs, adds a
`countChanged` term to the gate so a commit whose prefix the geometry never
uploaded gets uploaded on the very next sweep.

Belt-and-braces alongside these: the default-white colour rebind now clears the
authored-colour currency stamps instead of leaving them stale (not reachable
today — colour presence is a per-node constant — but a stale stamp there could
otherwise make a later authored commit a permanent no-op).
