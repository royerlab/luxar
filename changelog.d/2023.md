#### Separate what the repo ships from what the record serves

`data_manifest.json` file entries gain an optional `hosted_sha256` alongside
`sha256`, and `ensure_dataset` now understands both. `sha256` describes the copy
this repository ships — for a git-LFS file it is literally the pointer's oid —
while `hosted_sha256` describes what the Zenodo record serves.

These were the same number by construction, so nothing ever had to choose between
them, and the manifest's one field quietly served both jobs. A refit broke the
identity: the hosted artifact and the in-repo copy became different bytes. Since
the fetch treated that field as the authority at every step, pinning the hosted
digest truthfully made the in-repo fallback fail its own checksum — so the LFS
payloads had to be deleted in the same change, so Zenodo became the only source,
so the record had to be published before the PR could merge. Publication ended up
on the critical path of every demo-data change, and there are eight more refits
queued.

Bytes already in hand are now accepted if they satisfy *either* contract: hosted
first (canonical, silent), then local (usable, reported as "the record hosts a
newer build"). Both the cache leg and the in-repo leg had to agree on this, since
the cache slot is keyed on `(dataset, variant, basename)` with no record of which
source filled it — a cache check stricter than the leg that wrote it would
quarantine its own copy and re-make it on every run. Only the download leg is
strict, and strictly on the hosted digest: bytes from the record must be the
record's bytes. Nothing changes for the datasets whose two digests agree, which
is most of them, and a `hosted_sha256` equal to its `sha256` is indistinguishable
from having none.

The generator carries `hosted_sha256` forward rather than deriving it, because it
cannot: `_checksum` reads a pointer's oid or hashes local bytes, and what a record
serves has no source on disk. Without that, a dataset whose data directory
happens to be *visible* would silently lose its hosted pin on the next
`make gen-data-manifest`, while a dataset with nothing on disk kept its own — a
field surviving in some rows and evaporating in others is worse than one that
never worked.

Consequence worth knowing: while an in-repo payload is present it wins over a
newer hosted artifact, so a checkout with a stale LFS object keeps serving the
older generation (loudly). That is the trade that lets the pins be truthful while
the payloads are still in the tree, and it ends when they are removed — which is
now an independent change rather than something sequenced around a human
publishing a record.
