#### The SortWorker starts before the data, not during it

The SortWorker was spawned lazily by the first order-dependent commit, which is
precisely when this thread and the data-worker pool are saturated decoding the
scene — and the worker's `initialize()` reply has to be dispatched on that same
busy thread. At around three million points (`demo_gaia_milky_way_3m` is exactly
this shape) the reply simply queued behind the decode: in the reproduction the
worker logged its own readiness, WASM up and answer sent, while the main thread
was still waiting for it.

The worker is now started at app init, while nothing is loading, so WASM
initialization no longer overlaps the data flood at all. The commit path still
calls `ensureWorker()` and still dedupes on the cached init promise, so an
embedder that configures late is unaffected — but it now normally finds a worker
that came up seconds earlier. The chunk and its WASM are now fetched on every
page load, including scenes with no order-dependent geometry; `?depthSort=0`
spawns nothing at all. One consequence for anyone relocating the worker bundle:
`setSortWorkerUrl` / `setSortWorkerWasmPath` must be called before
`LuxarApp.init()`, since the spawn they redirect happens during app init rather
than at the first commit. Those two are internal entry points on
`rendering/depth-sort-coordinator` — not re-exported from `src/index.ts`, and the
package's `exports` map publishes only `.` and `./styles.css` — so they are
reachable from inside the source tree (a vendored or bundled viewer), not from an
npm install.

The coordinator also stopped hand-rolling its own init race and now uses the
data-worker pool's `worker-pool/lifecycle/init-with-guard.ts`, which is how the
two startup paths stay in step. It gains the `onmessageerror` arm the private
copy never had: a worker answering with an unserializable payload used to leave
`initialize()` pending until the deadline, i.e. reported as a slow start rather
than as the broken worker it is. The deadline itself is now the configurable
`depthSort.workerInitTimeoutMs` (default 30 s, `0` disables the guard) instead of
a module constant.

Finally, giving up is no longer silent. Once the subsystem has given up for the
session AND some visible, still-committed, order-dependent node actually wants
sorting, the data-loading monitor's performance footer says `depth sort
UNAVAILABLE` — the same "does anything want sorting" predicate that gates the
retry, so the two cannot drift, and so a CSP-blocked warm-up on an all-additive
scene does not report on a subsystem that scene never uses. The note is a
one-directional proof: when it shows, visible order-dependent geometry IS being
drawn in storage order. Its absence proves nothing — a starved init that is still
retrying, `?depthSort=0`, and a single commit that could not reach an otherwise
healthy worker all draw identity order without it.
