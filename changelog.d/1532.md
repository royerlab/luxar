#### The mesh index-buffer reuse guard now survives WebGPU's own in-place substitution

`applyMeshIndices` allocates a mesh node's index buffer once, at its full
face-count capacity, and draws the visible prefix via `setDrawRange` — because
three never frees an index buffer when `geometry.index` is *replaced*
(`WebGLAttributes.remove()` only runs on geometry disposal), so a per-epoch
`setIndex` would orphan one GPU buffer per slice move. Reuse depended on a
dtype check comparing the existing buffer's array type against whatever
`createMeshIndexAttribute` would allocate for the node — but on the WebGPU
backend, `WebGPUAttributeUtils.createAttribute` rewrites any non-normalized
Uint16Array (or Uint8Array) index attribute to Uint32Array IN PLACE the first
time it uploads it, mutating `bufferAttribute.array` directly. After the first
WebGPU upload of any mesh under 65,536 vertices, the existing buffer's array was
already a Uint32Array even though it was allocated as a Uint16Array, so the
"matches what I would allocate" comparison failed on every subsequent epoch —
forcing a `setIndex` (and the leak this function exists to prevent) on every
slice move, on WebGPU only.

The guard now asks the right question: can the existing buffer *carry* the
indices about to be written, not whether it is the exact dtype the node would
be allocated fresh. A Uint32Array always can; a Uint16Array can only when the
node itself fits under 65,536 vertices. The genuine widening direction — a
node whose existing buffer is a Uint16Array but which now needs 32-bit indices
— still falls through to `setIndex` and rebinds, since a Uint16Array cannot
represent an index past 65,535 no matter what mutated it.
