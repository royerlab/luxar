#### The silent E2E waits stop passing on state they never read

Two of the E2E poll loops ended their budget by simply returning:
`waitForNavigationComplete` closed with `// Timeout is not an error - loading may
have completed` and `waitForSpatialQuery` with the same shape, and every
iteration of both swallowed a probe failure in an empty `catch`. That is right
for the case they were written for — a navigation or query that settled before
polling started, which several call sites deliberately choose the silent variant
because of, since their action never toggles `isLoading` at all. It is
indistinguishable, though, from the starvation class #1724 describes: on a page
whose main thread is saturated, `getLuxarState` answers nothing, the helper
returns after its full budget having read no viewer state, and whatever the spec
asserts next reads stale state. `spatial-index-accuracy.spec.ts` calls
`waitForNavigationComplete` twice in one test. That is a vacuous pass rather than
a flake, which is why it is worth a change of contract rather than a longer
timeout.

The end of the budget is now a real decision, split on one question: did any
probe ever answer? If none did, the helper throws, naming itself, its budget and
the last probe failure — it never once read viewer state, so there is nothing for
the caller's assertions to stand on. If a probe answered but the condition never
settled, the helper still returns normally — that is the tolerated case the nine
`waitForNavigationComplete` call sites depend on — but emits exactly one
`console.warn` in the house `[⚠️] [E2E <helper>]` form saying the condition was
never observed, with the carried probe diagnostic appended when there is one. The
healthy path is unchanged and stays silent: those call sites succeed on their
first probe, because `isLoading` is already false by the time they poll.

For that decision to mean anything each probe is now clamped to whatever is left
of the loop's own budget, raced against a fresh Node-side object sentinel. An
unbounded `page.evaluate` can outlive the loop's `timeout` entirely and let it
exit as though it had polled, which is exactly what must not happen where exiting
is a tolerated outcome; a missed clamp counts as a probe failure rather than as an
answer. The reverse is true of the loops #1725 fixed
(`waitForPointsLoaded`, `waitForDimensionNavigation`): those throw on timeout
already, so a late answer is still a success there and clamping their probes would
newly fail a healthy-but-slow page. Same primitive, opposite conclusion,
because the give-up differs.

`waitForNavigationComplete` also had a second silent exit. Its preliminary
`page.waitForFunction` for `typeof isLoading === 'boolean'` used to `catch`, sleep
300 ms and return, on the stated reasoning that "navigation completes before we
start polling" — which does not explain a missing `isLoading` at all, since the
flag exists whenever the debug interface does. That failure is now recorded as the
initial probe diagnostic and falls through into the poll loop, so the state probe
gets its chance to answer, or to produce a better diagnostic, and the single
end-of-budget decision governs both paths.

`waitForWebGLError` had the same swallow-and-continue shape one level down:
`getWebGLErrors` is a bare `page.evaluate`, so the first unanswered read blew
straight through the helper's 5 s budget to the whole test's. Its reads are
bounded the same way, with the sentinel being a Node-allocated array compared by
identity rather than by contents — an empty list is a legitimate answer here, one
a clean GL queue returns on nearly every poll. It still never throws, since it
returns data rather than a verdict, but a give-up now warns once and says whether
any read answered at all, so an unsatisfied predicate cannot be read as "the page
was healthy and produced no such error".

What this cannot do is tell a page that would have answered late from one that
never will; a deadline has no way to distinguish them, so a generous budget that
elapsed is the only evidence available, and any bound can in principle cut short a
stall that would have ended. The trade is the same one #1651 took for
`getConsoleMessages`, and for the same reason: a named failure after a bounded
wait is worth more than an unattributable pass. `src/tests/unit/tests/e2e-helpers-silent-waits.test.ts`
covers all three helpers against fake pages — the wedged case rejects (or, for
`waitForWebGLError`, returns) within roughly its own budget instead of hanging,
the answered-but-unsettled case resolves with exactly one warning, and the healthy
case stays silent, which is the assertion that protects the existing call sites.
