#### The silent E2E waits stop returning on state they never read (#1726)

Two of the E2E poll loops ended their budget by simply returning:
`waitForNavigationComplete` closed with `// Timeout is not an error - loading may
have completed` and `waitForSpatialQuery` with the same shape, and every
iteration of both swallowed a probe failure in an empty `catch`. That is right
for the case they were written for — a navigation or query that settled before
polling started, which several call sites deliberately choose the silent variant
because of, since their action never toggles `isLoading` at all. It is
indistinguishable, though, from a run in which every probe FAILED: `getLuxarState`
rejects on a page with no debug interface or a destroyed execution context, the
loop swallows each rejection, and the helper returns after its full budget having
read no viewer state at all.

What that cost at today's call sites is ATTRIBUTION, not a false pass. All nine
`waitForNavigationComplete` calls follow the wait with a page probe of their own —
`getLuxarState`, a bare `page.evaluate`, or a `getDimensionValue` that answers
`-1` and then fails its own `expect` — so a helper that read nothing produced a
FAILING test one statement later, charged to the wrong statement and reported as a
bare `Debug interface not ready` or a nonsense `-1`. Six of the nine (all in
`spatial-index-accuracy.spec.ts`) additionally sit right after
`waitForSpatialQueryOrThrow`, which cannot have succeeded unless the page answered
within the last 8 s, so on those the new throw is near-unreachable. The vacuous
pass proper — confirmed nothing, and nobody re-probes afterwards — is a hole in
the CONTRACT rather than a bug in a current caller, and it is closed here for the
next caller alongside the attribution win, which is the immediate one.

The end of the budget is now a real decision, split on one question: did any
probe ever answer? If none did, the helper throws, naming itself, its nominal
budget, the time it actually spent and the last probe failure — it never once read
viewer state, so there is nothing for the caller's assertions to stand on. If a
probe answered but the condition never settled, the helper still returns normally
— that is the tolerated case the nine `waitForNavigationComplete` call sites
depend on — but emits exactly one `console.warn` in the house `[⚠️] [E2E <helper>]`
form saying the condition was never observed, with the carried probe diagnostic
appended when there is one. Both reports state the measured elapsed time next to
the nominal budget, because neither loop clamps its probes: a
`waitForNavigationComplete(page, 15000)` whose preliminary wait spends 10 s and
whose state probe then carries its own 45 s deadline can run for ~55 s, and
reporting that as "15000ms" would send the reader after the wrong problem. The
healthy path is unchanged and stays silent: those call sites succeed on their
first probe, because `isLoading` is already false by the time they poll.

What this fixes is precisely the swallowed probe FAILURE, not a swallowed
timeout. A probe that never answers AT ALL still hangs the loop — `page.evaluate`
carries no deadline of its own — and surfaces as the test-level timeout, which
this change deliberately does not paper over: these loops succeed on ANY
satisfying answer, so bounding the probe here would turn a late-but-satisfying
answer from a healthy-but-slow page into a hard failure. The bound belongs on the
probe. Once `getLuxarState` carries one (#1725, alongside the two loops that
already throw on timeout — `waitForPointsLoaded` and `waitForDimensionNavigation`),
the starvation class #1724 describes reaches this decision as a rejection with its
own diagnostic, and the new throw is what reports it instead of discarding it.

`waitForNavigationComplete` also had a second silent exit. Its preliminary
`page.waitForFunction` for `typeof isLoading === 'boolean'` used to `catch`, sleep
300 ms and return, on the stated reasoning that "navigation completes before we
start polling" — which does not explain a missing `isLoading` at all, since the
flag exists whenever the debug interface does. That failure is now recorded as the
initial probe diagnostic and falls through into the poll loop, so the state probe
gets its chance to answer, or to produce a better diagnostic, and the single
end-of-budget decision governs both paths. The fall-through has a stated cost: a
page that never answers now hangs this loop on that path too, where before it
returned after `min(timeout, 10000) + 300` ms — a wash at today's call sites,
whose very next statement is itself an unbounded evaluate that hangs on the same
page. The poll loop became a `do`/`while` so it always probes at least once: the
preliminary wait can cost up to 10 s on its own, and reporting "no probe answered"
without having probed would be a false diagnostic.

`waitForWebGLError` is bounded rather than split, because it returns data instead
of a verdict: `getWebGLErrors` is a bare `page.evaluate`, so the first unanswered
read blew straight through the helper's 5 s budget to the whole test's. Each read
is now raced against the remaining budget, with the sentinel a Node-allocated
array compared by identity rather than by contents — an empty list is a
legitimate answer here, one a clean GL queue returns on nearly every poll — and no
FURTHER read is dispatched into a remainder shorter than one poll interval, since
`getWebGLErrors` DRAINS the GL queue in-page and an answer discarded for missing
the deadline takes the real errors it already cleared with it. The FIRST read
always goes out, however short the budget, so a `timeout` below `pollMs` still
checks the queue once instead of returning `[]` while warning that nothing was
checked. That trade is inherent to bounding a helper that returns data; removing
it means bounding `getWebGLErrors` itself, which has 21 direct call sites across 11
spec files and belongs with the probe-bounding work in #1651. The helper still
never throws, but a give-up now warns once and says whether any read answered at
all, so an unsatisfied predicate cannot be read as "the page was healthy and
produced no such error". It has no call sites today, so that contract change is
forward-looking.

`src/tests/unit/tests/e2e-helpers-silent-waits.test.ts` covers all three helpers
against fake pages, with the per-test redness against the old code recorded in its
header: a page whose probes reject makes both loops throw within their own budget
(and, separately, never resolve); an answered-but-unsettled page resolves with
exactly one warning carrying the probe diagnostic; a budget the preliminary wait
consumes whole is still probed exactly once; a page whose probes never settle
leaves the helper PENDING rather than resolving, which is the "we do not fabricate
a success" half of the contract; and the healthy cases stay silent, which is the
assertion that protects the existing call sites.
