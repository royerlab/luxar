#### One copy of the LOD-refinement plumbing instead of four

The viewer's four progressive-LOD refinement wrappers — one per geometry type —
were 83-91% identical after name normalisation. Each carried its own copy of the
admission gate, the abort-versus-failure catch block with its pass rollback and
backoff counting, the residency bookkeeping, and the four loop-progress
callbacks. Only the load-and-commit body genuinely differs, and it still lives
per geometry, because parameterising it would trade four readable flows for one
function with a strategy argument.

The saving in lines is small — 43 — and that is not the point. One coupled
invariant in particular now lives in one place: the gate's decline reasons must
match the progress callbacks' exclusions, because a budget-declined loader still
reports having more levels, so leaving it out of the "is anyone still working?"
check means the refinement loop never terminates while holding the update lock.
That pairing used to be restated four times.

Nothing about how refinement behaves changed. The four wrappers were already
covered by one shared behavioural contract, which is what made collapsing them
verifiable: each of three deliberate regressions introduced into the extracted
code fails in all four geometries and passes again when reverted.
