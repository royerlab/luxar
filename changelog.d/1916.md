#### Changing the field of view now invalidates the GPU pick buffer (#1916)

A field-of-view edit reprojects every element on screen, and picking was never
told. `adjustFOV` wrote `camera.fov`, called `updateProjectionMatrix()` and
pushed the new projection into materials — but dirtied nothing, so the cached
offscreen pick buffer kept answering at the *pre-FOV* projection. Hover then
resolved whichever element used to occupy that pixel; with a wide enough FOV
swing the tooltip named something else entirely. It self-healed on the next
thing that happened to dirty the buffer — any camera orbit, a window resize, a
perspective↔ortho swap, a layers-panel visibility toggle — which is why it went
unnoticed.

Both FOV entry points were affected, and neither is reachable through the
controls: the rendering-controls panel (slider, presets, cinematic mode) calls
`SceneManager.updateFOV` directly, and the Ctrl/Cmd-wheel path is *deliberately*
declined by the orbit controls, which bail out of exactly that event on the
grounds that "Ctrl/Meta+scroll belongs to the window-level FOV handler". So no
`change` event fired from either, and `change` is what the picking session wires
to `markDirty`.

`SceneManager` now dispatches a `projection-changed` event, which
`initPicking` wires to `pickingSystem.markDirty()`. It is deliberately distinct
from the existing `camera-changed`: that one announces the camera *instance* was
swapped and is answered with `setCamera`, whereas here the same camera simply
reprojects, so `setCamera` would be the wrong verb. The dispatch is gated on the
camera's `fov` actually moving rather than on `adjustFOV`'s return value, which
is `true` even when `validateFOV` clamped the request to the value already in
effect — at the min/max bound that would otherwise fire on every wheel tick and
fade the hover tooltip for nothing. The orthographic branch of `updateFOV` stays
silent too: it only updates the stashed perspective FOV for a later swap and
leaves the live projection untouched.

Clipping-plane updates mutate the projection matrix by the same route and are
left alone: near/far shifts depth precision rather than where an element lands
on screen, so a stale pick buffer stays correct in the way that matters here.
