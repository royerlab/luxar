#### `luxar mesh import` reads VTK XML PolyData (`.vtp`)

`.vtp` is what ParaView, VTK, PyVista and meshio write for a surface, and what a
marching-cubes isosurface comes out of a segmentation pipeline as — so it was the
conspicuous gap in an importer that already read PLY, OBJ, STL and glTF. It now joins
them, on the same terms: NumPy plus the standard library (`xml.etree`, `base64`, `zlib`)
and no new dependency, so it works on a bare `pip install luxar`.

Every encoding the format allows is decoded, because a `.vtp` in hand is whichever one
its writer chose: `ascii`, inline base64 (`format="binary"`), and an appended section in
either `raw` or `base64` form, each optionally `vtkZLibDataCompressor`-compressed, with a
`UInt32` or `UInt64` block header and either byte order. `Polys` are fan-triangulated and
`Strips` triangulated with the alternate winding a strip requires; `Verts` and `Lines`
carry no surface and are dropped; `PointData` normals and colours come across.

Three of those are traps that misparse *without erroring*, which is why each is handled
explicitly and tested on decoded geometry rather than on bytes. ParaView's default
`<AppendedData encoding="raw">` puts arbitrary binary inside the document, so an XML
parser refuses the whole file, header included — the stream is split on the literal
`<AppendedData` first and only the header portion parsed, by a pull parser that hands back
a usable tree even though the closing tags never arrive. A *compressed* base64 block is
two concatenated base64 streams, the block header encoded separately from the payload, so
a single `b64decode` of the element text yields plausible garbage. And `offsets` are
cumulative *end* offsets with no leading zero, which read as starts merely rotates the
polygon list. An LZ4- or LZMA-compressed file is refused by name rather than inflated as
zlib, and a `.vtu` (UnstructuredGrid) is named as the volume mesh it is, with a pointer at
ParaView's *Extract Surface*, instead of failing thirty lines deeper in the PolyData
parser.

Two structural features of the format come across as well. A PolyData may hold several
`<Piece>`s, each numbering its own points from 0; they are concatenated into one surface
with every index rebased, bounded against its own piece first so an over-running index
cannot quietly stitch itself to a neighbouring piece's geometry, and `PointData` is taken
all-or-nothing across them rather than inventing rows for the pieces that lack it. And
every tag may sit in an XML namespace, prefixed or default — tags are matched by local
name throughout, and the header parser reads the tree ElementTree already built rather
than reconstructing source spellings, which is not possible in general because one
namespace URI may legally have two in-scope prefixes at once.
