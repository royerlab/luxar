#### Authored appearance now survives a rebuild from a compressed archive too

Carrying the source root's compositing attrs across a `gsplat lod` rebuild only
worked for a `.gsplats.zarr` *directory*. The read bailed on anything else, so a
`.gsplats.zarr.zip` or `.gsplats.zarr.tar.gz` — both first-class recipe inputs,
extracted transparently by the loader — still lost every authored value:
`blending_mode` gone, `opacity` / `gamma` / `intensity` / `absorption` back to
their identity, the run exiting 0 without so much as a mention. The identical
dataset stored as a directory kept all of it, which made the loss look like a
property of the data rather than of how it happened to be packaged.

The stated reason for the bail was that peeking into an archive would extract
gigabytes a second time. It would not. A root's `.zattrs` is one small member: the
zip central directory (or the tar header stream) locates it and only that member's
bytes are read, nothing is written to disk, and no link is ever followed. That
peek now lives beside the extractor in `luxar.gsplats.io._archive`, where the
archive layout and its threat model are already single-sourced, and it looks for
the same *kind* of store root the extractor does: the top-level `*.gsplats.zarr`
directory a compressed save writes, else — only when it is the archive's *sole*
top-level directory — that directory whatever it happens to be named. For an
archive holding one store, which is every archive a compressed save writes, that
is the same node the extractor loads. Both layouts therefore read correctly, and
neither a child group's `.zattrs` nor a stray one loose at the archive root can
be mistaken for the dataset's own. An archive holding *several* `*.gsplats.zarr`
stores is not a single dataset, and the extractor itself picks among them
arbitrarily; the peek may land on a different one.

An archive with several top-level directories and no `*.gsplats.zarr`-named one
carries nothing rather than guessing. There is no right answer to guess: the
extractor picks among such directories by `iterdir()` order, which no archive
index can predict, so the peek cannot agree with it. Carrying nothing is simply
the behaviour that preceded this feature, whereas carrying a junk sibling
directory's attrs would author an appearance from a node that is not the dataset.
