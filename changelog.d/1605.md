#### The demo manifest catches up with what is actually uploaded

Five datasets were marked `pending_upload` with the flag never cleared after the
upload happened. Four of them were fine in practice, because their checksums had
been filled in anyway; two were not fetchable at all, since `pending_upload` came
with an empty `files` list and nothing else pins a name, size or checksum. The
neuromast timelapse and the h2afva 253-timepoint fit were both live in their
Zenodo records while the manifest still described them as awaiting upload, so
`ensure_dataset` could not reach either one.

Both are now pinned by SHA-256 (each local copy's MD5 checked against the
checksum Zenodo reports for the uploaded file first), the four stale flags are
gone, and the h2afva variant sizes are corrected: the full timelapse is 11.4 GB,
not the 16 GB the manifest and the record both estimated.

A pin is the prerequisite, not the whole download path. The three records now
carry their real ids and reserved version DOIs — Zenodo fixes both at deposition
time, and the deposition id becomes the record id on publication, while the
version-independent concept DOI is only minted once a record goes public —
together with a `published` flag that is still false, because all three are drafts and
a file URL into a draft 404s for everyone. While that flag is false no URL is
built at all, so the Zenodo leg stays dormant exactly as it did when the ids were
null and demos keep resolving cache then in-repo copy. Flipping the three flags at
publication is the only edit needed to turn fetching on; recording the ids now
keeps the manifest, the record text and the DOIs from drifting apart in the
meantime. The record titles are synced with the live ones as well — the h2afva one
used to call the 51-timepoint cut a "subset", which its own record text
contradicts.

The h2afva 51-timepoint variant stays deliberately unpinned. The file currently
in the record predates the isotropic correction, so it would render squashed by a
factor of four along z, and it carries no substitutive level-of-detail levels at
all. Pinning it would point the demo's default download at that build.

Separately, four demos wrote a cache directory they never declared in `DEMO_META`,
so `luxar demo cache list` and `cache clear` could neither show nor free it: the
INRIA garden capture (1.5 GB), the SOG MatrixCity scene (423 MB), the Visible Human
head and the Dip-C genome. The cache inventory saw them only as anonymous orphans.

Two tests hold this together, each checking both directions. `pending_upload` now
has to agree with the file lists, so a stale flag fails and so does an unflagged
dataset with an empty list; and every cache directory a demo writes has to be
declared, derived from the demo's own path expression rather than a hand-kept list.
