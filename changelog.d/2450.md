#### The README gallery is hosted now, and pinned to the bytes rather than a path

The 58 committed gallery tiles — 181 MB of git-LFS across 29 demos — are gone,
and the README points at `data.luxarviewer.dev/media/<sha256-prefix>.<ext>`
instead. HEAD's git-LFS drops from 599.5 MB to 418.6 MB, which matters because
GitHub's free tier allows 1 GB of bandwidth a month and a public clone pulls
HEAD's LFS objects: at the old size the second clone of the month exhausted the
quota, and an exhausted quota fails CI as readily as it fails a visitor.

The keys are content-addressed rather than dated, because retention by wave
count is a countdown — a tag pinned to `…/media/<wave>/` breaks after N
refreshes, which is a slower version of the problem being solved. A key that
names its own bytes cannot rot, and a refresh uploads only what actually
changed.

`scripts/gallery/media-manifest.json` is committed alongside, carrying each
object's key, byte count, full sha256 and content type. It is what generates the
README's URLs and what the harness maps a key back through — but it also keeps
"what did the gallery look like at this commit" answerable from the repo alone,
which is the one thing deleting the tiles would otherwise have destroyed.

Two consumers followed the id into the manifest. `GALLERY_ONLY=readme` used to
recover demo ids from README paths and now recovers them from keys, treating an
unmapped key as an error rather than quietly capturing a smaller set than the
README shows. The tile-staleness report used to blame each committed tile and
now dates the whole generation by the commit that last touched the manifest,
which is what a capture rewrites.
