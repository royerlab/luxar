#### An invalid `partition=` spec on the gsplats wrapper doors no longer strands a wrapper

`add_gsplats_from_data(..., lod_group=True, partition="nonsense")` raised
`Could not add gsplats 'child_0': partition must be None, True, or dict; got
str` and left `g` on disk as a childless `kind=lod` group that survived
`finalize()` — so it reached the viewer. The same held for `partition=3`,
`partition={"max_elements": 0}` and `partition={"rule": "bogus"}`: the two
faults #1529/#1534 closed elsewhere, a stranded wrapper and a message blaming
an internal `child_0` for the caller's own kwarg.

#1534 hoisted `validate_render_attrs` into the pre-wrapper gate on this door,
which closed the bad-attr-KEY half. The spec half stayed open because
`partition` is one of the three keys that gate deliberately excludes — it is a
named parameter of the leaf adder and must ride through to drive each child's
BSP split — so its VALUE was still judged one level down, inside `child_0`,
after `add_lod_group` had created the group. The fix is not a wider exclusion:
excluding the key is exactly what lets a valid spec through.

The leaf adders' partition-spec validation is now one function,
`core/group/partition.py::resolve_partition_spec`, replacing four byte-identical
inline copies (Points, Lines, GSplats, and Mesh's private
`_resolve_mesh_partition`). The gsplats `lod_group=` gate calls it in the slot
right after the node-attrs gate, for its verdict alone. Messages and exception
types are unchanged and now byte-identical to the flat `add_gsplats(...,
partition=<same bad value>)` call, prefix included, with nothing written on a
refusal. Precedence parity with the flat path is pinned in both directions now
— the node-attrs gate above the check still wins, the labels refusal below it
still loses — because the slot, not the check, is the design claim here.

The GRAFT door had the identical bug and is closed the same way.
`scene.add_gsplats_from_file("g", <nested .gsplats.zarr>, partition="nonsense")`
answered `Could not add gsplats 'part_0': …` and left the `kind=partition`
wrapper on disk through `finalize()`, because `graft_gsplat_node` builds its
wrapper from the stored tree before the first leaf write; one call in the slot
that already holds that door's `strip_absent_attr_kwargs` /
`reject_data_owned_channels` pair fixes it, with the same message parity.

Two values are deliberately NOT judged, at either door, because the leaf does
not judge them either. `partition=False` is vocabulary, not a bad spec — it is
the explicit no-partition bypass, and the only way to opt a `lod_group=` ladder
out of a compiler-level `auto_partition_max_elements` (which would drop
`coverage_fraction` and break the LOD selector). And below 2 spatial dimensions
the leaf DROPS the request with a warning before it ever resolves the spec, so a
1-dimension scene accepts even a nonsense spec on the flat path; the gates skip
silently there rather than emit a second warning.

A VALID-spec strand of the same shape is closed alongside it, at both doors.
`add_gsplats_from_data(..., additive_lod={…}, partition={"max_elements": 2})`
answered `Could not add gsplats 'child_0': Unknown node attribute 'partition'`
and stranded the `kind=lod` wrapper, because the multi-LOD child writer has no
`partition` parameter. `add_gsplats_from_file("g", <partition of laddered
leaves>, partition={"max_elements": 4})` did the same from inside `part_0`,
leaving a childless `kind=partition` — and that is the most commonly produced
store shape in the whole gsplat pipeline, since `gsplat lod --recipe
tiles|overview|adaptive` and `batch-fit merge --recipe stream` all emit it with
stream ladders on by default. Both are now refused up front, the data door above
its route branch so the two routes say the same thing, the file door in the slot
that already holds its other pre-wrapper gates. Partitioning a ladder is a
feature, not a wording fix.

The refusal names the STRUCTURE and gives each door its own remedy, through one
shared reason builder — the convention `labels_on_wrapper_reason` /
`GRAFT_REMEDY` already keep in the same module. On the `additive_lod=` door it
still says "drop one of the two"; on the file door it names the stored ladder and
points at `gsplat flatten`, because there is no `additive_lod=` in an
`add_gsplats_from_file` call and nothing there to drop.

`partition=False` on those same routes stranded the identical wrappers, from
`Unknown node attribute 'partition'` rather than from a conflict. It is now
DELETED instead, and the calls succeed: `False` is the no-partition bypass, and
writing no partition is exactly what the multi-LOD writer does. The deletion is
scoped to that destination only — `resolve_auto_partition` reads `user_partition
is False` to bypass a compiler-level `auto_partition_max_elements`, so stripping
the key at the adder entry (the way an explicit `None` is stripped, #1496) would
silently re-enable auto-partitioning everywhere else. A multi-substitutive call
keeps the key and hands it to each child, where the same question is asked per
level.

The file door's half of that gate reads the ladder off the STORE, so it also has
to honour the kwarg that empties the store's ladder: an `additive_lod=False` in
the same call is the documented "collapse the ladder" spelling, and
`resolve_additive_axis_gsplats` flattens every level to a single sub-LOD before
the data door asks the same question. Both `add_gsplats_from_file("g", <laddered
leaf>, partition={"max_elements": 4}, additive_lod=False)` and its nested
`kind=partition` twin split into real parts, so the gate skips that spelling
rather than refusing them. Only that spelling: telling a `{"n_lods": 1,
"recompute": True}` that resolves to one rung apart from a `{"n_lods": 2}` needs
the resolved rung count instead of the spec — the same missing query as the graft
residual below.

`core/group/partition.py::is_requested` is the fifth thing this PR de-duplicates:
the `partition is None or partition is False` predicate the new gates need, which
`adders/mesh.py::_requested` already spelled (with the `partition=0` / `0 ==
False` hazard it documents). One predicate rather than two more copies, in a
change whose thesis is that the copies were the bug.

Known and NOT closed: the ladder conflict is checked ABOVE the route branch, so
it outranks the node-attrs gate, the `dim_order` spec check and the
colours/colormap exclusion, where the same call without `additive_lod=` reports
the other fault. Every combination still refuses with an empty store, so only the
naming differs. It is a deliberate trade — the two routes must answer
identically, and only one of them has a pre-wrapper gate to sit in — stated in
the helper's docstring and pinned by
`TestTheLadderConflictOutranksTheOtherPreWrapperFaults`.

Also not closed: one graft shape still strands. The graft gate reads the ladder
off the STORE (`iter_leaves`), so an unladdered nested file grafted with
`partition=` *and* `additive_lod=` — where the ladder is built per part, after
the wrapper — is still refused from inside `part_0` with the childless
`kind=partition` left behind. Closing it needs the resolved rung count, not the
kwarg's presence: `additive_lod={"n_lods": 1}` resolves to a single rung and
takes the flat route, where `partition=` is perfectly legitimate, so a
presence-only check would refuse a valid call. That is a design question of its
own rather than another line in this slot.

The sibling `substitutive_lod=` doors on Points, Lines and Mesh were checked
for the same shape and do not have it: all three refuse `partition=` together
with `substitutive_lod=` outright ("partition-of-substitutive is not
implemented"), before any wrapper exists, so an invalid spec can never be
forwarded into a ladder child there. They do not agree on the `False` spelling —
`add_points`/`add_lines` guard on `substitutive_lod is not None`, so
`substitutive_lod=False` beside a `partition=` is refused there and accepted on
Mesh, which uses the shared `is_requested`. Pre-existing, left alone here rather
than changed as a drive-by: adopting the shared predicate at those two sites
relaxes a user-facing refusal and wants its own tests. That survey covered the
gsplats `lod_group=`/graft doors and those three; it is not a claim about every
adder kwarg that rides into a child.
