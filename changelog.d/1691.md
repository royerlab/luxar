#### One colormap window per gsplat structure — LOD switches no longer re-tone or pop

Every gsplat node derived its own `amplitude_data_range` — the colormap window the
viewer maps amplitudes through — as `[min(a), p99.9(a)]` of *that node's own*
amplitudes. On a lone flat leaf that is exactly right. On anything larger it is a
per-node window over one object, and it showed. A `kind=lod` ladder's coarse level
packs the same total mass into far fewer merged representatives, so its p99.9 sits
~4.5x above the finest level's while its *typical* amplitude only grows ~1.1x: at
every LOD switch the object re-toned through the colormap and popped ~2x in
brightness. A `kind=partition` compounded it — two adjacent tiles of one object were
measured windowed at `[0.40, 4.04]` and `[0.0036, 0.0355]`, a ~100x difference across
a single seam.

Finalize now harmonizes the whole structure. For each maximal `kind=lod` /
`kind=partition` group holding gsplats, one reference window is taken from the finest
content and handed down: LOD levels get it scaled by their **mass-weighted mean
amplitude ratio**, partition parts get it **verbatim**. The two rules were picked by
measurement, not by symmetry. Scored on a rasterized orthographic proxy of the real
colormap render against the finest level, per-level windows gave luminance ratios
0.49 / 0.51 / 0.71 and chromaticity L1 0.187 / 0.183 / 0.100; the mass-weighted
scaling gives 1.04 / 1.01 / 1.00 and 0.048 / 0.028 / 0.028. That estimator also
tracked the swept optimum (1.19/1.10/1.09 predicted vs 1.22/1.06/1.06 measured) where
the p99.9 the window itself uses did not at all (4.51/3.95/2.36). For a partition the
answer is the opposite: parts are disjoint spatial pieces of one object with no
representation change between them, so there is nothing to normalize away — a dim
tile really is dim. Per-part windows scored luminance 0.62 / chroma 0.123 with a 5.6x
spread in window tops; one shared window scored 1.00 / 0.0001.

A partition's own reference is pooled from its parts: the exact union minimum for the
bottom, and the **count-weighted mean of the part tops** (weights = each part's splat
count) for the top. Not their max — each part's top is that part's own p99.9, so the
max of N of them climbs with N toward the global maximum p99.9 exists to avoid (1.14x
the union's true p99.9 at 16 parts, 1.58x at 256, 3.40x at 5000, and 1551x for 60 dim
tiles plus one small bright one, which renders the whole object black; the batch-fit
streaming merge routinely writes thousands of parts). The weighted mean's expectation
does not move with the part count; the honest cost is that a part whose own top sits
far above the shared window clips more than its own brightest 0.1% — exactly what a
flat store of the same splats does to that same content. And the reference LOD child
is the finest one that actually has a window, not necessarily the literal finest: a
`substitutive_lod` Points/Lines ladder and a scalar-amplitude level both put an
un-windowed node there, which used to leave the whole structure alone.

To make that computable, each written splat set now carries two cheap O(N)
statistics: `amplitude_mass` (`Σ aᵢ·|Σᵢ|^½`, the integral mass this codebase already
ranks LOD ladders by) and `amplitude_mass_weighted_mean` (`Σ aᵢ²·|Σᵢ|^½ / Σ aᵢ·|Σᵢ|^½`
— total self-energy over total mass, i.e. the amplitude a unit of mass typically
carries). Both use the RAW amplitudes, since that is the scalar the window applies
to. An additive ladder's parent aggregates them over its sub-LODs. These two are
format-additive: an older reader ignores them, and a store that lacks them shares the
reference window verbatim instead of being scaled.

The level ratio is bounded to `[1/10, 10]`, mirroring the analogous mass rescale in
`gsplats/lod/substitutive.py`: the real ratios are ~1.1-1.2, `mwma` is a second-moment
ratio and so not robust on heavy-tailed amplitudes, and a 10x window rescale would be
a larger switch pop than the ~2x defect being fixed. Out of bounds, the level shares
the window verbatim and says so.

This is producer-side only: no viewer change, and the `amplitude_data_range` attr set
is unchanged — the pass only ever **overwrites** a window a writer already stamped,
never creates one, and refuses to write anything that is not a finite `lo < hi`. It
runs in `LuxarZarrCompiler.finalize()` and in both standalone `.gsplats.zarr` writers,
before the content hash is stamped — so `gsplat lod` / `fit` / `convert`, the scene
graft, and the batch-fit streaming merge all get it.
