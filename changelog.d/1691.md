#### One colormap window per gsplat structure — LOD switches no longer re-tone or pop

Every gsplat node derived its own `amplitude_data_range` — the colormap window the
viewer maps amplitudes through — as `[min(a), p99.9(a)]` of *that node's own*
amplitudes. On a lone flat leaf that is exactly right. On anything larger it is a
per-node window over one object, and it showed. A `kind=lod` ladder's coarse level
packs the same total mass into far fewer merged representatives, so its p99.9 sits
~4.5x above the finest level's while its *typical* amplitude only grows ~1.1x: at
every LOD switch the object re-toned through the colormap and popped ~2x in
brightness. A `kind=partition` compounded it — two adjacent tiles of one object were
measured windowed at `[0.40, 4.04]` and `[0.0036, 0.0355]`, a ~100x difference across
a single seam.

Finalize now harmonizes the whole structure. For each maximal `kind=lod` /
`kind=partition` group holding gsplats, one reference window is taken from the finest
content and handed down: LOD levels get it scaled by their **mass-weighted mean
amplitude ratio**, partition parts get it **verbatim**. The two rules were picked by
measurement, not by symmetry. Scored on a rasterized orthographic proxy of the real
colormap render against the finest level, per-level windows gave luminance ratios
0.49 / 0.51 / 0.71 and chromaticity L1 0.187 / 0.183 / 0.100; the mass-weighted
scaling gives 1.04 / 1.01 / 1.00 and 0.048 / 0.028 / 0.028. That estimator also
tracked the swept optimum (1.19/1.10/1.09 predicted vs 1.22/1.06/1.06 measured) where
the p99.9 the window itself uses did not at all (4.51/3.95/2.36). For a partition the
answer is the opposite: parts are disjoint spatial pieces of one object with no
representation change between them, so there is nothing to normalize away — a dim
tile really is dim. Per-part windows scored luminance 0.62 / chroma 0.123 with a 5.6x
spread in window tops; one shared window scored 1.00 / 0.0001.

A partition's own reference is pooled from its parts: the exact union minimum for the
bottom, and the **count-weighted mean of the part tops** (weights = each part's splat
count) for the top. Both candidate rules are biased, in opposite directions, and
neither recovers the union's true p99.9. `max` over part tops drifts upward without
bound in the part count — 1.05x the union's true p99.9 at 2 parts, 1.58x at 256, 3.40x
at 5000, and ~1500x for 60 dim tiles plus one small bright one, at which point the
whole object renders black — and the batch-fit streaming merge routinely writes
thousands of parts. The count-weighted mean is biased slightly low instead, because a
part's own p99.9 already under-estimates the union's. It wins on two counts: its bias
does not grow with the part count, and its failure mode is the recoverable one —
clipping outlier-bright content, which is exactly what a p99.9 window does by design.
It is not unbiased and not a consistent estimator of what a flat store would derive;
it is the better-behaved of two biased choices.

The reference LOD child is the finest one that actually carries a *usable* window
(`hi > lo`), not necessarily the literal finest. Three shipped shapes put an
un-windowable node there: a `substitutive_lod` Points/Lines ladder, a scalar-amplitude
level, and — the one that bites hardest — a constant-amplitude level, which the writer
windows as the degenerate `[x, x]`. `gsplats/interop` gives *every* imported classical
splat file (INRIA PLY, `.splat`, SPZ, SuperSplat) `amplitudes = 1`, so
`gsplat import` → `gsplat lod --recipe levels` produced exactly that, and the pass
would then have refused every write and left the ladder on its per-level windows with
no diagnostic. A degenerate top is likewise excluded from the partition pool (its `lo`
still counts toward the union minimum): admitted at full weight, a 100 000-splat
`[1.0, 1.0]` part next to a 1 000-splat `[0.01, 50.0]` pooled to `[0.01, 1.49]`,
over-brightening the second part 34x.

To make that computable, each written splat set now carries two cheap O(N)
statistics: `amplitude_mass` (`Σ aᵢ·|Σᵢ|^½`, the integral mass this codebase already
ranks LOD ladders by) and `amplitude_mass_weighted_mean` (`Σ aᵢ²·|Σᵢ|^½ / Σ aᵢ·|Σᵢ|^½`
— total self-energy over total mass, i.e. the amplitude a unit of mass typically
carries). Both use the RAW amplitudes, since that is the scalar the window applies
to. An additive ladder's parent aggregates them over its sub-LODs. They are stamped
unconditionally — a mass-less set gets `0.0` / `0.0` — because "present and zero" and
"absent" have to stay distinguishable: absence is how the pass recognises a legacy
store. These two are format-additive: an older reader ignores them, and a store that
lacks them shares the reference window verbatim instead of being scaled. That fallback
is not provably better than the self-consistent per-level windows it replaces — it can
clip a legacy sibling — but it is the honest answer with no ratio to scale by, and it
puts the structure on one window, which is what the partition arm does anyway.

The level ratio is clamped into `[1/10, 10]`, mirroring the analogous mass rescale in
`gsplats/lod/substitutive.py`: the real ratios are ~1.1-1.2, `mwma` is a second-moment
ratio and so not robust on heavy-tailed amplitudes, and a 10x window rescale would be
a larger switch pop than the ~2x defect being fixed. Out of bounds the ratio is
clamped rather than thrown away — discarding it applies the *full* uncorrected error
(at a genuine ratio of 0.02, scale 1.0 leaves the level windowed 50x too wide and it
renders black, where clamping to 0.1 caps that at 5x) — and each harmonized structure
reports its clamps in one rolled-up line rather than one per level.

This is producer-side only: no viewer change, and the `amplitude_data_range` attr set
is unchanged — the pass only ever **overwrites** a window a writer already stamped,
never creates one, and refuses to write anything that is not a finite `lo < hi`. It
runs in `LuxarZarrCompiler.finalize()` and in both standalone `.gsplats.zarr` writers,
before the content hash is stamped — so `gsplat lod` / `fit` / `convert`, the scene
graft, and the batch-fit streaming merge all get it. One knock-on worth knowing: a
`levels` structure's reference top is a real p99.9 while an `overview` / `adaptive`
one is a pooled estimate, so the same splats can tone slightly differently depending
on the topology they were written in (measured 222.34 vs 160.50 on one dataset).
