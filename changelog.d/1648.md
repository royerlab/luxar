#### Adaptive DPR now acts in the regime it was built for

Adaptive resolution was structurally inert below about 2.9 fps — exactly the regime a
software rasterizer (headless Chromium's SwiftShader, a machine without a usable GPU)
puts a heavy gsplat scene into. Two mechanisms conspired. The frame-gap reset, meant to
throw away a one-off stall (a GC pause, a synchronous decode, an idle resume) before it
poisons an otherwise-healthy window, fired on _every_ frame once every interval exceeded
its 350 ms threshold, clearing the sample window and pushing the evaluation clock forward
so the control loop never ran at all. And the 1-second sliding window dropped the previous
frame as too old before the next one arrived, leaving a single sample and an undefined
frame rate. A measured 116-second episode at 0.48 fps rendered at full native pixel ratio
from beginning to end.

A long interval is now classified by comparison rather than by an absolute threshold: it
is dead time only if it clears the 350 ms floor _and_ is at least four times the median of
the recent inter-frame intervals. A 5-second gap in a 60 fps stream is a 300× outlier and
is still thrown away; a 2-second interval in a stream whose recent intervals are all
around 2 seconds is simply the frame rate, and its samples are kept so the manager scales
down. The cadence memory survives the reset it triggers, which is what makes it converge —
a scene that genuinely slows down costs one or two misread intervals before adaptation
resumes — and is cleared only where the frame stream itself breaks (display change, pause,
disable). A scene-content change is deliberately not one of those: frames keep arriving at
the rate they were arriving at, and a cold memory falls back to the absolute threshold
alone, which misreads the very next ordinary interval of a slow loop as dead time — which
in turn threw the freshly restarted window away a second time and voided the probe in
flight. With per-frame LOD churn at half a frame per second the pixel ratio used to walk
unratified from 2.0 down to the floor of 0.5 without ever learning anything; it now settles
at 1.8 with a measured floor, as it does without the churn. The window's retention floor keeps two samples regardless of age, so the
estimate stays defined slower than the window itself.

Behaviour at healthy frame rates is unchanged, and an isolated long stall — one, or up to
two in a row — is still discarded outright. The third in a row is the median of the
five-interval memory, so it is absorbed as the frame rate; there is no way to tell the two
apart from timestamps alone, since three five-second gaps in a row genuinely is a fifth of
a frame per second for fifteen seconds. A cadence that has only just been reclassified is
therefore untrusted for a couple of intervals: the reduction still applies, because fewer
pixels never hurt a stuttering loop, but nothing is learned from a window that may hold
nothing but dead time. A stall burst in a healthy session now costs a transient ten percent
and lifts again, where before it pinned a learned floor with exponential backoff onto a
session that was rendering at sixty frames a second either side of it.

The rule sees only inter-frame intervals, so one pattern still escapes it: a dead period
alternating one-for-one with a single fast frame makes the dead intervals the majority of
the memory, so they become the median and are kept as the frame rate, and a window landing
on the fast frame reads as healthy even though the user perceives about one frame every two
seconds. Two or more fast frames between dead periods fail the other way — the median stays
fast, the dead time is correctly discarded every cycle, and the window simply never
accumulates.
