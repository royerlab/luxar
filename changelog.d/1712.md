#### Recording: correct frame edges, an honest encode script, and capture sizes an encoder accepts

The `geq` filter that re-applies the viewer's grade to an EXR sequence was sampling with
ffmpeg's default bilinear interpolation, which clamps the sample coordinate to
[0, w−2] × [0, h−2]. The rightmost column and the bottom row of every frame therefore came
out as copies of their neighbours: on an 8×2 float frame under an identity expression, a
last column of 1.0 read back as 0.6. The expressions only ever read integer X, Y, so every
`geq` in the generated script now asks for `interpolation=nearest`, which is both exact and
cheaper.

The exposure/offset/gamma block now always emits the shader's `max(…, 0)`. It used to be
emitted only alongside a non-zero offset, which left a negative component in a scene-linear
EXR free to run through the tone curve the viewer never applied it to — Reinhard maps −2 to
+2, so a black pixel encoded as white. The cost warning in the script header was also
describing the wrong thing: it quoted wall-clock figures as if `geq` ran on one core, when
the filter is slice-threaded. It now gives CPU time (~2.9 s/frame at 720p, ~7.5 s at 1080p,
~35 s at 4K) alongside the measured wall clock for the 1080p chain (~0.73 s/frame on 16
threads), rather than a divide-by-your-cores rule the measurements do not support.

The header also no longer promises that "the video matches what you saw" unless the chain
really carries the viewer's curve. It used to make that promise whenever the grade was
readable, which put it six lines above the NOTE explaining that AgX has no closed form and
degrades to a plain clamp. The exposure/offset/gamma and tone-mapping lines are still
printed for AgX — they are worth reading, and they _are_ applied — under a lead-in that
only claims the grade.

When the viewer's grade cannot be read at all, the script says the frames are "only clamped
and sRGB-encoded" — and now that is actually what happens. That branch previously emitted no
`geq`, so nothing clamped the linear floats before the transfer conversion and over-range
values were clipped per channel after the RGB→YUV matrix instead: a linear (100, 0.5, 0.5)
pixel came out (255, 237, 7) where clamping first gives (254, 186, 186). No shipped code
path reaches that branch today — `PostProcessingManager` always answers
`getGradeSettings()` — so it is the defensive fallback that is now honest rather than a
user-visible failure that was fixed.

HTML overlays are composited through `XMLSerializer` rather than `outerHTML`. The markup
goes into an `image/svg+xml` data URL, which the browser parses as XML, and HTML
serialization leaves void elements unclosed — a single `<br>`, which the overlay allowlist
permits and several demos use, was a fatal well-formedness error, so the image never loaded
and the overlay was missing from every captured frame. Wrapped overlay text no longer
treats `\n` as a line break either: the overlays this path can see are laid out
`white-space: normal`, where a newline collapses to a space, so honouring it broke lines the
DOM does not and a trailing newline lifted a bottom-anchored overlay by a whole line.

Finally, capture resolution. Offline captures were truncating the target height to a
multiple of 16, so the menu entry labelled 1080p recorded 1072 lines and "Native" recorded
neither the canvas size nor anything the tooltip claimed. Multiples of 16 were never the
requirement: H.264/H.265 with yuv420p need _even_ dimensions, and encoders pad to their own
macroblock size internally. The requested height is now walked down until the PHYSICAL frame
is even — the frames on disk are the SSAA-multiplied render size, not the size asked for —
and the width is derived from the aligned height, so the framing the user set is preserved.
A 3024×1698 Native target at SSAA 1.5× captured at 4536×2547, and x265 refuses an odd height
outright ("Picture height must be an integer multiple of the specified chroma subsampling"),
writing a 0-byte file after the user had already downloaded a multi-gigabyte ZIP. Only the
product has to be even, so the walk steps by one pixel rather than two; requiring the
request to be even as well threw away half the candidates and cost far more than a factor of
two, which is how a legal 1.05× multiplier ended up shipping 1700 → an odd 1785 — six even
steps from an answer the unit walk finds in one.

That capture size is now read from `PostProcessingManager.getDisplaySize()` instead of
`renderer.getSize()`. The two are not the same number: post-processing hands the renderer the
SSAA-multiplied size and stamps the display size on the canvas CSS, while `resize()` takes a
display size and applies the multiplier itself. So under SSAA the multiplier was being
squared. "Native" on a 1512×850 canvas at DPR 2 with 2× SSAA asked for a 12096×6800 render
target — four times the pixels of the canvas the option's own tooltip promises, and ~1.3 GB
of float per EXR readback, which in practice means a lost context part-way through the
capture. The same read is what the session snapshots and restores around _any_ capture, so a
recording used to leave the viewer at twice its size, compounding on the next one.
