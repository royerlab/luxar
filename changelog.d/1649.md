#### The library build's entry chunk can find its WASM shim (#1649)

`initWasm` resolved the wasm-bindgen JS shim with a single bundle-relative
literal, `new URL('../wasm/luxar_wasm.js', import.meta.url)`. That literal is
correct for three of the four chunks that carry the loader and wrong for the
fourth. The compiled artifact always lands in a `wasm/` directory at the output
root, while the chunk carrying the loader sits at one of two depths: the app
build emits `dist/assets/index-*.js` alongside `dist/assets/data-worker-*.js`
and `dist/assets/sort-worker-*.js`, all one level below `dist/wasm/`, but the
library build emits its ENTRY chunk at `dist/lib/luxar-viewer.js` — the output
root itself, where `../wasm/…` climbs out of `dist/lib/` and lands on a
`dist/wasm/` that does not exist.

The consequence was invisible rather than loud. An embedder consuming the
published package unbundled (a CDN, or a served `node_modules`) without passing
`LuxarAppOptions.wasmPath` got compiled kernels in the data and sort workers,
whose chunks resolve correctly, and a silent `TypeScriptFallback` on the main
thread — which since the in-process Points projection landed is a path that
matters. `module-overrides.ts` only applies `wasmPath` when it is truthy, so
nothing downstream corrected the default.

One literal cannot serve both depths, so the loader now tries an ordered list:
`../wasm/luxar_wasm.js` first, then `./wasm/luxar_wasm.js`. The order is the
point — every hot path resolves on the first entry, so the app build and both
worker chunks still cost exactly one request and only the library entry chunk
pays a failed import before finding its shim. Only the IMPORT is retried: once a
candidate's module loads, initialization and the staleness check run against
that module alone, because re-running them elsewhere risks instantiating the
binary twice and would mask a genuinely stale artifact behind the next
candidate's 404. When every candidate fails, the last error is rethrown intact
so the documented TypeScript fallback still logs a real cause.

The resolution is a pure exported helper (`wasmShimCandidateUrls`) so the two
real depths are pinned in a unit test, ordering included. `check-lib-exports`
gains a built-layout assertion in the same spirit: it walks every `.js` under
`dist/lib`, and for any chunk that spells out a bundle-relative shim specifier
it requires at least one of them to resolve, from that chunk's own directory, to
a file that exists. That check earns its keep because `build:lib` is not run by
PR CI at all — this script, invoked from `pnpm build:lib:check`, is the only
place the shipped layout is ever inspected. It strips block comments before
scanning and accepts only quoted string literals, since the unminified library
bundle ships the loader's own JSDoc verbatim and prose naming the path would
otherwise satisfy a naive grep.
