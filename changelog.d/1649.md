#### The library build's entry chunk can find its WASM shim (#1649)

`initWasm` resolved the wasm-bindgen JS shim with a single bundle-relative
literal, `new URL('../wasm/luxar_wasm.js', import.meta.url)`. Six chunks carry
the loader, and that literal is correct for five of them and wrong for the
sixth. The compiled artifact always lands in a `wasm/` directory at the output
root, while the chunk carrying the loader sits at one of two depths: the app
build emits `dist/assets/index-*.js` alongside `dist/assets/data-worker-*.js`
and `dist/assets/sort-worker-*.js`, and the library build emits
`dist/lib/assets/data-worker-*.js` and `dist/lib/assets/sort-worker-*.js` — all
five one level below their build's `wasm/` — but the library build emits its
ENTRY chunk at `dist/lib/luxar-viewer.js`, the output root itself, where
`../wasm/…` climbs out of `dist/lib/` and lands on a `dist/wasm/` that does not
exist.

The consequence was invisible rather than loud. An embedder consuming the
published package unbundled (a CDN, or a served `node_modules`) without passing
`LuxarAppOptions.wasmPath` got compiled kernels in the data and sort workers,
whose chunks resolve correctly, and a silent `TypeScriptFallback` on the main
thread — which since the in-process Points projection landed is a path that
matters. `module-overrides.ts` only applies `wasmPath` when it is truthy, so
nothing downstream corrected the default.

One literal cannot serve both depths, so the loader now tries an ordered list:
`../wasm/luxar_wasm.js` first, then `./wasm/luxar_wasm.js`. The order is the
point — every hot path resolves on the first entry, so the app build and all
four worker chunks still cost exactly one request and only the library entry
chunk pays a failed import before finding its shim. A candidate only counts as a
hit if it exposes a callable `default`: a host that answers the entry chunk's
404 with a JS-typed SPA fallback page returns a module that imports fine and
then throws on `default()`, which would reproduce the original symptom on that
host class. The shape check reads a property and instantiates nothing, so the
commit-to-the-winner rule stands: once a candidate wins, initialization and the
staleness check run against that module alone, because re-running them elsewhere
risks instantiating the binary twice and would mask a genuinely stale artifact
behind the next candidate's 404. Failures are attributed per candidate — a
single-URL attempt (an explicit `wasmPath`, or the dev server) rethrows its own
error untouched, while a multi-candidate walk throws an `AggregateError` naming
every URL in order, so a real failure on candidate 1 (shim served as
`text/plain`, blocked by CSP, corrupt) is no longer reported as a 404 on a
phantom `dist/assets/wasm/` directory that exists in no layout.

Both halves are exported and unit-tested: `wasmShimCandidateUrls` pins the two
real depths, ordering included, and `importFirstWasmShim` takes the dynamic
importer as a parameter so the candidate walk itself — try order, short-circuit,
fall-through on a rejection and on a `default`-less module, and the error
attribution — is exercised with a stub. That injection is what makes the loop
testable at all: `import.meta.env.DEV` is true under vitest, so every in-suite
`initWasm()` takes the single-candidate dev-server branch and never reaches the
list. `check-lib-exports` gains a built-layout assertion in the same spirit: it
walks every `.js` under `dist/lib`, and for any chunk that spells out a
bundle-relative shim specifier it requires at least one of them to resolve, from
that chunk's own directory, to a file that exists inside the published tree. It
strips comments before scanning and accepts only quoted string literals, since
the unminified library bundle ships the loader's own JSDoc verbatim and prose
naming the path would otherwise satisfy a naive grep — and because that makes it
a text-level check that could quietly self-disable, the entry chunk is
additionally required to name at least one specifier. The ordinary
typescript-tests job does not build the library; `build:lib` runs in the
`release-readiness` job (and in `publish-npm.yml` on a tag), and this script is
the only thing that inspects the shipped layout there.
