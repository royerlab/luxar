#### `content_hash` now covers storage layout and encoding, not just values (#1718)

`content_hash` is the token the viewer's `MultiLevelCachingStore` compares against
the remote to decide whether a cached dataset is still valid, and that cache holds
**encoded chunks keyed by chunk index**. What a chunk index addresses is a function
of the chunk shape — so two stores holding byte-identical values under different
chunk shapes are not interchangeable, and until now they hashed EQUAL. As reported
in #1718, re-chunking a compiled scene left its `content_hash` untouched, so a
client holding a cached copy of the original would have served those chunks for
the re-chunked store at every key. Two smaller omissions fell out of the same
loop: array NAMES were not hashed (a renamed array was invisible), and neither was
SHAPE (`tobytes()` of a `(2, 3)` and a `(3, 2)` array holding the same values is
identical, so a reshape was invisible).

Both implementations of that token now fold an array's storage identity into the
hash: `name`, `shape`, `chunks`, `dtype`, the shard shape (`None` when unsharded,
folded in unconditionally so its presence is stable) and the array's codec **ids**
in encode-pipeline order. That happens in `compute_content_hashes` (the compiler's
finalize pass, which also keeps hashing the decoded values) and in
`_stamp_content_hash` (the metadata-only variant the gsplats writers,
`gsplat annotate-quality` and `gsplat doctor --fix` use, which must never read
array data). All of it comes from metadata already in hand, so there is no extra
I/O. The two remain separate digests over different serializations and are never
compared with each other; they simply now agree that chunk/shard layout and codec
identity are part of a store's identity. Folding it into the metadata-only variant
matters less for today's callers than for tomorrow's: neither in-place re-stamper
can currently change layout (every mutation on those paths is attrs-only), but a
future in-place re-layout tool must not be able to re-stamp a store to its input's
digest — and the two digests should agree on what identity means regardless.

The codec ids are derived at **both** on-disk formats. Format 3 lists its pipeline
under one `codecs` member; format 2 holds the same information under `filters` plus
`compressor`, and folding only the format-3 spelling would have left the very
defect this entry describes standing at format 2 — where three arrays identical in
values, shape and chunks but written raw / Blosc-zstd / GZip all hashed the same.
Luxar writes format 2 on demand (`LUXAR_ZARR_FORMAT=2`) and re-finalizes legacy v2
stores, so a mixed-format tree is the normal steady state. Both formats contribute
**ids** rather than full codec settings: an id list catches a raw↔compressed switch
and a codec-family switch (blosc↔gzip), each of which changes what the stored bytes
at an unchanged chunk key mean, while a pure tuning change (a blosc `clevel`, a
gzip `level`) leaves the ids — and so the hash — alone instead of churning every
store's digest. That exclusion is sound rather than merely pragmatic: blosc/gzip/
zstd streams are self-describing (cached bytes decode correctly against metadata
announcing different settings), and the one Luxar codec whose settings *are*
load-bearing, `luxar_delta_v1`, derives its `cols`/`bits` from the array's column
count and dtype itemsize, both already hashed. Both directions are pinned by tests.

The one place the full pipeline is folded in is a SHARDED array in
`compute_content_hashes`: there a chunk key addresses a shard, and everything that
decides what its bytes mean — inner `chunk_shape`, inner `codecs`, `index_codecs`,
`index_location` — sits nested inside the single top-level `ShardingCodec`, behind
an id list that would read only `["sharding_indexed"]`. Nothing in Luxar emits a
sharded store today, so a test that varies only the inner compressor is what keeps
that fold honest.

Also closed, an adjacent blind spot of the same function found in review: each
array's **own** `attrs` were hashed by neither implementation. That is where Luxar
keeps every array's dequantization parameters — `/amplitudes` carries an
`encoding` document with the quantization `min`/`max`, `/centers` a per-channel
`col_lo`/`col_hi`, a `broadcasted` array its `n_elements` — so those attrs are what
turn the stored ints back into scientific values. Mutating a single `min` shifted
the decoded float of every splat and moved neither digest; a `broadcasted`
`n_elements` even changes the decoded *length*, which the value-hashing compiler
variant could not see either. Each array's attrs now contribute one term, sorted
and serialized the same deterministic way the group attrs already were. Nothing
writes an array attr after the stamp (finalize's back-fills touch group attrs only,
and all of them run before the hash), so the input is stable.

The accepted consequence: changing the hash inputs changes every existing store's
hash **on its next write**. A client holding an L2/OPFS cache for a dataset that
gets re-finalized will see the hash change, invalidate, and re-download once —
which is exactly the behaviour the token exists for, and it happens one time per
dataset. Nothing rewrites hashes for stores already on disk: an un-touched store
keeps the hash it was written with until something re-finalizes it, so old and new
stores coexist without a migration.
