#### The Layers panel windows each LOD level on its own scalar range (#1753)

The panel has one display-range slider per layer, so it composes one window —
but `LayerApplyEngine.applyComposed` fans that window out over
`collectDataDescendants`, and a layer is very often a `kind=lod` wrapper whose
levels do not share a scalar range. gsplat LOD merging SUMS amplitudes, so a
coarsened level is the same physical signal at a different numeric SCALE, and
the gsplat compiler
(`packages/luxar/src/luxar/io/_compiler/gsplat_assembly.py`) derives
`amplitude_data_range = [min, p99.9]` independently from each splat set's OWN
amplitudes. The layer's reference range is merely whichever descendant
`deriveScalarRangeFromDescendants` picked — the one with the largest `n_splats`,
or, when no descendant declares one (points, lines and mesh write `n_points` and
never `n_splats`) or several tie, simply the first visited. The composed window
went into every level verbatim, so the whole layer rendered on the reference
level's window and every per-level window the producer had stamped was
discarded.

Two things made that worse than a one-off interaction bug. It happened **on
load** — `layers-panel.ts` runs `applyDisplayRange` for every layer while
building the panel — and `applyOpacity` / `applyGamma` / `applyAbsorption` /
`applyBlendingMode` / `applyColormap` all funnel through the same
`applyComposed` afterwards. And a level created lazily AFTER the last commit kept
its own window until the next one, so two levels of the same object could be
windowed differently depending only on load order.

A colormap-active leaf under a LOD ladder now receives the layer's window
re-expressed in its own `scalar_data_range` / `amplitude_data_range`, with the
window's relative position inside the range preserved: the middle 40% of the
layer's signal stays the middle 40% of each level's signal, which is what the
slider means to the user. The per-level window scaling proposed in #1752 (still
in flight) needs exactly this to reach the screen — until now the panel flattened
any per-level window differentiation before it got there.

The remap crosses a LOD ladder and nothing else: every group node from the edited
layer down to the leaf must be `kind === 'lod'`. A partition's parts are disjoint
SPATIAL subsets of one field at the SAME scale, differing only by content, so a
per-part window would be per-tile auto-contrast — the same value rendering as a
different colour in different tiles, with a visible discontinuity at every BSP
seam. (On the repo's own `test_partition_layer.luxar.zarr` fixture the two tiles
are `[0.5000, 0.7455]` and `[0.7542, 0.9998]`, so the field would step white →
black across the seam.) So an `overview` tree remaps its coarse cap and declines
under its nested partition branch; `adaptive` declines throughout, because the
right reference for a tile's ladder is that tile's own finest level rather than
the layer's, and that is more than #1753 asks for; and a plain `layer=True` group
over two colormapped channels declines too, since two physical fields are not one
field at two scales. Once #1691 / PR #1752 harmonizes `amplitude_data_range`
across a gsplat structure, partition siblings will carry equal ranges and the
equality short-circuit would make this a no-op anyway; the `kind` gate is the
safety net until then, and for every store already written.

Mesh ladders never reach any of this, and the reason is the PRODUCER's rather
than the panel's: `core/group/adders/mesh.py::_shared_scalar_window` derives one
window from the whole field before any split or decimation and stamps it on every
part and every level, precisely so "a level or a part that stamps its own subset
min/max" cannot render the same value as a different colour. Mesh siblings
therefore have equal ranges and the equality short-circuit fires. That is also
what makes gsplat LOD the principled exception rather than an inconsistency: mesh
decimation drops vertices without touching the scalars they carry, while gsplat
LOD merging changes the amplitude scale — and only a scale change is something a
window has to be re-expressed across.

The remap is a pure helper (`rendering/display-range.ts::remapWindowToLeafRange`,
beside the `computeUniforms` / `computeDisplayRange` / `resolveColormapWindow`
math it belongs with) and it declines to fire in four cases, each of which would
otherwise produce a _different_ window rather than a refined one. Either range
missing: nothing to map between. Either range non-remappable — degenerate,
inverted, or non-finite. `[x, x]` is legitimate and common (every imported
classical splat file has `amplitudes = 1`); the width floor is the shared
`DEGENERATE_SCALAR_RANGE_EPS`, because below it the two ends of the pipeline have
already collapsed — `computeUniforms` answers a sub-eps span with the identity
gain, so the composed window is `[0, 1]` and not the reference window at all,
while on the leaf side `computeScalarRangeUniforms` answers a sub-eps span with
the LUT MIDPOINT (#631), i.e. one flat neutral colour for every element of that
leaf. Finiteness is a separate arm: `[0, Infinity]` passes any width test and
then `0 × Infinity` sends a NaN window to the shader. The predicate rejects a
NaN-bearing range for free. And the two ranges being equal, which is the
overwhelmingly common case (the finest level IS the reference, and so is every
leaf of an ordinary single-range layer) — short-circuited so an untouched layer's
window stays bit-exact instead of round-tripping through two floating-point
divisions.

The remap also runs only when the composed window really is STATED in the
reference range. `composeEffective` multiplies `intensity` and sums `offset` over
the whole ancestry with live panel state substituted for `layer=true` nodes, so
a window contributed at or below the edited layer leaves the composed one in a
different basis, and remapping it would corrupt a window that was already
correct. `LayerApplyEngine.composedWindowIsInReferenceBasis` declines in four
shapes: the edited layer is off the leaf's ancestry; the edited layer itself
AUTHORED a gain (`layer=True, intensity=0.5` on a wrapper makes `walkSceneGraph`
seed `displayMin/Max` from `computeDisplayRange(0.5, 0)`, a normalized-gain
window with no relation to `scalarDataRange`); a node strictly BELOW the layer is
itself tracked as a LAYER — regardless of its gain, since it owns its own window
and its own panel row (a gain test was a false negative for any nested child
whose range is exactly `[0, 1]`, where `computeUniforms(0, 1)` is the identity
`{1, -0}` and `[0, 1]` is the ordinary range of a normalized scalar, probability
or mask); or a non-layer node below the layer authored an `intensity`, which
mirrors `resolveColormapWindow`'s "non-identity raw leaf gain ⇒ the composed gain
IS the window" rule. A gain on an ancestor ABOVE the layer is deliberately not
gated: it composes so the panel lands on exactly the window the node factory
computes at creation, and that agreement is now pinned by a test.

The ancestry chain is walked ONCE per leaf and shared between the composition and
the gate. `collectAncestorNodes` resolves each step with a linear `children.find`
that allocates a string per comparison, so a fan-out over a P-part wrapper costs
~P²/2 comparisons — 7.0 ms at 512 parts, 129 ms at 2000 — and `applyComposed`
runs on every slider tick. Walking it twice would have doubled that.

Nothing else moved. The direct-colour gain/offset route is unchanged, the #936
identity reset on the colour GOG still fires on the colormap path, and the
`identityLayerWindow` route for a mixed direct-colour/colormapped group is
untouched — it only ever fires for a leaf that is NOT colormap-active, so it
cannot overlap the new remap. `applyColormap`'s own `updateScalarRange` write now
goes through the same per-leaf helper: it is immediately superseded by the
`applyComposed` call at the end of that method, but two places pushing a window
by different rules is a trap for the next reader.
