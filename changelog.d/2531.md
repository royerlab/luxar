#### Wheel input is normalized across browsers

`WheelEvent.deltaY` only means something alongside `deltaMode`, and the viewer read
it as if it were always pixels. Chromium and WebKit report one notch as
`deltaMode = 0` with `deltaY = 100`; Firefox reports the same notch as
`deltaMode = 1` (lines) with `deltaY = 3`. Every wheel path that consumes the
magnitude therefore ran about 32x weaker there: wheel zoom moved 0.15% of the
distance to the target per notch instead of 5%, which in practice felt like a dead
wheel, and Ctrl+wheel FOV was off by the same factor at 0.15 degrees per notch
instead of 5. Shift+wheel view-axis roll had it too.

The three magnitude-consuming entry points — orbit/ortho wheel zoom, Shift+wheel
roll, Ctrl/Cmd+wheel FOV — now convert the delta to a pixel equivalent first, with
a line worth 16 px and a page worth the canvas's own height (falling back to a
nominal 800 px for an element that has not been laid out yet). Pixel-mode events
pass through verbatim and unclamped, so Chromium and WebKit behaviour is exactly
what it was and neither the per-scene Zoom Speed nor the global Zoom Sensitivity
needed re-tuning; a fast trackpad fling still arrives whole. Only the converted
line and page deltas are capped, at 200 px — two Chromium notches, the largest
single step worth allowing — so a page-mode event on a tall canvas or a driver
reporting an absurd line count cannot produce one enormous jump. Firefox's ordinary
3-line notch lands at 48 px, nowhere near that cap.

Normalization sits at the wheel handlers, not inside the zoom math, which is shared
with pointer-drag dolly — those deltas are real screen pixels and must stay raw. Fly
controls take only the sign of the wheel delta and are unaffected; the comment there
claiming to "normalize deltaY across browsers" was the mislabel that let this sit
unnoticed, and now says what it actually does.
