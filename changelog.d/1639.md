#### The debug snapshot reports a real `isLoading`, so the E2E data waits gate on something

`window.__luxarDebug.getState()` never carried a loading flag, and the E2E
helpers in `src/tests/e2e/helpers.ts` have always read `state.isLoading` — in
eight places (`waitForDataLoaded`, `waitForDimensionNavigation`,
`waitForSpatialQuery`, `waitForSpatialQueryOrThrow`,
`waitForNavigationComplete`, `waitForNavigationCompleteOrThrow`, and the
state-based fallbacks inside `waitForRenderStable` and `waitForNextRender`),
plus `real-dataset-loading.spec.ts` and the two capture specs under
`src/tests/screenshots/`. `!undefined` is `true`, so `waitForDataLoaded`,
`waitForDimensionNavigation` and both spatial-query waits resolved the instant
`getState()` returned an object: they waited for the debug interface to exist
and for nothing else. `waitForNavigationComplete` first waits for
`typeof isLoading === 'boolean'`, which could never become true, so it took its
catch branch and degraded to a fixed 300 ms sleep on every call — the silent
variant several specs deliberately prefer, blaming flaky keyboard events.
`waitForNavigationCompleteOrThrow` requires `isLoading === false` strictly and
could therefore only ever time out, which is why it has no callers.

The snapshot now carries `isLoading`, sourced from
`SceneLoaderManager.isAnyLoadPassInProgress()` — true while a sweep for the
requested view is outstanding on *any* registered loader rather than only the
default one, because the manager's contract admits several and the default is
merely one elected entry. It is read inside the `getState` closure, per snapshot,
so a load that starts after the debug interface was installed is visible.
`computeDebugState` takes it as a parameter alongside `isAnimating` and
`initialized`, keeping that helper free of singleton lookups.

"Outstanding" is the running `updateView` sweep (fetch/decode/upload) up to its
geometry commit, minus the progressive-LOD refinement drain, plus a view-state
that is queued and has not started loading yet. The refinement subtraction comes
first: that drain does not take the serialization lock, it inherits it — the
update tail and the post-load kick hand `_updateInProgress` straight to the
refinement orchestrator, whose last phase releases it once every additive ladder
has emptied. Folding it in would make the flag report full-ladder latency
instead of first-commit latency, the same distinction
`update-view/queue-next.ts` already draws where it settles its pass waiters at
refinement entry. `SceneLoader` tracks that stretch in a `_refining` flag and
exposes `isLoadPassInProgress()` alongside the existing `isUpdateInProgress()`,
which keeps its broader "the lock is held at all" meaning for the adaptive-DPR
manager and the init pipeline.

Subtracting the drain alone would have left a hole exactly where the E2E waits
live. On any laddered dataset the steady state right after a commit is "lock
held, refining"; a keyboard nav arriving then takes `updateView`'s supersede
branch, which parks the state with `viewStateQueue.setPending` and returns
without touching either flag. Both would still describe the refinement that
preceded the request, so the flag would read idle while the slice the user asked
for had not begun loading — every poller would settle on its first poll and
assert against the previous slice, which is the vacuity this change exists to
remove. `isLoadPassInProgress()` therefore also reports the queued slot. It
cannot latch: the slot is cleared by `takePending()` at the moment the next pass
starts, whether that is `queueNext` re-entering `updateView`, the refinement
loop's loop-top cancellation check handing off, or `finalReleaseLock` draining.
`kickRefinementIfIdle` counts a live refinement as busy for the same reason —
the final phase opens the lock while `_refining` is still set (it is cleared one
level up, in the orchestrator's `finally`), and a continuation landing in that
gap would otherwise start a second refinement run whose drain the first run's
`finally` would then mis-report as a load pass.

`dispose()` clears the lock, the refinement flag and any queued view-state, as
defence in depth rather than a fix for an observable bug: only the lock can
genuinely latch (an early update phase bailing before its release runs), and no
production caller can see it, since every `SceneLoaderManager` disposal path
detaches the loader from its map before disposing it — the only self-dispose that
stays in the map is `lifecycle/load-scene.ts`'s, on the loader-reuse path the
class documents as unsupported. That is the manager's ordering hiding a
torn-down loader's state, not the loader being consistent on its own, so teardown
now clears it outright.

One real latch did turn up, in the post-load refinement kick in
`lifecycle/load-scene.ts`. Its rejection handler released the lock but left the
queued view-state alone, unlike its two siblings — `update-view/queue-next.ts`
and `kickRefinementIfIdle` — which drain the slot into a fresh `updateView` and
then settle the parked pass waiters. That slot is routinely occupied in exactly
this window: the kick fires from inside `loadScene`, before it returns, so the
init pipeline's first `updateAllNDNodes` → `updateView` lands while the kick
holds the lock, takes the supersede branch and parks its state. A rejection
escaping outside the refinement loops' own `finally`s — a double fault, not an
expected path — therefore stranded the user's initial slice, and with the queued
slot now counted would also latch `isLoadPassInProgress()` true for good, so
every polling helper would burn its full timeout. The handler is now symmetric
with its siblings: release, drain, resolve.

Two things the flag does not cover, documented rather than fixed here: the
initial `loadScene` (it only touches the lock at its very end, to hand it to the
post-load kick — and an in-page dataset switch therefore reads `isLoading:
false` throughout its load, with `initialized` staying true as well), and lazy
substitutive-LOD / deferred-partition `ensureLoaded` promotions, which run
outside any `updateView` cycle.

No helper CODE changed and no spec was touched — only one
`waitForNavigationComplete` docstring, which claimed a cached path "may never
toggle it true at all". A same-task keyboard nav always does toggle it true
(`updateView` takes the lock before its first await); the honest statement is
that a fully cache-served pass may never be OBSERVED true, because polling is
discrete and such a pass can start and finish between two polls. Nine call sites
do get faster:
`waitForNavigationComplete` used to burn its full 10 s first-phase timeout on
every call, and its six callers in `spatial-index-accuracy.spec.ts`, two in
`dimension-animation.spec.ts` and one in `keyboard-input-system.spec.ts` now
settle as soon as the loader is idle.
