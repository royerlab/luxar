#### The LOD cross-fade sweep now actually moves the camera (#1930)

`lod-group.spec.ts`'s volumetric cross-fade test swept 61 camera distances and
found "a single level at opacity 1" — because the sweep never left the opening
framing. Two independent reasons, both of which fail silently:
`__luxarDebug.controls` is the `ControlsManager`, which has no `target` field, so
`debug.controls?.target ?? {x:0,y:0,z:0}` read the world origin instead of the
real pivot; and `runUpdateStep` step 8 re-applies the controls' own
target/orientation/distance to the camera every frame, so a bare
`camera.position.set()` is overwritten on the next line unless `reinitialize()`
re-derives the orbit state from it first. All 61 iterations therefore sampled the
same settled pose — which sits outside both bands of the fixture's 0 / 0.5 / 1.0
ladder, so one level at full opacity was the correct answer for the pose the test
was in. Nothing was wrong with volumetric cross-fading.

`helpers.ts` gained the one definition of the placement idiom:
`placeCameraAt(page, position, { target, up })` writes the position, aims at the
active controls' pivot, `reinitialize()`s and `update()`s, and returns the
post-clamp pose plus a `viaOrbitControls` flag saying whether any controller
actually re-derived the write — so a caller can PROVE the camera moved instead of
assuming it. `getCameraPivot` reads the pivot for poses expressed relative to the
content centre, and THROWS when there is none rather than answering with the
world origin: a silent origin fallback is half of what hid this bug, so the
helper written to end it does not ship one. Both are thin wrappers over a page-side
`window.__luxarE2ECamera`, so the lod-group sweep — which places the camera 61
times inside ONE `page.evaluate` — and `ortho-mode.spec.ts`'s `putCameraOffAxis`,
converted here, drive the same routine rather than three copies of it.

`withOrbitDistanceLimits` (widen the orbit distance clamp for the duration of a
body, restore in a `finally`) is kept but demoted to DEFENSIVE, because the
original rationale was overstated: the clamp is
`[D / 1000, D × 10000]` around the framing distance `D`
(`ZOOM_IN_FACTOR`/`ZOOM_OUT_FACTOR`), measured as `[0.0138, 137990]` on the
`test_lines` fixture. The lod sweep spans `0.15·D … 15·D` and the line
placement sits at `~D/3`, both two-plus decades inside it, so the clamp could
not have fired at either site — the missing `reinitialize()` was the whole
cause. The wrapper is kept on the lod sweep only because that sweep's range is
a knob that could be widened past `D/1000`. It now THROWS when the widening
could not be applied (non-orbit
controls) instead of silently running the body under the original clamp.

The reworked sweep records every step's distance scale, post-clamp camera
distance and `{idx, opacity}` vector, attaches the whole trace to the Playwright
report as JSON, and renders it into the failure message of the assertions that
can go red — so a future failure distinguishes "the band exists but is narrow"
from "the opacities are only ever 0 or 1". Most importantly it now asserts that
the camera moved at all — observed distance spread > 10x across a requested ~100x
span, and every placement re-derived by orbit controls — which is exactly the
failure mode that hid here. Each observed band is also checked as a DISSOLVE
rather than just a pair of partial weights: within a band the finer level's
opacity must fall monotonically as the camera retreats, and must actually vary.
Adjacency + strict partiality + `sum ≈ 1` are all satisfied by an inverted weight
mapping and by a constant 50/50 split (a pop at each band edge — the very defect
the cross-fade prevents), and the trace already carries the distance needed to
rule both out. The blend-state read was
moved inside the widened-limits window and parked at the pose where the blend was
observed, so it samples the cross-fading pair rather than whatever the far end of
the sweep left on screen.

With the camera finally moving, the trace exposed a second defect the old
assertion could not see: it was DISCONTINUOUS. The 0↔1 band cross-faded, but the
1↔2 band — which the fixture's ladder puts squarely inside the swept range — was
missing entirely, because the sweep outran the loader. The registry requests a
level's chunks only when that level is first needed and holds the resident level
at opacity 1 until the replacement has arrived, so a fast sweep crosses the
boundary before the incoming level exists and the band never happens (the server
log showed `child_1`'s chunks arriving ~4 s after `child_0`/`child_2`'s). The
sweep now runs a bounded residency warm-up first: coarse passes over the same
range (every 4th step) repeated until every level published by the scene has been
observed VISIBLE at least once — the in-page proxy for "resident" — bounded by a
12 s WALL CLOCK and nothing else, so a page that never settles still runs the
measuring pass and reports what was actually observed instead of hanging. The
clock is the only bound on purpose: residency is gated on chunk fetches, so the
only useful response to "not resident yet" is to keep the loop turning, and an
incomplete warm-up therefore always spent its entire budget — which is what makes
incompleteness mean "the data did not arrive in 12 s" and nothing else. Typical
cost is a few seconds of wall clock.

The assertion was tightened to match: instead of "some cross-fade happened
somewhere", the sweep collects EVERY crossing that meets the cross-fade contract
and requires each adjacent pair — derived from CONSECUTIVE observed level
indices, with a contiguity check so a level the probe cannot see fails loudly
rather than quietly shrinking the contract — to have been seen fading. That is
the assertion that would have caught the loader race, and it makes the test a
per-boundary cross-fade guard. Contiguity is checked against the lod group's own
`children.length` as well as against `0…n`, because `[0, 1]` is contiguous: a
nested `kind=lod`/`kind=partition` child attaches as an ANONYMOUS placeholder
group, and the finest level is the natural place for one, so a missing tail is
invisible to a name-matching probe.

The strength of that claim follows the evidence, because per-boundary residency
is not an implementation invariant: the registry hard-swaps instead of blending
on several legitimate paths (partner not yet loaded, never-downgrade display
hold, off-screen pinning, `?noLodFade`, a manual level lock), and the warm-up
compensating for that is bounded by a clock. So the strict per-boundary
assertion holds only when the warm-up reached residency AND the sweep was not
truncated. What replaces it otherwise is a NARROWER contract, not the absence of
one: a run whose warm-up came up short still requires a genuine cross-fade for
every adjacent pair among the levels that DID become resident. That is nearly as
strong — every pair that does not touch the missing level still has to fade — and
it cannot go red on a healthy product, because a level that never arrived cannot
fade. A never-displayed END level costs the contract one pair; a MIDDLE one costs
two, so on the three-level fixture a missing level 1 leaves no pair to claim and
the run falls to the floor ("something was displayed"), which the annotation says
in as many words. Only a TRUNCATED sweep, which never visited
part of the distance range and so implies no particular subset of pairs, falls
all the way back to the pre-change contract of at least one genuine cross-fade
with every per-blend invariant still enforced. Each narrowing is said loudly, in
the failure text and in a `degraded` annotation that names the levels which were
never displayed. The failure messages name the missing pairs and
print the warm-up and sweep summaries next to the trace, so "the fade is broken",
"the level was never resident" and "the sweep ran out of time" are
distinguishable at a glance. The test also raises its own timeout to 150 s: its
in-page budgets (12 s warm-up + 90 s sweep) can outlast the suite-wide 60 s one,
and being killed mid-`page.evaluate` discards the very attachment the test exists
to produce. The sweep now STOPS at its deadline (recording the truncation) rather
than paying one more frame per remaining step — and that deadline is sized from
the budget actually available, because truncation costs assertion strength and
must stay exceptional: 61 steps of paced frames on a single-worker,
software-rendering runner are plausibly the same order as the 20 s first tried,
which would have made the degraded path the normal CI outcome.

Two more inert camera sites were converted to the same helper:
`gsplat-rendering-visual.spec.ts`'s "camera rotation does not produce shader
errors" (four rotations that all rendered the same pose) and
`line-rendering-visual.spec.ts`'s near-camera line test (whose camera never
reached the scene origin it claims to sit at). Both now ASSERT the returned
placement — non-null, orbit-re-derived, coordinates where they asked — so a
regression in the helper makes them fail instead of going quietly inert again.
The line test's "no full-screen artefact" check was unfalsifiable while it was
there: the fixture's vertices carry a red→blue gradient (green is 0 on every
vertex), so its `r>240 && g>240 && b>240` on all four corners could never be
true. It now asserts a TWO-SIDED contract: at least one central sample is painted
(something rendered) and at least one canvas corner still reads as background
(it did not paint the whole viewport). The corner half is what the artefact
actually DESTROYS, and needs no colour threshold to defend — but four background
corners are equally consistent with an EMPTY frame, so on its own it would stay
green through a regression in the very mechanism the test names, `uNearCull`
degenerating every segment. The central half, sampled with the same 3×3 grid
idiom as the cap-factor test in the same file, is the complement. A
colour-uniformity threshold would not have worked either: adjacent vertices
differ by ~28/255 in R and B across a single segment, so an artefact that keeps
any of the line's own interpolation is wider than any spread bound tight enough
to mean something. Both sample sets are logged on every run, so "the healthy
frame really does paint the middle and leave a corner dark" is checkable from the
run log instead of assumed.
