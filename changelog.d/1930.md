#### The LOD cross-fade sweep now actually moves the camera (#1930)

`lod-group.spec.ts`'s volumetric cross-fade test swept 61 camera distances and
found "a single level at opacity 1" — because the sweep never left the opening
framing. Two independent reasons, both of which fail silently:
`__luxarDebug.controls` is the `ControlsManager`, which has no `target` field, so
`debug.controls?.target ?? {x:0,y:0,z:0}` read the world origin instead of the
real pivot; and `runUpdateStep` step 8 re-applies the controls' own
target/orientation/distance to the camera every frame, so a bare
`camera.position.set()` is overwritten on the next line unless `reinitialize()`
re-derives the orbit state from it first. All 61 iterations therefore sampled the
same settled pose — which sits outside both bands of the fixture's 0 / 0.5 / 1.0
ladder, so one level at full opacity was the correct answer for the pose the test
was in. Nothing was wrong with volumetric cross-fading.

`helpers.ts` gained the one definition of the placement idiom:
`placeCameraAt(page, position, { target, up })` writes the position, aims at the
active controls' pivot, `reinitialize()`s and `update()`s, and returns the
post-clamp pose plus a `viaOrbitControls` flag saying whether any controller
actually re-derived the write — so a caller can PROVE the camera moved instead of
assuming it. `getCameraPivot` reads the pivot for poses expressed relative to the
content centre. Both are thin wrappers over a page-side
`window.__luxarE2ECamera`, so the lod-group sweep — which places the camera 61
times inside ONE `page.evaluate` — and `ortho-mode.spec.ts`'s `putCameraOffAxis`,
converted here, drive the same routine rather than three copies of it.

`withOrbitDistanceLimits` (widen the orbit distance clamp for the duration of a
body, restore in a `finally`) is kept but demoted to DEFENSIVE, because the
original rationale was overstated: the clamp is
`[D / 1000, D × 10000]` around the framing distance `D`
(`ZOOM_IN_FACTOR`/`ZOOM_OUT_FACTOR`), measured as `[0.0138, 137990]` on the
`test_lines` fixture. The lod sweep spans `0.15·D … 15·D` and the line
placement sits at `~D/3`, both two-plus decades inside it, so the clamp could
not have fired at either site — the missing `reinitialize()` was the whole
cause. The wrapper is gone from `line-rendering-visual.spec.ts` and kept on the
lod sweep only because that sweep's range is a knob that could be widened past
`D/1000`. It now THROWS when the widening could not be applied (non-orbit
controls) instead of silently running the body under the original clamp.

The reworked sweep records every step's distance scale, post-clamp camera
distance and `{idx, opacity}` vector, attaches the whole trace to the Playwright
report as JSON, and renders it into the failure message of the assertions that
can go red — so a future failure distinguishes "the band exists but is narrow"
from "the opacities are only ever 0 or 1". Most importantly it now asserts that
the camera moved at all (observed distance spread > 10x across a requested ~100x
span), which is exactly the failure mode that hid here. The blend-state read was
moved inside the widened-limits window and parked at the pose where the blend was
observed, so it samples the cross-fading pair rather than whatever the far end of
the sweep left on screen.

With the camera finally moving, the trace exposed a second defect the old
assertion could not see: it was DISCONTINUOUS. The 0↔1 band cross-faded, but the
1↔2 band — which the fixture's ladder puts squarely inside the swept range — was
missing entirely, because the sweep outran the loader. The registry requests a
level's chunks only when that level is first needed and holds the resident level
at opacity 1 until the replacement has arrived, so a fast sweep crosses the
boundary before the incoming level exists and the band never happens (the server
log showed `child_1`'s chunks arriving ~4 s after `child_0`/`child_2`'s). The
sweep now runs a bounded residency warm-up first: coarse passes over the same
range (every 4th step) repeated until every level published by the scene has been
observed VISIBLE at least once — the in-page proxy for "resident" — capped at 6
passes and 12 s, and fail-open, so a page that never settles still runs the
measuring pass and reports what was actually observed instead of hanging. Typical
cost is a few seconds of wall clock.

The assertion was tightened to match: instead of "some cross-fade happened
somewhere", the sweep collects EVERY crossing that meets the cross-fade contract
and requires each adjacent pair — derived from CONSECUTIVE observed level
indices, with a contiguity check so a level the probe cannot see fails loudly
rather than quietly shrinking the contract — to have been seen fading. That is
the assertion that would have caught the loader race, and it makes the test a
per-boundary cross-fade guard.

The strength of that claim follows the evidence, because per-boundary residency
is not an implementation invariant: the registry hard-swaps instead of blending
on several legitimate paths (partner not yet loaded, never-downgrade display
hold, off-screen pinning, `?no-lod-fade`, a manual level lock), and the warm-up
compensating for that is bounded and fail-open. So the strict per-boundary
assertion holds only when the warm-up reached residency AND the sweep was not
truncated; otherwise the test falls back to the pre-change contract — at least
one genuine cross-fade, every per-blend invariant still enforced — and says
loudly, in the failure text and a `degraded` annotation, that this run could not
check every boundary. The failure messages name the missing pairs and print the
warm-up and sweep summaries next to the trace, so "the fade is broken", "the
level was never resident" and "the sweep ran out of time" are distinguishable at
a glance. The test also raises its own timeout to 150 s: its in-page budgets
(12 s warm-up + 20 s sweep) can outlast the suite-wide 60 s one, and being killed
mid-`page.evaluate` discards the very attachment the test exists to produce. The
sweep now STOPS at its deadline (recording the truncation) rather than paying one
more frame per remaining step.

Two more inert camera sites were converted to the same helper:
`gsplat-rendering-visual.spec.ts`'s "camera rotation does not produce shader
errors" (four rotations that all rendered the same pose) and
`line-rendering-visual.spec.ts`'s near-camera line test (whose camera never
reached the scene origin it claims to sit at). Both now ASSERT the returned
placement — non-null, orbit-re-derived, coordinates where they asked — so a
regression in the helper makes them fail instead of going quietly inert again.
The line test's "no full-screen artefact" check was unfalsifiable while it was
there: the fixture's vertices carry a red→blue gradient, so its
`r>240 && g>240 && b>240` on all four corners could never be true. It now asserts
what the artefact would actually produce — all four corners painted in the same
colour — with an "all four painted" precondition so a legitimately dark frame
does not trip it.
