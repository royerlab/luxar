#### `optimize` decides a payload-name collision from a listing, not a lookup

A store whose group carries a payload attr naming a case-shifted zarr metadata
document — `image_file = "Zarr.json"` — with no such file behind it is skipped
with a notice, on every platform. It used to be refused on macOS and Windows,
and the refusal quoted the wrong bytes.

`_copy_payload_files` has to separate two stores that spell a payload the same
way: one whose attr dangles, which the re-chunk should skip (the output is then
exactly as complete as its input), and one that really holds a distinct file
called `Zarr.json`, which it must refuse, since writing that key on a
case-insensitive filesystem replaces the document the whole node is read
through. It told them apart by trying to READ the name — and that is the one
question an open-by-name cannot answer here, because the OS resolves it: on the
very filesystems the branch exists for, `Zarr.json` folds onto the group's own
`zarr.json` and comes back full of bytes. So the skip was unreachable there, a
merely incomplete store was stranded instead of re-chunked, and the refusal
reported the node document's size while advising the user to rename a payload
file that does not exist. The CI filesystem does not fold, so the existing
regression test passed there and failed on a developer's laptop.

The verdict now comes from a directory listing compared case-sensitively in
Python. `_zarr_compat.list_raw_keys` reports the key names stored directly under
a group's own prefix — store-agnostic, like its `read_raw_bytes` neighbour, and
verified against `LocalStore`, `MemoryStore` and `ZipStore`. A listing is not
folded, so the copy consults it first and only reads a name the store really
holds — which is what keeps the dangling case visible on every platform. It
reports every immediate child, subdirectories included, so the read still has
the last word: a name held by a child group rather than a file has no bytes to
drop and no file to rename, and takes the same skip as a dangling attr. The
hasher's name gate is deliberately untouched: it feeds the content hash, and
tightening it would move the digest of every store carrying such a name.
