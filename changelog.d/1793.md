#### An OME-Zarr level declared as `"./0"` resolves again (#1793)

NGFF lets a `multiscales` block spell its own levels explicitly relative — `"./0"`
is a legal spelling of `"0"` — and writers do emit that form. The
metadata-MATCHING half of the reader already saw through it, but
`_declared_levels` handed the declared path straight to zarr, which rejects a path
holding a `.` segment outright (`ValueError: The path './0' is invalid…`, at both
zarr formats). So an image group whose pyramid is declared `["./0", "./1"]`
resolved *no* level at all.

Everything downstream then degraded together, and plausibly. With no declared
level resolved, the block stops being evidence about the array that was selected,
so the owning group's `multiscales` is rejected as "does not name it" and
discovery falls through to the ndim shape heuristic: a 4D `TZYX` store is read as
`CZYX`, which fans a `batch-fit` out over the wrong axis. The declared voxel size
is lost with it, and selection falls back to the largest array in the group — so a
declared full-resolution level that happens to be smaller than an undeclared
sibling (a projection, a scratch copy) loses to it and the fit runs against the
wrong data. It was loud, at least: a per-level `Skipping declared level` line plus
the give-up notice.

The declared path is now normalised at that one lookup boundary, through the same
`_normalised_dataset_path` rule the matching side uses, so both halves apply the
same rule to any string spelling. A path still holding a `.` segment after the
single leading `./` is removed (`"."`, `"a/./b"`) names no level under any
spelling; those fall back to the slash-stripped original, so the lookup still
fails and is still reported under that spelling rather than vanishing or becoming
a lookup of some other array. The `labels/` exclusion and the returned key path
are both taken from the normalised spelling: a mask declared as
`"./labels/seg/0"` stays excluded, and the key the loader prints
(`Using array '0/0'`) is one a reader can pass straight back as `--array-key`,
which `"0/./0"` would not have been.

**A store that spells its levels `./N` may now select a different array**, and
read different axes off it — that is the point of the fix, but it is a change of
answer for an input that already worked its way through a pipeline. The 4D
`CZYX`→`TZYX` correction changes the T/C fan-out, and a pyramid mixing spellings
(`["./0", "1"]`) used to select the half-resolution level and now selects the
declared full-resolution one. Nothing carries an input fingerprint across that:
`batch-fit run` re-plans from `discover_ome_zarr_shape` on every resume and skips
completed tiles by output filename, so a batch planned before this change and
resumed or merged after it can mix two different `(t, c)` fan-outs, and
`merge --refine volume` would re-open a different array than its tiles were
fitted against — as would `gsplat lod --refine volume --target <store>` against a
pre-fix fit. Re-plan such a batch rather than resuming it.

One adjacent silent drop closed with it: a declared level that resolves to a
*group* is now reported like any other dropped declaration (`names a Group, not
an array`) instead of disappearing into the ndim heuristic unexplained.
