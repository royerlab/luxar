#### The WASM loader no longer needs a browser to resolve its own URL (#1642)

`initWasm()`'s dev-server branch resolved the shim against `self.location.origin`.
`self` does not exist in Node, so in any DOM-less host — SSR, a Node-based
embedder, a plain `node` test environment — the loader threw
`ReferenceError: self is not defined` before it ever reached the dynamic import,
and the `catch` flattened that into the documented "no WASM build" TypeScript
fallback. The fallback is the right answer for a missing artifact and the wrong
answer for a loader that assumed a browser, and because the TypeScript reference
implementation is a real production backend (it is the >16-dimension path), the
degradation was silent.

The origin branch now reads the bare `location` global through `typeof`, which
is present in both window and dedicated-worker scopes and never throws
elsewhere. A host without one falls through to the `import.meta.url`-relative
path: there is no dev-server origin to resolve against in Node, so the
bundle-relative URL is the only resolution that could mean anything there. The
fallback warning also names the URL it tried (or says resolution failed before
the import), since "the artifact isn't there" and "the loader never computed a
URL" read identically otherwise — precisely how this stayed invisible.

The seven test files pinned to jsdom to supply `self` are back on `node`. They
were not buying compiled-kernel coverage: `initWasm`'s success path cannot run
under vitest in *any* environment, because its
`new Function('url', 'return import(url)')` indirection is not serviceable by
vitest's VM module runner. jsdom only changed which error the `catch` swallowed.
Tests that want the real kernels load the built artifact through
`src/tests/helpers/wasm-artifact.ts`, and the comments in the two `wasm/` test
files that credited jsdom for the limitation now say so.
