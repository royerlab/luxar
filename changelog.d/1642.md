#### The WASM loader no longer needs a browser to resolve its own URL (#1642)

`initWasm()`'s dev-server branch resolved the shim against `self.location.origin`.
`self` does not exist in Node, so a **dev build** running in a DOM-less host — a
plain `node` test environment being exactly that — threw
`ReferenceError: self is not defined` before it ever reached the dynamic import,
and the `catch` flattened that into the documented "no WASM build" TypeScript
fallback. The dereference sat inside the `import.meta.env.DEV` branch and Vite
folds that constant to `false` in the production and library builds, so a host
consuming the published bundle never reached it. The fallback is the right answer
for a missing artifact and the wrong answer for a loader that assumed a browser,
and because the TypeScript reference implementation is a real production backend
(it is the >16-dimension path), the degradation was silent.

The origin branch now reads the bare `location` global — present in both window
and dedicated-worker scopes — and reads it through `typeof`, so a dev build in a
host that merely lacks the global falls through to the
`import.meta.url`-relative path: there is no dev-server origin to resolve
against in Node, so the bundle-relative URL is the only resolution that could
mean anything there. The fallback warning also names the URL it tried (or says
resolution failed before the import), since "the artifact isn't there" and "the
loader never computed a URL" read identically otherwise — precisely how this
stayed invisible.

What this does *not* do is hand a DOM-less host compiled kernels. `initWasm` is
not part of the package's public exports, and `LuxarApp.init` refuses a caller
with no `window`/`document` outright, so such a host only reaches the loader by
deep-importing internals; even then Node cannot load the artifact through it,
because the wasm-bindgen shim's async `default()` fetches a `file://` URL and
Node rejects that with `TypeError: fetch failed`. The change is that the loader
stops dying on a missing browser global and starts reporting which URL it tried,
which is what makes this class of downgrade visible in the first place.

The seven test files pinned to jsdom to supply `self` are back on `node`. They
were not buying compiled-kernel coverage: `initWasm`'s success path cannot run
under vitest in *any* environment, because its
`new Function('url', 'return import(url)')` indirection is not serviceable by
vitest's VM module runner. jsdom only changed which error the `catch` swallowed.
Tests that want the real kernels load the built artifact through
`src/tests/helpers/wasm-artifact.ts`, and the comments in the two `wasm/` test
files that credited jsdom for the limitation now say so.
