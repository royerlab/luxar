#### The Zenodo uploader authenticates by header and fails without a URL (#1706)

`scripts/zenodo_upload_draft.py` sends its `deposit:write` credential as an
`Authorization: Bearer` header and never in a URL, so it cannot be copied into
server or proxy access logs, a TLS-terminating middlebox's records, or anything
that formats `HTTPError.url`. The header is *unredirected*: `urllib` copies
ordinary headers onto a redirect's follow-up request, whatever host `Location`
names, so this one is withheld there and a redirect fails closed instead. A bucket
PUT that is rejected, or that dies at the transport level instead of answering with
a status, exits non-zero naming the file and the status or reason — never the URL.
That includes the failures `urllib` does not wrap in `URLError`
(`RemoteDisconnected`, a read timeout, a bad status line, a short body), which are
the likely end of a multi-GB transfer: Zenodo checksums the body only after all of
it lands, so the long wait is on the response.

`ZENODO_TOKEN` is also stripped, and refused outright if a line break survives
inside the value. A CRLF-terminated token file used to work by accident — a URL
drops `\r` and `\n`, a header value does not — and the resulting `ValueError` from
`http.client` would have printed the whole credential.

The bucket URL now percent-encodes the filename, which is a path segment rather
than free text: a space in it used to be rejected as an illegal request line
before any byte went out, and a `?` or `#` truncated the key Zenodo stored the
file under — so a re-run no longer recognised it and uploaded it again.
