#### bioformats2raw stores load instead of crashing on `'Group' has no attribute 'shape'` (#1777)

`bioformats2raw` — the converter most of the OME ecosystem produces its zarr with
— writes one image **group** per series (`0`, `1`, …) with the pyramid levels one
level further down (`0/0`, `0/1`, …), plus an `OME` metadata group at the root.
Three separate places picked the array to read with the same `elif "0" in store:
arr = store["0"]` branch and then asked the result for `.shape`, so such a store
died with `AttributeError: 'Group' object has no attribute 'shape'` in
`discover_ome_zarr_shape` and `load_volume`, and was refused with a
`ValueError` in `open_volume_lazy` — despite its `0/0` being right there and
findable. Both on-disk zarr formats, identically.

The rule now lives in one place, `luxar.io.volume._select_zarr_array`, which all
three call: an explicit `array_key` (nested paths allowed, blank treated as
absent, and a key naming a *group* now descends into it instead of crashing),
else NGFF resolution level `"0"` when that really is an array, else the largest
array found recursively — with a size tie broken on the lowest key path, because
`zarr` does not stabilise key order across opens and the planner and a per-tile
worker are different processes. The three had to move together — had discovery
alone started succeeding, `batch-fit` would have written a whole plan and then
lost every task to the same crash. When `"0"` is a group, resolution is **scoped
to that group**: the store root also holds the other series and the `OME` group,
so a whole-store search could hand back level 0 of a *different image*, which is
a plausible wrong answer rather than an error. Inside the group the candidates
are narrower still — the levels its own `multiscales` block declares, else its
direct array children, else (skipping `labels/`) whatever is nested below —
because NGFF puts an image's segmentation masks at `<image>/labels/<name>/<level>`
and a mask as big as level 0 would otherwise be fitted instead of the image.
Scoping keeps the existing intent: full resolution of the first image, and it is
terminal — an image group holding no array of its own is a `ValueError` naming
the group, not a fall-through to the unscoped whole-store sweep, which would
answer with that image's own mask (a group holding only `0/labels/seg/0`) or with
a different series (an empty one). The owner reported for the selected array is
resolved by one rule as well, the nearest ancestor whose `multiscales` declares
it — for *every* route, the whole-store sweep included. That last one was the
hole: with no `"0"` at the root the sweep reports the level's immediate parent, so
a store whose `img` group declares `res/0` gave `img/res` as owner and only the
no-key spelling fell through to the ndim heuristic, losing the declared axes and
voxel size while `--array-key img`, `img/res` and `img/res/0` all read them. A
rule that skips one route is not a rule: the route left out gives the same array
different axes and a different `batch-fit` fan-out, decided by nothing but the
spelling. The resolution also no longer re-walks a block the search just walked —
a group reported as declaring nothing was already asked, so the ancestor walk
starts above it (a store with a stale four-entry `multiscales` cost 14 group
lookups, five of them exact repeats; now 9 with none).
The terminal "group holds no array" error stopped blaming a key nobody passed:
with no `--array-key` it names the OME-NGFF `"0"` convention that actually chose
that group, and — since the condition is unrecoverable without a key — it lists
the array keys the store *does* hold, so the "`0` is an empty stub, the real image
is at `1`" store answers with `'1/0'` rather than leaving the reader to guess.
A **present but empty** `multiscales` on the owning group is now reported as
"declared but unusable" with the same reason the identical declaration gets on the
root, instead of as "no OME-Zarr/NGFF metadata found" — the one distinction that
notice exists to draw, and it must not depend on which node carries the block.
`_load_zarr_volume` now names the array it actually landed
on (`Using array '0/0'`), where the old "using resolution level '0'" line would
have been a lie.

The metadata half was the quieter half. NGFF `multiscales` was read from the store
ROOT's attributes, but a bioformats2raw store puts that block on the *image* group
and leaves only `bioformats2raw.layout` at the root — so even once the array was
found, discovery would find no `multiscales`, fall through to the shape heuristic,
GUESS the T/C roles (a 4D store is assumed `CZYX`) and recover no voxel size at
all. The root's attributes still stand by default; the group that owns the
selected array now overrides the root's `multiscales`, but only on **evidence**
that its block is about that array — one of the block's own `datasets[*].path`
entries has to resolve to the array that was selected (and the block has to
describe one axis per dimension). A matching axis *count* is not evidence,
because a permuted axis list has exactly the right length: a group can carry a
block describing something else entirely, and adopting that on the strength of
its mere existence would discard good root metadata and rewrite `batch-fit`'s
whole T×C fan-out into a silently wrong plan. An owner block that fails the
evidence gate is *named* in the give-up notice rather than reported as "no
OME-Zarr/NGFF metadata found", which would be a lie about a store that plainly
declares a pyramid — and hides the one detail (its `datasets[*].path` entries do
not resolve to the selected array) that makes it fixable.
The custom (non-NGFF) bare `axes` attribute is the other way round — root first,
owner only as a fallback — because a bare list names nothing, so no such evidence
is obtainable for it; that still fixes bioformats2raw, whose root carries no
`axes` at all.
