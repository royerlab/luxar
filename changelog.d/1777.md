#### bioformats2raw stores load instead of crashing on `'Group' has no attribute 'shape'` (#1777)

`bioformats2raw` — the converter most of the OME ecosystem produces its zarr with
— writes one image **group** per series (`0`, `1`, …) with the pyramid levels one
level further down (`0/0`, `0/1`, …), plus an `OME` metadata group at the root.
Three separate places picked the array to read with the same `elif "0" in store:
arr = store["0"]` branch and then asked the result for `.shape`, so such a store
died with `AttributeError: 'Group' object has no attribute 'shape'` in
`discover_ome_zarr_shape` and `load_volume`, and was refused with a
`ValueError` in `open_volume_lazy` — despite its `0/0` being right there and
findable. Both on-disk zarr formats, identically.

The rule now lives in one place, `luxar.io.volume._select_zarr_array`, which all
three call: an explicit `array_key` (nested paths allowed, blank treated as
absent, and a key naming a *group* now descends into it instead of crashing),
else NGFF resolution level `"0"` when that really is an array, else the largest
array found recursively — with a size tie broken on the lowest key path, because
`zarr` does not stabilise key order across opens and the planner and a per-tile
worker are different processes. The three had to move together — had discovery
alone started succeeding, `batch-fit` would have written a whole plan and then
lost every task to the same crash. When `"0"` is a group, resolution is **scoped
to that group**: the store root also holds the other series and the `OME` group,
so a whole-store search could hand back level 0 of a *different image*, which is
a plausible wrong answer rather than an error. Inside the group the candidates
are narrower still — the levels its own `multiscales` block declares, else its
direct array children, else (skipping `labels/`) whatever is nested below —
because NGFF puts an image's segmentation masks at `<image>/labels/<name>/<level>`
and a mask as big as level 0 would otherwise be fitted instead of the image.
Scoping keeps the existing intent: full resolution of the first image.
`_load_zarr_volume` now names the array it actually landed on (`Using array
'0/0'`), where the old "using resolution level '0'" line would have been a lie.

The metadata half was the quieter half. NGFF `multiscales` was read from the store
ROOT's attributes, but a bioformats2raw store puts that block on the *image* group
and leaves only `bioformats2raw.layout` at the root — so even once the array was
found, discovery would find no `multiscales`, fall through to the shape heuristic,
GUESS the T/C roles (a 4D store is assumed `CZYX`) and recover no voxel size at
all. The root's attributes still stand by default; the group that owns the
selected array now overrides them **per key** (`multiscales`, `axes`), and only
when its block is usable for that array — its axis count has to match the array's
dimensionality. A group can carry a block describing something else entirely, and
adopting that on the strength of its mere existence would discard good root
metadata and rewrite `batch-fit`'s whole T×C fan-out into a silently wrong plan.
