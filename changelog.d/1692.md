#### OME-Zarr 0.5 metadata is read instead of silently guessed

`discover_ome_zarr_shape` only understood the OME-Zarr **0.4** attribute layout,
where the NGFF block sits at the top level of a node's attributes. OME-Zarr
**0.5** — what a zarr v3 store declares, and what every crop of the Biohub
cell-tracking competition data is — nests the whole block one level down under an
`ome` key. Nothing raised: `multiscales` simply came back missing, the custom
`axes` fallback did not match either, and discovery landed on the shape heuristic
that guesses axis roles from ndim and recovers no physical voxel size. On a 4D
`TZYX` store that heuristic reads the TIME axis as a channel, so `batch-fit`
planning fanned out over the wrong axis — seven channels of one timepoint instead
of seven timepoints — while reporting an ordinary-looking result.

Both layouts now parse, resolved in one place by the new exported
`luxar.io.ome_zarr.resolve_ngff_attrs`, which every reader of NGFF attributes
should go through (the demo's local copy of the same logic now calls it). The
layout deliberately cannot be inferred from the store's zarr format version: a
zarr v3 store written by a 0.4-era tool has the v3 chunk layout with top-level
0.4 attributes, so both spellings are always tried. The nested block wins only
when it carries a NON-EMPTY `multiscales` (or when the top level declares none at
all, so "declared but unusable" is still reportable). Presence alone is not
enough, in either direction: an `ome` block holding nothing but `omero` rendering
metadata, or an empty `ome.multiscales` list, must not displace a perfectly good
top-level 0.4 pyramid — that is the same silent mis-read from the other side, and
it made the give-up notice blame an empty `multiscales` that the store did not
have.

Several adjacent wrong answers went with it. A `multiscales` block whose `axes`
count disagrees with the SELECTED array's ndim — the classic image-with-labels
store, a 5D `TCZYX` pyramid beside a 3D `labels/cells` — is not metadata about
that array; it used to be parsed anyway and `batch-fit … --array-key
labels/nuclei` died on a bare `IndexError`, where discovery now falls through to
the remaining fallbacks. For a nested `array_key`, discovery uses a non-empty
`multiscales` block on the array's parent group and matches `datasets[].path`
exactly relative to that owner, so a same-named level in an unrelated root
pyramid cannot supply a confidently wrong spacing. An optional
`coordinateTransformations` on the multiscales entry itself is composed on top
of the per-dataset one rather than ignored. Where that composition or that match
cannot be made honestly, the answer is now no spacing rather than a
plausible one: a multiscales-level scale whose length differs from the dataset's
cannot be composed (a half-composed number was being returned as fact), and an
`array_key` that matches no entry of a multi-level pyramid means the selected
array's spacing is simply unknown. Malformed metadata degrades throughout instead
of raising a traceback out of discovery — a `datasets` that is not a list of
mappings, a `scale` carrying a `null` or a non-numeric string (numeric strings
still convert), an axis record with no `name` or a `null` `type`. And when
discovery does fall through to the heuristic on an ambiguous (≥4D) store it now
says so on the console — naming the guessed labels, the missing voxel size, and
the `axes_override` / `--axes` escape hatch — and distinguishes "nothing
declared" from "declared but unusable", quoting the reason.

`batch-fit` planning gained a guard for what it can now learn. Without an
explicit `--axes` the manifest records no axes, so every fit worker slices the
store POSITIONALLY (`luxar.io.volume._load_zarr_volume`: at 4D it can consume
exactly ONE leading axis, preferring `--channel` over `--timepoint`). Discovery
reading real labels means the planner can learn a layout that contract cannot
reproduce — a `(t, c, y, x)` store planned 5 timepoints × 3 channels while the
workers only ever read 3 distinct volumes, so the merged partition was five
duplicate timepoints and nothing raised. Planning now refuses such a layout up
front. It decides by comparing two sets rather than matching whole layouts
against a per-ndim table: the axes the loader CONSUMES for a task (axis 0 for the
timepoint, the axes that fold into the flat channel index, both read off the
loader's own branches) and the axes the plan FANS over. They have to agree axis
for axis once singleton axes are dropped from both — a size-1 axis is indexed at
0 whatever the task index says, and contributes nothing to a flat channel decode
— and what is left after the loader's indexing has to be the planned spatial
shape, squeezed, because `load_volume` squeezes its positional result. The
set comparison is what admits a 2D timelapse with a singleton channel (`t,c,y,x`
at `(5, 1, 32, 32)`, whose worker `arr[3]` IS the planned volume): the table
refused it while admitting its `T=1` sibling, so its verdict flipped on the size
of T alone. The question is asked of the decomposition discovery published —
`OMEZarrInfo` gained `time_axis` / `channel_indices` / `spatial_indices`, the
axis roles it actually used — and never of the axis LABELS: NGFF classifies by
the `type` field, so re-deriving the roles from names disagrees in both
directions. A channel axis named `stain` looks spatial to a name rule (refusing a
canonical 5D store that always worked), while an axis typed `view` is spatial to
the parser and channel-like to a name rule (waving through a plan that tiles four
dimensions the worker never sees). Layouts whose non-spatial axes are all
singletons — `t,c,y,x` at `(1,1,32,32)`, `z,y,x,c` at `(16,32,32,1)`, `t,y,x` at
`(1,64,64)` — still plan, because `load_volume` squeezes them away; 2D gsplats
are a first-class authoring path and refusing them would be a real regression.

The refusal quotes an `--axes` string only when the store is one that spec can
address, which takes two conditions rather than one. Its vocabulary is narrower
than discovery's (`volume._axis_kind` rejects `stain` and heuristic `dim0…dimN`
labels), so quoting those back prints a command that fails — and worse,
`plan_batch`'s override path is lenient enough to ACCEPT it first, folding the
unknown label into the tile grid so that every worker dies later instead. And a
recognised spec is not sufficient either: `_apply_axes_spec` pins EVERY
channel-kind axis with the same `--channel` value and never decodes the flat
channel index the batch tasks carry, so on a `camera,time,channel,z,y,x` store at
`(2, 3, 2, …)` following the quoted advice plans 4 channel tasks of which task 1
silently loads (camera 1, channel 1) and tasks 2-3 die with "--channel index 2 is
out of range for the 'camera' axis". A spec is therefore quoted only for a store
with at most one channel-like and at most one time label; otherwise the message
says which condition failed — the unrecognised labels, or the second
channel-like axis and why a flat index cannot address it — and asks for an
`--axes` spec of the user's own. (The flat-index limitation in `_apply_axes_spec`
itself is pre-existing and tracked separately; this only stops the refusal from
recommending it.) Forwarding the discovered labels automatically was deliberately
not done, for the same reasons.

Known gap, unchanged and documented on the guard: a size-1 SPATIAL axis. The
loader squeezes it away while the plan's `spatial_shape` keeps it, so a canonical
`t,c,z,y,x` store at `(3, 1, 1, 512, 512)` plans a 3-D `(1, 512, 512)` volume the
worker loads as 2-D `(512, 512)`, and the merged partition's split planes then
name center columns that do not exist. The comparison above is squeezed on both
sides precisely so this keeps planning exactly as it does today; closing it means
dropping the axis from the plan's spatial shape everywhere, which is its own
change.

Known non-goal: a bioformats2raw-style store — root attributes `{"ome":
{"version": "0.5", "bioformats2raw.layout": 3}}` with the `multiscales` block on
a CHILD image group — is still not discovered, and fails with `AttributeError:
'Group' object has no attribute 'shape'` exactly as it did before, because
attributes are read from the root node only. A test pins that error so the day
someone teaches discovery to descend, it says so.

Upgrade note: a `batch-fit` output directory PLANNED against a 0.5 store before
this fix will re-plan after it. The recovered T/C roles change every tile
filename, so a resume refits from scratch and the previously fitted tiles stay
in `tiles/` unreferenced — delete them, or plan into a fresh output directory.
