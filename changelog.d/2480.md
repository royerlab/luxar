#### The CI queue watchdog can see obsidian work inside queued runs

`queue-watchdog`'s repository-wide liveness scan listed only runs whose
**run-level** status was `in_progress`. GitHub reports a run as `queued` while any
one of its jobs is still queued, even as its other jobs execute — and on a push or
the daily full-matrix schedule `max-parallel` deliberately holds one Python leg
queued — so the runs carrying live obsidian legs were exactly the ones the scan
never listed. The fuller the box, the more certain the watchdog was that the box
was dead, and it cancelled whichever healthy run happened to be inside its
ten-minute window: three PRs lost required contexts that way in a single morning,
and a leg cancelled while queued cannot be revived by re-running failed jobs.

The scan now covers both run-level statuses. Covering two statuses out of one
first-come run budget would have reproduced the same failure from the other side —
a full page of queued runs could spend the whole budget and hide the `in_progress`
pass, whose absent evidence reads as a dead box — so `--max-runs` is still spent
first-come, less one run reserved for each status still to come. Every pass is
therefore guaranteed at least a look, no pass is capped while budget remains, and
the worst-case job fan-out per scan is unchanged, the added cost being one
runs-list call; the expected cost does rise, since it is now the queued runs that
are numerous. `--stop-after-running 1` still short-circuits on the first active
job, and `queued` is scanned first because that is where the evidence usually is.
