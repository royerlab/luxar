#### Content hashes now converge across case-insensitive filesystems

A payload attr that named a case-shifted zarr metadata document, such as
`image_file = "Zarr.json"`, could make `content_hash` depend on its own previous
value on macOS and Windows. The hasher's semantic name gate rejects `zarr.json`
exactly, but the shifted spelling passed; an open-by-name then case-folded onto
the group's real `zarr.json`, whose bytes include the hash being restamped.
Repeated compiles or `luxar optimize` runs therefore produced a different digest
each time, while the same store converged on a case-sensitive Linux filesystem.

The hasher now asks the store's immediate-child listing whether this narrow
collision class exists with the exact authored spelling before reading it. A
dangling shifted name folds the same `absent:` term on every platform, while a
store that genuinely holds a distinct case-shifted payload still hashes its
bytes. Ordinary payload names retain the existing store-native lookup semantics;
the listing is not used to enumerate payloads.

Affected macOS and Windows directory stores receive a one-time hash migration to
the platform-independent digest on their next compile or re-chunk; the same
store's digest is unchanged on a case-sensitive filesystem. Republishing the
migrated store invalidates warm viewer caches keyed by the old digest. Subsequent
rewrites converge, and stores without a case-shifted metadata-document payload
name keep their existing hashes.
