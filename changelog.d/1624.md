#### Two `--downscale` gaps in the tiled worker chain (#1624)

A downscaled tile worker no longer forgets its own truncation radius. On the way
to saving, `rescale_and_save` scales a `--downscale`d tile's splats back to
original coordinates, and it did so by rebuilding a plain `GSplatData` from the
top-level (concatenated) arrays — a convenience constructor whose
`truncation_radius` argument defaults, so the fitted value was silently replaced.
`truncate:` is a documented YAML key (`gsplat fit --dump-config` emits it), so
`gsplat fit --tile k/M --downscale N` with a `--config` holding
`truncate: 3.5` stored 2.75: a
wrong radius in that tile's store, on the plain non-progressive path too. The
merge's `concatenate` requires the non-empty tiles to AGREE on the radius, so a
downscaled tile also refused to compose with an un-downscaled sibling. The
rescale now goes through `GSplatData.transform(np.diag(factors))`: a per-axis
rescale IS a diagonal linear transform, its diagonal fast path multiplies centres
and the packed Cholesky by exactly the vectors `rescale_centers` /
`rescale_cholesky_packed` apply, and it carries the radius (and colors, stats and
any additive ladder, per rung) through untouched. The ladder half is a
by-construction guarantee rather than a fixed symptom: every fitter reachable
from this line flattens first (`fit_progressive_gaussian_splats` returns
`final_result.flattened()`), so no ladder arrives here today.

A decimating `downscale:` inside a `batch-fit --config` is now refused at plan
time — but only where the workers' tile grid genuinely disagrees with the planned
one. `batch-fit run` / `batch-fit submit` forward that YAML verbatim to every
array task, and a uniform task is a `fit --tile k/M` run that decimates its own
volume and then recomputes the tile grid on the DECIMATED shape, while the planner
tiled the full-resolution one. When the two grids differ the run cannot complete:
on a 32^3 store with `--tile-size 12 --overlap 2` the plan builds 64 tiles per
slot while a `downscale: 2` worker sees 8, so tiles 8..63 exit 1 with "tile index
out of range" and no merge ever happens. `plan_batch` now compares the grids
directly — same tile count, and every worker tile origin scaled per axis by the
factors (what `rescale_and_save` does to that tile's splats) equal to the planned
origin — and rejects only a real disagreement, before a task is submitted or a
tile is written, naming both tile counts and the working alternatives (`gsplat fit
-j N --downscale ...`, whose grid is computed after the downscale, or
pre-decimating the store). Three shapes are measured to complete correctly and
plan silently: a `--tiling content` plan (a content task is `fit --plan-box K` and
never re-tiles), a single-tile plan, and an anisotropic factor
confined to axes that hold a single tile at full resolution, which leaves the grid
identical. Measured for the last one: spatial `(40, 8, 8)` with `--tile-size 12
--overlap 0` and `downscale: [1, 2, 2]` plans 4 tiles, the worker's decimated
`(40, 4, 4)` also tiles into 4, and all four real `fit --tile k/4` workers exit 0
with their splats in the correct full-resolution slabs. A malformed value
(`downscale: 0`, `2.5`, a wrong-length list) is a plan-time usage error in every
mode, checked before any voxel is sampled or `plan.json` written, and a no-op
(`downscale: 1`, `[1, 1, 1]`) still plans silently.

Relatedly, a batch manifest's `grid_scale` no longer composes in a config
`downscale:` at all. That term is correct for the single-fit `fit --tiling
uniform -j N --downscale` parent, whose tile grid IS built on the decimated
shape, but wrong for a batch run: the planner tiles the full-resolution shape and
every task rescales back to it, so the splats never leave the grid's frame.
Recording it changed no split plane and falsely refused `--merge-refine volume`.
