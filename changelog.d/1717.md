#### `luxar optimize` re-chunks a store that already exists, without touching a value (#1717)

Hosting the demo gallery on object storage exposed a problem that no amount of
bandwidth fixes. The demo corpus (`datasets/demos`, 80 stores) is 606,349 files
for 2.94 GB of real bytes — an average file of 5.1 KB, 97.0% of them under
16 KB and 48.6% under 4 KB, against a `TARGET_CHUNK_BYTES` of 64 KB and a
documented 16-256 KB band. Cold-loading `desi_galaxies` from Cloudflare R2 in a
real browser took 245 s over 9,390 requests as written, and 51 s over 2,348
requests once re-chunked to 64 KB, for 20 s of CPU. It was never bandwidth-bound
— 38.6 MB over 245 s is 158 KB/s — it was round trips.

`luxar optimize src.luxar.zarr out.luxar.zarr` is one structure-preserving pass
that changes zarr chunk shapes and nothing else. No refit, no source volume, no
GPU. Values are bit-identical, and `--verify` re-reads the output and compares
every array — and every payload file the pass copied — byte for byte rather
than trusting a metadata checksum, reporting how many of each it checked. dtype,
compressor, filters, serializer, `fill_value`, memory order and every group and
array attribute except the two the pass must move — the root's `content_hash`
and the `chunk_layout` summary beside it, the cache guard described below —
survive verbatim, and a v2 store stays v2 (format conversion is
`gsplat migrate-format`'s job). Codecs are reused off the SOURCE array rather
than re-derived, because an omitted compressor is not "no compressor" — zarr's
`"auto"` is Blosc/lz4 at format 2 and zstd at format 3 — and some Luxar arrays
are deliberately RAW. The plain non-zarr files a group's attrs name — an overlay
image, written straight into its group's directory and reachable through no
array or group API — are carried across byte for byte and compared by `--verify`
like everything else, so a re-chunked scene does not silently lose an overlay
the source still holds. Three kinds of name never reach the output, and none of
them quietly: one that is not a plain file name (it addresses a key outside the
group's own directory, which the hasher likewise folds in by name and never
reads) is skipped with a notice, as is an attr whose file the source no longer
has; and a name that collides case-insensitively with a zarr metadata document —
`Zarr.json` is an ordinary file on ext4 and the group's own document on macOS —
REFUSES the re-chunk outright when the source really holds those bytes, naming
the file and asking for a rename, rather than dropping the payload and shipping
an `image_file` attr pointing at nothing. A payload the source has but cannot be
read (a mode bit, an NFS hiccup) refuses the run the same way, and that is a
deliberate divergence from the compile-time hasher, which degrades an unreadable
payload to a deterministic term so a compile can still finish: a re-chunk has
nothing to gain from finishing without it. `--target-kb` /
`--target-bytes` set the budget directly,
`--profile {hosting,local,archive}` picks 256 KB / 64 KB / 1 MB, `--dry-run`
reports without writing, and `--generic` allows a plain zarr store.

This is not the writer fix (#1713) applied twice. It reaches data that already
exists, where regeneration means a GPU-days refit or a new Zenodo DOI. It sizes
from the STORED dtype, where the writer can only see the input dtype — float32
positions, before the encoder quantizes them to uint16 — which leaves its chunks
2-4x under target; on `spiral_galaxy` the writer fix bought 3.1x fewer requests
and re-chunking bought 8.6x. And authoring and serving want different targets,
which is a flag rather than a rebuild.

The hard part is what must NOT move. `chunk_size` and `chunk_bounds` are the
viewer's partition grid, so every emitted chunk is a whole multiple of the
node's atom — rounded down from the byte budget, never below one atom — and no
row-range read straddles a boundary; Lines' two atoms
(`vertex_ordering.chunk_size` for the per-vertex arrays,
`segment_ordering.chunk_size` for `segments` alone) are resolved separately, and
the bounds arrays themselves are never re-chunked. A `chunk_size` attr is
believed only when the matching bounds array is there: a gsplat leaf written
with `ordering="none"` still gets a default `chunk_size` stamped, its arrays are
not on that grid, and the stamped value is a power of two — so "the array's
chunk is already a multiple of it" is a coincidence, not proof. `array_ref`
placeholders (physical shape `(0, D)`), `(1,)` / `(1, k)` broadcasts and sharded
arrays are copied as-is, a sharded array keeping its SHARD grid rather than
having its inner chunk shape promoted; the chunk key layout (v2
`dimension_separator` / v3 `chunk_key_encoding`) survives; nothing is ever
chunked smaller than it already is; and the copy runs in chunk-aligned slabs,
never `arr[:]` on a whole array — the corpus contains a 629 MB one, and the
content-hash recompute is slab-wise for the same reason.

Cache invalidation is the part with no error to raise, so it is worth stating
which half does the work. The viewer's `MultiLevelCachingStore` validates its
persistent cache on `content_hash`, and that cache holds encoded chunks keyed by
chunk index, so a re-chunk that left the hash where it was would have chunk key
`0/0` covering a different row range while a warm client believed itself current.
Since #1719 and #1721 both hashers fold layout in themselves —
`compute_content_hashes` hashes each array's storage identity (name, shape,
dtype, chunks, shards, codec ids, own attrs) before its values, and the
`.gsplats.zarr` stamp folds the same identity terms over metadata alone — so
recomputing over the output lands on a different digest by construction. What
makes that reach the viewer is the RESTAMP: nothing else rewrites the stored
`content_hash`, and the stored one is what gets compared. The `chunk_layout`
summary attr written on the root is folded in too (attrs ARE hashed):
belt-and-braces against a layout-aware hasher, and still the whole guard for a
store carrying no `content_hash` to restamp, where the viewer falls back to a
digest of the raw root document bytes. The restamp runs for `--generic` too:
that flag describes the INPUT, and gating cache safety on it shipped
re-chunked Luxar scenes under their source's hash.

The output is all-or-nothing. It is built in a hidden sibling directory and
renamed into place only after the copy — and `--verify`, when asked for — has
succeeded, so a failure leaves neither a half-written store at the destination
nor a damaged previous one. A `.zarr.zip` destination is compressed out of that
directory rather than written into a `ZipStore`, which appends rather than
replaces: writing directly produced 211 members for 50 unique names, and under
`-W error` the duplicate-name warnings were a hard failure. Overwriting an
existing output needs `--overwrite`, which replaces an existing zarr store or an
empty directory and refuses anything else; a destination that contains the
source or lives inside it is rejected before the source is even opened; and
rewriting in place is refused outright, precisely because "republish under a new
URL prefix" is the real fix and cannot be enforced from a CLI.

`luxar info --stats` grew the matching diagnostic, computed off the same helper:
average chunk KB, the share of arrays under the 16 KB floor, and the projected
request count for a full load. The problem is now visible before you host
something and count round trips.

`--jobs` is deliberately not implemented. The pass is ~20 s of CPU on the
measured dataset and the copy is I/O bound; parallelism can come later if a
corpus-wide sweep ever wants it.
